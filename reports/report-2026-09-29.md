## Platform Details

### Claude Enterprise (Anthropic)

- **The advisor tool — a caller-configured second model that reads the entire
  conversation server-side, first audit.** Tool type `advisor_20260301`, name `advisor`.
  A faster "executor" model can consult a higher-intelligence "advisor" model mid-turn.
  When it does, the executor emits a `server_tool_use` block whose `input` is **always
  empty** — "the server constructs the advisor's view from the full transcript
  automatically." What the advisor receives is the executor's **full transcript**, and the
  docs enumerate it: "your system prompt, the tool definitions, the prior turns and tool
  results, and the text the executor has produced so far in this turn." The advice returns
  in an `advisor_tool_result` block and the executor continues. All inside one
  `/v1/messages` call. Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool

- **On current models, the advice text is unreadable by the customer.**
  `advisor_tool_result.content` is a discriminated union: `advisor_result` carries plaintext
  `text`, while `advisor_redacted_result` carries `encrypted_content`. Sonnet 5.5, Fable
  5.1, Mythos 5.1, Opus 5.5, Opus 5, Fable 5 and Mythos 5 advisors all return the encrypted
  variant, **and those same models as executors pair only with advisors that return the
  encrypted form** — so, in Anthropic's own words, "on those executors the advice text isn't
  readable in the response." Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool#result-variants

- **`max_uses` defaults to unlimited.** The tool takes `model` (required — the advisor's
  model ID, billed at that model's rates), `max_uses` (**default unlimited**; exceeding it
  yields `advisor_tool_result_error` with `error_code: "max_uses_exceeded"` and the executor
  simply continues), `max_tokens`, and a `caching` on/off object. It also accepts the
  generic `allowed_callers`, `defer_loading` and `cache_control` properties. Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool#tool-parameters

- **A second, differently-shaped form exists on Claude Managed Agents.** There the advisor
  is configured **as part of the agent, not as a tool** — a `{"type": "advisor", "model":
  ...}` entry in the agent's **multiagent roster** — it takes no `max_uses`, `max_tokens` or
  `caching`, and the advice arrives as **thread events on the session's event stream** rather
  than as `advisor_tool_result` blocks. Any detector keyed on the block type misses this
  path entirely. Source: https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration#give-the-session-an-advisor

- **Availability:** beta on the Claude API and on Claude Platform on AWS. Explicitly **not**
  available on Amazon Bedrock, Google Cloud, or Microsoft Foundry. The advisor must be
  Sonnet 4.6 or better and at least as capable as the executor; invalid pairs return a
  `400 invalid_request_error`. Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool#model-compatibility

- **Claude Sonnet 5.5 shipped 2026-09-28 with account-bound thinking blocks.** Thinking
  blocks the model produces "work only in the account that produced them, or in an account
  linked to it. When another account sends one of these blocks, **the API drops the block
  before the model sees it, and the request succeeds**." Blocks from earlier models are
  unaffected. The failure is silent — no error, just a model that no longer sees its own
  prior reasoning. Source: https://platform.claude.com/docs/en/build-with-claude/preserved-thinking#account-bound-thinking

### Google Gemini Enterprise

- **Resource-level IAM on apps and data stores (2026-09-28).** Administrators can now
  "configure granular, resource-level Identity and Access Management (IAM) permissions to
  restrict access to specific Gemini Enterprise apps and data stores using the Google Cloud
  console, the Google Cloud CLI, or the REST API." The Gemini Enterprise Admin, Viewer and
  User roles can be granted on an individual app or data store without project-wide access,
  and organizations can mint custom project-level roles for "restricted administrators,
  restricted viewers, and restricted end users." A new console view exposes data store
  configurations, connected apps, sync details and user permissions. Source: https://docs.cloud.google.com/gemini/enterprise/docs/iam-policy-for-apps

### ChatGPT Enterprise (OpenAI)

- **Codex CLI 0.158.0 (2026-09-28) adds OAuth client-secret storage and bearer-token
  exec-server sockets.** Codex can now connect to MCP servers that require pre-registered
  OAuth client secrets, supplied through `codex mcp add --oauth-client-secret` — meaning the
  developer workstation now holds long-lived MCP client secrets on disk. Separately,
  "direct exec-server WebSocket connections now support bearer token authentication," with
  support extended to app-server configured connections. The release also turns terminal
  input approval **on by default** for commands with elevated permissions. Source: https://learn.chatgpt.com/docs/extend/mcp

## New Coverage Required

- **[AIDR] [HIGH] Anthropic advisor tool — an undeclared, model-initiated transcript egress to a second model**: A new server-side tool (`advisor_20260301`) lets any Claude request nominate a second "advisor" model that, on the executor's own initiative, receives the **entire conversation transcript including the system prompt, all tool definitions, every prior turn and every tool result**. The calling application never sees what was sent — `server_tool_use.input` is always empty and the server assembles the advisor's view itself. `max_uses` defaults to **unlimited**, so a single request can trigger an unbounded number of these passes. AIDR needs a new activity type for advisor invocations and must treat the `advisor` tool's presence in a `tools` array as a full-context data flow to a second model, distinct from the tool calls it already tracks. Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool

- **[AIRT] [HIGH] Advisor results are encrypted on every current model — an opaque model-to-model channel**: On Sonnet 5.5, Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Fable 5 and Mythos 5, the advisor returns `advisor_redacted_result` with `encrypted_content`, and those models as executors *cannot* be paired with a plaintext advisor — Anthropic states "the advice text isn't readable in the response." Strategic guidance therefore reaches the executor and steers its subsequent tool calls through a channel neither the customer nor any content inspector can read. This is a prompt-injection amplification path worth red-teaming: content injected into the transcript reaches the advisor, whose (invisible) response then redirects the executor. AIRT should build probes that measure executor behaviour change across advisor-on/advisor-off runs, since inspecting the advice directly is not possible. A second variant exists on Claude Managed Agents where advice is delivered as **thread events** rather than result blocks, so detectors keyed on the block type miss it. Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool#result-variants

- **[AISPM] [MEDIUM] Gemini Enterprise resource-level IAM on apps and data stores**: Gemini Enterprise apps and data stores are now first-class IAM resource scopes, managed through `getIamPolicy` / `setIamPolicy` on the app itself, with `roles/discoveryengine.agentspaceUser` bound per-app, alongside new custom project-level roles for restricted administrators, viewers and end users. Two behaviours make this a detection requirement rather than a nicety. First, **project-level IAM takes precedence over app-level policy** — a principal holding Gemini Enterprise User at the project level reaches *every* app regardless of app-level bindings, so genuinely restricting a user requires swapping them to the new **Gemini Enterprise Restricted User** role and then granting per-app. Second, `setIamPolicy` **replaces** the entire policy, so a partial write silently strips bindings. AISPM must fetch per-resource IAM policy on each app and data store, add the restricted-{administrator,viewer,user} personas to its inventory, and flag the toxic combination of a project-level Gemini Enterprise User grant coexisting with app-level restrictions that it silently defeats. Source: https://docs.cloud.google.com/gemini/enterprise/docs/iam-policy-for-apps

- **[ENDPOINT] [MEDIUM] Codex CLI stores MCP OAuth client secrets and exposes bearer-authenticated exec-server WebSockets**: Codex CLI 0.158.0 adds `codex mcp add --oauth-client-id <id> --oauth-client-secret <secret>`, which **persists a pre-registered OAuth client secret into the Codex server configuration** on the developer workstation (the secret is redacted in debug output and kept out of authorization URLs and persisted token records, but the config file itself now holds it). The same release adds bearer-token authentication to direct exec-server WebSocket connections, extended to app-server configured connections. ENDPOINT needs to inventory this new credential material in the Codex config and to recognise the exec-server WebSocket as a locally-listening, token-authenticated command-execution surface. Source: https://learn.chatgpt.com/docs/extend/mcp
