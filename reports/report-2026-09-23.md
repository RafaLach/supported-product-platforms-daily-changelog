### Claude Enterprise (Anthropic)

- **Inline tool definitions — `tool_addition` by value (`inline-tools-2026-09-15` beta, September 22)** — a `tool_addition` block in a mid-conversation `role: "system"` message can now carry a **full tool definition by value** (name, description, `input_schema`) rather than naming a tool that was already declared in the request's `tools` array. The `tools` array never changes, so the prompt cache still hits. Re-sending a definition under the same name **replaces the tool's schema from that point onward**. Combined with the `mcp-client-2026-09-15` beta header, the same block can attach an **`mcp_toolset`** mid-conversation, and the response then carries `mcp_tool_listing` blocks enumerating that server's tools. Limits: 10,000 deferred tools, 10,000 tools defined after the first user message, 4 MB of post-first-user-message tool definitions. Computer-use tools cannot be defined inline. Supported on Claude Fable 5.1, Mythos 5.1, Opus 5, Opus 5.5 — on the Claude API, Amazon Bedrock and Google Cloud. Source: https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages

### Amazon Bedrock AgentCore

The September 2026 release-notes section grew from 4 entries to 5. The new entry is again in the managed **harness**.

- **Harness: Interactive shells (terminals)** — `InvokeAgentRuntimeCommandShell` opens a persistent, interactive **Bash PTY over WebSocket** inside the microVM running a harness session, at `wss://bedrock-agentcore.<region>.amazonaws.com/runtimes/<harness-arn>/ws/shells`. Environment variables, working directory, command history and running processes persist across inputs. A client can detach and **reconnect with the stored `shellId`**, replaying up to 256 KB of buffered output; up to **10 concurrent shells** per harness session (20 retained active+detached entries), 1-hour connection cap, 64 KB frames, 250 frames/sec. Auth is SigV4 (`bedrock-agentcore:InvokeAgentRuntimeCommandShell`), a SigV4 pre-signed URL, or a bearer token accepted by the harness inbound authorizer — including a **browser-friendly base64url bearer token passed through `Sec-WebSocket-Protocol`**. Works in the managed default environment and in a configured custom container. AWS's own guidance: the shell "can access customer-provided data, files, and secrets in the selected environment or on mounted filesystems" and "connect to network destinations that the session can reach." **CloudTrail records the API call and CloudWatch gets connection metadata, but neither logs terminal input or output.** Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-command-shell.html

## New Coverage Required

- **[AIRT] [HIGH] Anthropic inline tool definitions — tools and MCP servers introduced mid-conversation, by value**: A `tool_addition` block in a `role: "system"` message can now carry a complete tool definition, so a tool that Claude will call **need never appear in the request's `tools` array**. Every static analysis Zenity performs that reads an agent's declared toolset from the top of the request is now incomplete by design: the real tool surface is the union of `tools` plus every inline definition appended across the conversation, and a later definition under the same name **silently replaces the earlier schema**. Two consequences compound this. First, the same mechanism can attach an entire **`mcp_toolset` mid-conversation** (with `mcp-client-2026-09-15`), which means an MCP server — and the arbitrary tool list it returns in `mcp_tool_listing` — can enter an agent's reach after the conversation started and after any pre-flight policy check ran. Second, because the system-message block is *appended data*, an agent pipeline that builds messages from retrieved or user-influenced content gives an injection a route to **define its own tool** rather than merely persuade the model to misuse an existing one. AIRT needs probes for inline tool injection and mid-conversation MCP attachment; AISPM must treat an agent's tool inventory as conversation-scoped and evolving, parse `tool_addition` and `mcp_tool_listing` blocks as first-class inventory events, and alert on schema replacement of an already-known tool name. Source: https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages

- **[AIDR] [HIGH] AgentCore harness interactive shells (`InvokeAgentRuntimeCommandShell`)**: A new WebSocket API that gives a caller a persistent, stateful Bash terminal inside the microVM running a harness agent — the same environment as the agent, with the same filesystem, mounted secrets and network reachability. AWS states plainly that **terminal input and output are not logged**: CloudTrail captures only the fact of the `InvokeAgentRuntimeCommandShell` call (caller identity, timestamp, source IP, resolved runtime, response status), and CloudWatch receives connection metadata only. Everything typed and everything returned is invisible to AWS-native logging, which makes this the least-observed execution path AgentCore has shipped. Detach-and-reconnect (`shellId` + runtime session ID) means a process started in one connection keeps running unattended and can be resumed later from a different client, and the browser-oriented **base64url bearer token over `Sec-WebSocket-Protocol`** path means a shell can be opened from a browser without SigV4 at all, authorised only by the harness inbound authorizer. Zenity must inventory which principals hold `bedrock-agentcore:InvokeAgentRuntimeCommandShell` and on which harness ARNs, treat any grant of it as a high-privilege finding (AWS's own security note says to restrict it to trusted principals and specific harness ARNs), surface harnesses whose inbound authorizer would accept a bearer-token shell connection, and ingest the CloudTrail event as an AIDR activity type — with the explicit caveat that content-level detection is not available and the compensating control has to be authorisation, not inspection. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-command-shell.html

- **[ENDPOINT] [MEDIUM] Codex CLI 0.156.0 — always-on voice with bundled runtimes, a local usage dashboard, and managed proxy routing in the Windows sandbox**: Three changes alter what Codex is on a workstation. **Voice conversations are now enabled by default and ship with bundled runtimes**, which turns the local coding agent into a always-available microphone-driven input path with its own embedded speech runtime on disk — a new prompt-entry vector that leaves no text artifact and a new bundled binary to inventory. The **`/usage` analytics dashboard with plan history** is a locally reachable record of the agent's own consumption; useful as telemetry, and also a reconnaissance surface. The Windows sandbox now carries **network policy support, DNS resolution and integration with managed proxy routing**, meaning Codex's egress on Windows is governed by a configurable local policy object that ENDPOINT should read and assess rather than assume. Alongside these, **MCP policy consistency enforcement** and improved MCP credential handling change how locally configured MCP servers are admitted, and **Code Mode tool metadata plus filesystem accessor bindings** expand what the agent can reach on the filesystem. This is an extension of the Codex daemon/worktree endpoint object already reported 2026-09-18, not a new product, hence MEDIUM. Source: https://learn.chatgpt.com/docs/changelog

- **[AISPM] [MEDIUM] Gemini Enterprise D&B Risk Analytics data store (GA)**: A second Dun & Bradstreet connector reaches GA, and unlike a plain search index it is a **connector with actions** — meaning a Gemini Enterprise agent can invoke operations against an external commercial-risk service, not merely read from it. The declared use cases (KYB onboarding, counterparty due diligence, sanctions screening, risk decisioning) put it directly in a regulated decision path: an agent grounded on this store is producing outputs that feed onboarding and credit decisions, and the store itself becomes a route by which internal counterparty identifiers leave the tenant for a third-party data provider. AISPM must add D&B Risk Analytics as an inventory entity alongside D&B Commercial Graph, enumerate the actions registered for it (the action set is the privilege, not the connector), capture its region binding (`global`/`us`/`eu`) as a data-residency attribute, and flag agents that hold it as a grounding source in a compliance-relevant workflow. Source: https://docs.cloud.google.com/gemini/enterprise/docs/connectors/d-and-b-commercial-graph
