## Executive Summary

**Twelve findings. The Microsoft Foundry documentation roll-up unfroze for the first time since July and immediately disclosed four agent surfaces this monitor has never reported; AWS made org-wide agent discovery a managed service; and Anthropic shipped a second safeguards-lifted model.**

**Foundry's What's New page advanced from July to August 2026 (`ms.date` 2026-09-01) after six consecutive scans stuck on July.** Reading its New-articles list as a pointer index — the method recorded after the 2026-08-14 scan — surfaced four genuinely new surfaces, each confirmed against every prior report before inclusion:

- **A private skill catalog** built on **Azure API Center**, where a skill is a registered organizational asset carrying an explicit **Allowed tools** list of APIs and MCP servers. Microsoft calls that list "the governance boundary for a skill." Skills are Git-synced from source repositories and can be gated by an automated **AI Assessment** before promotion.
- **Long-running and steerable hosted agents** (preview) on a new `azure-ai-agentserver` SDK: durable crash-resilient tasks that survive process death and re-enter with `entry_mode: recovered`, and a **steering queue** that lets a second caller redirect an agent's in-flight turn rather than being rejected with `409 conversation_locked`.
- **Bring your own registry**: Foundry hosted agents can now pull container images from **non-Azure registries** — JFrog Artifactory, self-hosted Docker Distribution — through OIDC token exchange against the Foundry project managed identity. The agent supply chain leaves Azure.
- **Microsoft Foundry Toolkit for Visual Studio Code**, the merged successor to AI Toolkit and the separate Foundry extension, with a Tool Catalog that discovers MCP servers and toolboxes and a one-command deploy path to Foundry Agent Service.

**AWS made agent discovery a managed, organization-wide service.** AWS Agent Registry went **GA with AWS Organizations auto-detection**: every AgentCore Runtime and Gateway in every member account is cataloged into a single organization-scoped registry with **no agent, no per-account permission, and no member-account resource to install**. That is a capability Zenity sells; it is now a checkbox in a competitor's console. Separately, **AgentCore Memory's new `IngestData` API writes straight into long-term memory with no short-term event at all** — the ingested content "cannot be retrieved with `GetEvent`, `ListEvents`, or `ListSessions`." The memory write path now requires neither a conversation nor an auditable event record.

**Anthropic released Claude Fable 5.1 and Claude Mythos 5.1 on September 1.** Mythos 5.1 is the successor to the safeguards-lifted Mythos 5 reported on 2026-08-23, still entitled only through Anthropic, AWS or Google Cloud account teams under Project Glasswing — and Bedrock published a **Mythos 5.1 model card the same day**. One documented divergence is new and directly usable: Fable 5.1 enforces a thinking-block prefix-integrity check that rejects replayed history, and **"Claude Mythos 5.1 doesn't run this check."** Anthropic also announced **Enterprise Frontier Safeguards**, which relocates transcript storage into the customer's own S3/Blob/GCS bucket under customer-managed keys and routes misuse detections to the customer instead of to Anthropic.

**Two endpoint-side items.** **Kiro** — the named successor to the Amazon Q Developer IDE plugins — shipped **Configuration Sync**, which pushes cloud-stored Steering files, custom agents, Skills, **Powers** and Hooks down into **local IDE and CLI sessions**. Combined with the `.kiro/agents` and `mcp.json` file-watcher hot reload recorded on 2026-08-23, a local agent's tool grants can now be changed remotely, mid-session, with no restart. And **Codex CLI 0.151.0** added **extension-level inspection and replacement of MCP tool results before they reach the model** — a supported in-process interception point between an MCP server and the LLM.

### Microsoft Foundry — What's New advanced to August 2026 (ms.date 2026-09-01), first movement since July

- **Create a private skill catalog in Foundry Agent Service (public preview).** A skill is "a reusable capability — instructions, bundled scripts, and tool references — that an agent can consume." A private catalog registers organization-scoped skills in **Azure API Center** as assets of type **Skill**, each carrying a title, summary, lifecycle stage, a **Source URL** pointing at the Git repository holding the skill's source, and an **Allowed tools** list naming "the APIs or MCP servers from your API inventory that the skill can access." Microsoft: "The allowed tools list is the governance boundary for a skill." Catalogs can be kept in sync from a Git repo. **Governance → AI Assessment** can score skills against default or custom criteria (name, score range, pass threshold, weight) before promotion. Developer access is gated by the **Azure API Center Data Reader** role; propagation takes up to 24 hours. Discovered in the Foundry portal under **Build > Skills**. `ms.date` 2026-08-19. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/private-skill-catalog
- **Long-running agents (preview)** on the `azure-ai-agentserver` packages (`-core` ≥ 2.0.0 GA for Python, `.NET` in preview). New primitives: `@task` and `@multi_turn_task` decorators declaring **crash-resilient units of work**; a `TaskContext` exposing `entry_mode` of `fresh` / `resumed` / **`recovered`**, `retry_attempt`, `RecoveryCount`, `is_steered_turn` and `pending_input_count`; `TaskStatus` of `Pending` / `InProgress` / **`Suspended`** / `Completed`; a `~10 MiB` task payload limit; and `ResponsesServerOptions` flags **`resilient_background`** (re-invoke stored background responses after a crash) and **`steerable_conversations`**, both defaulting to off. A **streaming registry** offers `use_in_memory_live()`, `use_in_memory_replay()` and **`use_file_backed_replay()`** — the last persists stream events to disk and **survives restart**. Sources: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/long-running-agent-reference and https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/long-running-agent-resilience
- **Steer an in-flight agent turn (preview).** With `steerable_conversations=True`, a second turn arriving on a busy conversation **queues and cooperatively cancels the running handler** instead of returning `409 conversation_locked`. The follow-up is sent as a new response with `previous_response_id` set to the running response and the same `agent_session_id`. Ordering is guarded only by an optional `if_last_input_id` precondition ("the input-queue equivalent of an HTTP `If-Match`"); the queue is bounded and raises `SteeringQueueFull`. `ms.date` 2026-08-05. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/steer-hosted-agent
- **Bring your own registry for hosted agents.** Foundry hosted agents can be deployed from **container registries outside Azure** — JFrog Artifactory is the validated example; self-hosted Docker Distribution requires a custom authentication adapter. Authentication is **OIDC token exchange**: an Entra application supplies the audience, the **Foundry project managed identity** is the exchanged subject, and the registry issues short-lived pull credentials. The configuration lands as a project connection of category **`CustomKeys`** with `metadata.type=registry_connection` and `mode=oauth_token_exchange`, holding `audience`, `tokenEndpoint` and provider-specific `body.*` keys; the agent definition references it as `registryConnectionId` alongside `docker.imagePassthrough: true`. `ms.date` 2026-09-01 — the newest Foundry page in this scan. Also documented here: the **Foundry RBAC roles were renamed** — Azure AI User / Owner / Account Owner / Project Manager are now **Foundry User / Owner / Account Owner / Project Manager**, with role IDs and permissions unchanged. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/private-registry-connections
- **Microsoft Foundry Toolkit for Visual Studio Code.** "Foundry Toolkit is the new name for AI Toolkit. It also includes the capabilities previously provided by the separate Microsoft Foundry extension." Ships a **Tool Catalog** to "discover Foundry tools, Model Context Protocol (MCP) servers, and toolboxes, and then add them to agents"; an **Agent Builder**; an **Agent Inspector** for debugging local agents, streaming responses and tool calls; local model execution through **ONNX, Ollama and Foundry Local**; local GPU fine-tuning; and deployment of hosted agents to Foundry Agent Service **from source code or a container image**. `ms.date` 2026-08-20. Source: https://learn.microsoft.com/en-us/azure/foundry/how-to/develop/get-started-projects-visual-studio-code

## New Coverage Required

- **[AISPM] [HIGH] AWS made organization-wide agent discovery a managed service — every AgentCore Runtime and Gateway in every member account, with no code and no member-account footprint**: **AWS Agent Registry is now GA**, and its headline launch feature is **auto-detection with AWS Organizations**. A single **organization-scoped registry** (one per Region, owned by the management account or, per AWS's own recommendation, a **delegated administrator**) automatically catalogs **`AWS::BedrockAgentCore::Runtime`** and **`AWS::BedrockAgentCore::Gateway`** resources across every member account, both those that already exist and those created afterward, and stays in sync as resources change and as accounts join or leave the organization. AWS is explicit that the collector is invisible: "there's nothing to install or configure in individual member accounts — **no agents, no per-account permissions, and no member-account resources to set up**." Zenity should treat this as both an ingestion opportunity and a competitive fact — **this is agent inventory as an AWS-native checkbox**, and a customer running it will compare its counts against Zenity's. Four specifics make the comparison winnable, and each is a coverage gap AWS leaves open. **First, the registry cannot tell an MCP server from an agent.** Every runtime protocol — `MCP`, `HTTP`, `A2A`, `AGUI` — maps to `recordType: AGENT`, "because auto-detection can't distinguish a standalone MCP server from an agent that exposes an MCP interface." An operator can hand-narrow a record from `AGENT` to `MCP`, but **the next protocol change silently resets it back to `AGENT` and overrides the narrowing**. Zenity's classification of the same resource should be independent and should be presented as the corrective. **Second, the authorizer detail is deliberately truncated.** Provenance carries the JWT **`discoveryUrl`** and the **`workloadIdentityArn`**, but "other authorizer fields (**`AllowedClients`, `AllowedAudience`, `AllowedScopes`**) are not carried into the record" — precisely the fields that answer *who may call this agent*. A registry-derived inventory therefore cannot evaluate authorization scope; Zenity's must read the source resource. **Third, deprecation silently freezes truth.** "If you deprecate an auto-detected record… auto-detection stops syncing changes from the source resource to that record. Subsequent updates — such as protocol, authorizer, or endpoint changes — are not applied." A deprecated record is a stale record that still looks like a record, and it is a plausible evasion: change a runtime's authorizer after its registry entry is deprecated and the catalog never notices. **Fourth, auto-detected records cannot be deleted while auto-detection is on**, and refreshes to an already-approved record are written as a new `Draft` revision that is undiscoverable until approved — so the discoverable view of an agent can lag its actual configuration indefinitely if no curator approves. AISPM should ingest organization-scoped registries via `agent-registry-control`, key on the `aws-autodetected-` name prefix and the `DETECTED_FROM` provenance relation to separate detected from hand-authored records, resolve each `sourceId` ARN back to the owning member account, reconcile the registry's agent list against Zenity's own AgentCore discovery in both directions, and flag deprecated auto-detected records, unapproved draft revisions, and `autoDetectionConfiguration.enabled=true` with `autoDetection.status=INACTIVE` — a state AWS documents as reachable and which means the org believes discovery is running when it is not. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-organizations.html

- **[AIDR] [HIGH] AgentCore Memory's new `IngestData` API writes into long-term memory with no event, no conversation and no retrievable record of what was written**: `IngestData` submits content "directly for long-term memory extraction, **without persisting it as a short-term memory event**." The consequence is stated plainly in the same paragraph: "the submitted content **cannot be retrieved with `GetEvent`, `ListEvents`, or `ListSessions`**, or reorganized with branching." This closes a progression this monitor has been tracking. On **2026-08-23** AgentCore Memory accepted a `json` payload type on `CreateEvent`, and the finding then was that **the memory write path no longer requires a conversation**. `IngestData` removes the remaining constraint: the write path no longer requires an **event** either. What lands in long-term memory — the store that shapes every future session for that `actorId` — now has no durable record of its own arrival on any of the three enumeration APIs an investigator would reach for. AWS frames this as a storage-cost optimization ("avoid the short-term storage overhead of persisting an event you would never read back"), and the framing is honest, but the security property is that **memory poisoning through this path is not merely undetected, it is unenumerable after the fact**. Both payload types are accepted — `conversational` messages with a `USER`/`ASSISTANT` role, and arbitrary `json` "such as behavioral events, activity logs, or system events" — and both **fan out to every configured long-term strategy except self-managed ones**, meaning semantic, user-preference, summarization and episodic extraction all consume it. Content sharing an `actorId`, `sessionId` and namespace "is treated as related context during extraction," so an attacker who can call `IngestData` for a victim's `actorId` can influence how that user's genuine interactions are summarized. AIDR should treat **`IngestData` as a first-class activity type distinct from `CreateEvent`** and alert on it specifically — an IAM principal that calls `IngestData` but never `CreateEvent` is writing memory without writing history. Because the data plane offers no retrospective view, the only durable signals are external: **CloudTrail on the `IngestData` call**, the **Kinesis memory-record stream** AWS documents for real-time notification when memory records are created, and `ListMemoryExtractionJobs` for the failure queue. AISPM should inventory which memory resources have long-term strategies configured (that is what makes them `IngestData` targets), enumerate every principal holding the `IngestData` permission as a distinct privilege class from event creation, and treat the ability to write another actor's namespace as a toxic combination. The companion **flexible namespaces** release in the same batch widens the blast radius by making namespaces variable rather than fixed. Sources: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/long-term-ingest-data.html and https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_IngestData.html

- **[AISPM] [HIGH] Foundry's private skill catalog makes a skill an inventory entity with a declared tool-reach boundary — and that boundary is enforced from an Azure API Center Zenity does not currently read**: Foundry Agent Service now supports a **private skill catalog** (public preview) in which a skill — "instructions, bundled scripts, and tool references" — is registered as an **asset in Azure API Center** with a title, summary, lifecycle stage, a **Source URL** naming the Git repository that holds its code, and, critically, an **Allowed tools** list specifying "the APIs or MCP servers from your API inventory that the skill can access." Microsoft's own language sets the stakes: "**The allowed tools list is the governance boundary for a skill.** It explicitly defines which resources the skill can consume, so a shared skill can't reach endpoints you didn't approve." That sentence is the finding. A skill is now a **first-class, permissioned, organization-shared unit of agent capability** whose authorization is declared in a *different Azure service* from the agent that consumes it — so an agent's effective reach is the union of its own tool connections and the allowed-tools lists of every catalog skill it loads, and neither view alone is complete. - **[AIRT] [HIGH] Foundry hosted agents can now be redirected mid-execution by a second caller, and their durable task state survives the process that created it**: The **long-running agents** preview introduces two properties that break assumptions AIRT and AIDR currently rely on. **First, steering.** With `steerable_conversations=True` on `ResponsesServerOptions`, or `steerable=True` on a `@multi_turn_task`, a second input arriving on a conversation that is **already executing a turn** no longer gets `409 conversation_locked` and no longer races — it **queues behind the active turn and the framework signals the running handler to cooperatively wind down**, after which the queued input takes over and reports `ctx.is_steered_turn == True`.
