## Platform Details

### Amazon Bedrock AgentCore (tier: primary) — carried audit debt cleared

Release notes themselves did **not** move (September 2026 still 5 items, all previously reported). The following come from the harness sub-pages flagged unaudited in the 2026-09-22 → 2026-09-24 reports.

- **Harness persistent filesystem mounts.** A harness can mount three distinct persistent filesystem types at paths under `/mnt`: service-managed **session storage** (survives stop/resume for a `runtimeSessionId`, no VPC needed), an **Amazon EFS access point** (customer-owned, explicitly "shared across sessions and agents", up to 2 mounts, VPC required), and an **Amazon S3 Files access point** (up to 2 mounts, VPC required) whose mount path **syncs bidirectionally with the backing S3 bucket**. Files written to these mounts survive session termination and are visible to later invocations. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-environment.html

- **`InvokeAgentRuntimeCommand` — direct root shell into the harness microVM.** AWS documents this as deliberate out-of-band access: "deterministic command execution with no model reasoning, no token cost." Commands run as **root (uid 0)**, and AWS states plainly that a `USER` directive in the customer's Dockerfile "applies to the agent process only" — `InvokeAgentRuntimeCommand` "runs at a higher privilege level," and "the IAM permission is the access gate, not the in-VM privilege level." Documented uses include cloning repos, installing packages, and pushing commits. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-environment.html

- **Harness memory: caller-supplied `actorId` is the isolation boundary, and managed memory is provisioned by default.** Memory events are scoped by `actorId` + `sessionId`, and `actorId` is passed by the caller on each `InvokeHarness` call. Long-term retrieval templates `actorId` directly into namespace paths (e.g. `/summary/{actorId}/{sessionId}/`). Retrieval is automatic on every invocation (`topK=10`, `relevanceScore=0.2` by default) and injects retrieved memories into context before the model reasons. Separately: creating a harness through the **service API** with the memory configuration omitted causes the service to **provision managed memory automatically** (the CLI defaults the other way, to disabled), and `DeleteHarness` cascade-deletes it unless `deleteManagedMemory=false`. BYO memory can be attached to and shared across multiple harnesses. Four long-term strategies: `SEMANTIC`, `SUMMARIZATION`, `USER_PREFERENCE`, `EPISODIC`. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-memory.html

- **Harness skill sources — four source types, fully enumerated.** The `skills` field (settable at create time, overridable per invocation, invoke-time entries appended after and winning on name collision) accepts: `awsSkills` (pre-built AWS-service skills from the AWS Agent Toolkit, glob-selected), `git` (clone **any public or private HTTPS Git repository**, sparse-checkout a subdirectory, private repos authenticated via a Token Vault `apikeycredentialprovider` ARN), `s3` (customer bucket, fetched with the execution role, ≤1 GB), and `path` (filesystem, baked into the container image *or installed at session start via `InvokeAgentRuntimeCommand`*). Skills follow the open **AgentSkills.io** standard — a `SKILL.md` plus optional `scripts/`, `references/` and `assets/` directories. Skills are fetched once per session and persist on disk across invocations. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-skills.html

## New Coverage Required

- **[AISPM] [HIGH] AgentCore harness persistent filesystem mounts — three new resource types, one explicitly cross-agent**: A harness can mount service-managed session storage, up to two **EFS access points**, and up to two **S3 Files access points** at paths under `/mnt`. AWS states the EFS mount is "shared across sessions and agents" — meaning two different agents, potentially with different execution roles and different data-classification levels, can be wired to the same access point and exchange files outside any modelled data flow. The S3 Files mount **syncs bidirectionally**, so anything an agent writes to its local mount path lands in the customer's S3 bucket automatically, and anything placed in that bucket becomes agent-readable input. Zenity's AgentCore inventory must add `filesystemConfigurations` as a first-class relationship — mapping each harness to its `sessionStorage`, `efsAccessPoint` and `s3FilesAccessPoint` mounts — and AISPM should raise a toxic-combination finding when one EFS or S3 Files access point is mounted by more than one agent or harness, and when an S3 Files-backed bucket is also writable by a non-agent principal (an injection path into agent context). Note `UpdateHarness` replaces the entire `filesystemConfigurations` list, so mount changes are not incremental and a drift-detection baseline must re-read the whole list. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-environment.html

- **[AIDR] [HIGH] `InvokeAgentRuntimeCommand` executes arbitrary shell as root inside the agent's microVM, bypassing the agent loop entirely**: AWS documents this API as a deliberate out-of-band path with "no model reasoning, no token cost" — meaning it produces **no agent turn, no tool-use event and no model trace**. Commands run as **uid 0** regardless of a `USER` directive in the customer's container image, and AWS is explicit that "the IAM permission is the access gate, not the in-VM privilege level." The documented use cases are themselves high-impact: clone a repository, install dependencies, run tests, **commit and push**, extract build artifacts, and install skills into `.agents/skills/` at session start. Any AIDR model that infers agent activity from invocation traces or model telemetry will see nothing at all for this path. Zenity must treat `bedrock-agentcore:InvokeAgentRuntimeCommand` as a distinct high-severity activity type sourced from CloudTrail rather than from agent traces, and AISPM must flag any principal holding it — it is effectively root on the agent host, and it is a separate IAM action from `InvokeHarness`. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-environment.html

- **[AIRT] [HIGH] Harness memory isolation depends on a caller-supplied `actorId` string**: Short-term and long-term memory are scoped by `actorId` + `sessionId`, and `actorId` is an ordinary request field the caller sets on `InvokeHarness`. Long-term retrieval templates it straight into the namespace path (`/summary/{actorId}/{sessionId}/`) and runs **automatically on every invocation**, injecting the top 10 semantically-matched records into context before the model reasons. If the calling application forwards a client-controlled identifier — or if the caller is a SigV4 principal, which per the harness security page gets **no per-user identity propagation at all** — then submitting another user's `actorId` retrieves that user's extracted facts, summaries, preferences and episodes into the attacker's session. This is a cross-tenant memory read reachable with no IAM change, and the injected content is also an indirect prompt-injection carrier (it is written by prior conversations). AIRT should add a probe that varies `actorId` across otherwise identical sessions and checks for retrieval leakage; AISPM should flag harnesses that are both memory-enabled and SigV4-invoked. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-memory.html

- **[AISPM] [MEDIUM] AgentCore harness managed memory is silently auto-provisioned by the service API**: Creating a harness through the service API with the memory configuration **omitted** causes AgentCore to provision a managed AgentCore Memory resource automatically — the AgentCore CLI defaults the opposite way (disabled). The result is a persistent store of conversation events and extracted long-term records (`SEMANTIC`, `SUMMARIZATION`, `USER_PREFERENCE`, `EPISODIC` strategies) that exists without the operator ever asking for it, and which cannot be deleted through the Memory APIs directly. Zenity's inventory must not assume "no memory configured" means "no memory" — it must resolve each harness's effective memory resource and mark implicitly-provisioned managed memory as an undeclared data store. Conversely, `DeleteHarness` cascade-deletes that memory by default unless `deleteManagedMemory=false` is passed, which matters for evidence retention. BYO memory attached to several harnesses is an additional cross-agent data-sharing edge to model. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-memory.html

- **[AISPM] [MEDIUM] AgentCore harness skill sources — four source types including arbitrary Git clone at invoke time**: This supplies the concrete entity model behind the per-invocation skill-override risk reported on 2026-09-24. The `skills` field accepts `awsSkills` (glob-selected AWS Agent Toolkit skills granting EC2/S3/Lambda/DynamoDB/CloudWatch/**IAM** operational knowledge), `git` (any public or private HTTPS repository, private repos authenticated with a Token Vault API-key credential provider holding a PAT), `s3` (execution-role-fetched, ≤1 GB), and `path` (baked into the image, or installed mid-session via `InvokeAgentRuntimeCommand`). Skills carry a `scripts/` directory alongside `SKILL.md` and conform to the open **AgentSkills.io** specification — the same cross-vendor plugin format Zenity already tracks — so a skill bundle is executable content, not just prose. Zenity should inventory skill attachments as a per-harness entity with the source type, URI/repo, and credential ARN recorded; flag invoke-time overrides as distinct from create-time defaults (invoke-time wins on name collision); and flag `awsSkills` globs that pull in IAM-operation skills. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-skills.html

- **[ENDPOINT] [MEDIUM] Codex CLI 0.157.0 starts a background server by default and opens `/import` to remote and background-server sessions**: As of 0.157.0 the Codex CLI "enable[s] automatic background-server startup for eligible interactive sessions" — a long-lived local listener now comes up without the user opting in — and `/import` (pulling external content into a session) is newly available **in remote sessions and in local background-server sessions**. A new `f` shortcut forks a conversation that is open in another application, carrying over drafts and queued prompts, which moves conversation state across process boundaries. For endpoint coverage this means Codex's local footprint is no longer bounded by a foreground TUI process: ENDPOINT must detect the background server, and treat `/import` in a background-server session as an untrusted-content ingestion point into a tool-capable local agent. Source: https://learn.chatgpt.com/docs/changelog
