## Platform Details

### Amazon Bedrock AgentCore

- **`harness-security` audited in full for the first time — the caller-controlled model
  configuration passthrough.** The `model` field on `InvokeHarness` accepts
  `additionalParams` for Bedrock, OpenAI and LiteLLM configurations, and AWS states
  plainly that "these parameters are passed through to the underlying model provider
  unchanged. The harness does not validate, filter, or restrict these parameters." The
  page then enumerates what a caller who controls that field can do: redirect requests to
  arbitrary endpoints via LiteLLM's `aws_bedrock_runtime_endpoint` — "a caller can route
  the signed request, **including the SigV4 signature and session credentials**, to an
  endpoint that is specified in the trust model configuration"; override outbound HTTP
  headers via OpenAI's `extra_headers`, "**including the `Authorization` header**";
  attempt IAM role assumption via LiteLLM's `aws_role_name`; and redirect inference to a
  different model, region or provider entirely through `modelId` and `apiBase`. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html

- **Skills can be overridden per invocation and are never inspected.** Skills are bundles
  of markdown and scripts fetched from S3 or Git *at invocation time* and injected into
  the agent's context. "The harness treats all skill content as trusted input. It does not
  validate, sanitize, or inspect the content or source of skills before providing them to
  the agent." Critically: "**Skills can be overridden per `InvokeHarness` call**" — a
  caller whose input reaches `InvokeHarness` can point the harness at their own S3 prefix
  or Git repository containing arbitrary instructions and scripts. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html

- **Harness IAM permissions model published, with one asymmetry.** Harness APIs require
  permissions on both the harness resource and the underlying Runtime (and Memory)
  resource: `InvokeHarness` needs `InvokeHarness` + `InvokeAgentRuntime`, `CreateHarness`
  needs `CreateHarness` + `CreateAgentRuntime` + `CreateMemory`, and so on for
  Update/Delete. **`InvokeAgentRuntimeCommandShell` is the sole exception — it requires
  only `bedrock-agentcore:InvokeAgentRuntimeCommandShell`**, with no `InvokeAgentRuntime`
  companion. New ARN shapes: `arn:aws:bedrock-agentcore:<region>:<acct>:harness/<id>` and
  `.../harness/<id>/harness-endpoint/<endpointName>`. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html#harness-iam-permissions

- **SigV4 callers get no per-user identity propagation.** "When callers authenticate with
  SigV4 (AWS IAM), the harness does not propagate per-user identity into downstream tool
  calls." User-scoped OAuth token storage and on-behalf-of token exchange in the AgentCore
  Identity Token Vault are available **only** on the Bearer-JWT inbound path. AWS notes
  SigV4 support "is planned for a future release." Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html

- **One server-side control that does exist, and its boundary.** The harness rejects a
  `toolUse` block in the final message of an `InvokeHarness` request, so a caller cannot
  name a tool and have it dispatched directly. The same page states that for
  **non-harness AgentCore Runtime deployments, "AgentCore Runtime provides no server-side
  protection"** — the customer entrypoint must strip `toolUse` blocks itself. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html#harness-trust-boundary

- **`harness-operations` audited — harness has no CloudTrail resource type of its own.**
  "In CloudTrail, harness resources appear under the `AWS::BedrockAgentCore::Runtime`
  resource type rather than a harness-specific type." All harness events use
  `resources.type = AWS::BedrockAgentCore::Runtime`, and the data-plane events are named
  `InvokeAgentRuntime`, `InvokeAgentRuntimeCommand` and `InvokeAgentRuntimeCommandShell` —
  **there is no `InvokeHarness` event name in CloudTrail**. Control-plane events carry the
  harness ARN in `resources.ARN`; data-plane events carry the *runtime* ARN. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-operations.html#harness-cloudtrail

- **Observability requires a one-time account-level opt-in.** Traces, logs and metrics are
  emitted on every invocation with no extra configuration — but "before you see traces,
  enable Transaction Search in CloudWatch (one-time per account)," and telemetry flows
  through the harness execution role. Execution limits are also now documented:
  `maxIterations` (default 75), `timeoutSeconds` (3600), `maxTokens` (none),
  `idleRuntimeSessionTimeout` (900), `maxLifetime` (28800) — all optional, and all three
  of `maxIterations`/`timeoutSeconds`/`maxTokens` can be **overridden per invocation**.
  Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-operations.html

## New Coverage Required

- **[AIRT] [HIGH] AgentCore harness: unvalidated caller-controlled model configuration allows SigV4 credential redirection and `Authorization` header override**: `InvokeHarness` accepts a `model` object whose `additionalParams` are, in AWS's words, "passed through to the underlying model provider unchanged. The harness does not validate, filter, or restrict these parameters." Any principal that can influence that field can set LiteLLM's `aws_bedrock_runtime_endpoint` to route the **signed request, including the SigV4 signature and session credentials**, to an attacker-chosen endpoint; set OpenAI's `extra_headers` to inject or override the outbound `Authorization` header; set `aws_role_name` to attempt assumption of a different IAM role (bounded only by whether the execution role holds `sts:AssumeRole`); or set `modelId`/`apiBase` to silently redirect inference to a different model, region or provider. AWS offers no server-side control — every suggested mitigation is customer-side input validation. This is a first-class prompt-injection and credential-exfiltration target: an agent that forwards any part of caller-supplied JSON into `InvokeHarness` hands over its model routing and its credentials. AIRT must add harness `additionalParams`/`apiBase`/`modelId` manipulation to its automated test surface; AISPM must flag harnesses reachable by untrusted callers that do not strip the `model` field, and execution roles carrying `sts:AssumeRole`. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html#harness-model-params-security

- **[AIRT] [HIGH] AgentCore harness: per-invocation `skills` override is an arbitrary instruction-injection channel**: Skills are markdown-plus-script bundles the harness fetches from S3 or Git **at invocation time** and injects directly into the agent's context. AWS states the harness "treats all skill content as trusted input. It does not validate, sanitize, or inspect the content or source of skills before providing them to the agent" — and that "skills can be overridden per `InvokeHarness` call." The combination means a caller who reaches `InvokeHarness` can point the agent at their own S3 prefix or Git repo and supply the agent's instructions and executable scripts wholesale, bypassing whatever skill set the harness was configured with at the control plane. The configured-skills view in any inventory is therefore **not** an accurate picture of what actually ran. AIRT should treat skill-source substitution as a distinct attack primitive from prompt injection; AISPM must inventory each harness's configured skill sources, alert when a skill source is an S3 bucket or Git repo outside the account's trust boundary, and treat "skills not stripped from caller input" as a toxic combination with any externally reachable harness endpoint. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html#harness-skills-security

- **[AIDR] [HIGH] AgentCore harness is invisible as a distinct resource type in CloudTrail**: AWS documents that "in CloudTrail, harness resources appear under the `AWS::BedrockAgentCore::Runtime` resource type rather than a harness-specific type," and that data-plane calls are logged as `InvokeAgentRuntime`, `InvokeAgentRuntimeCommand` and `InvokeAgentRuntimeCommandShell` — **`InvokeHarness` never appears as a CloudTrail event name**. A harness invocation is therefore indistinguishable by event name from a plain AgentCore Runtime invocation, and control-plane events carry the harness ARN in `resources.ARN` while data-plane events carry the *runtime* ARN, so the two halves of a harness's audit trail do not join on a common identifier without an externally maintained harness→runtime mapping. Compounding this, harness traces only exist if **Transaction Search is enabled in CloudWatch (a one-time, per-account opt-in)** and the execution role carries the logs/X-Ray statements — so an account can run harnesses with no trace data at all and no error. AIDR must build the harness→runtime ARN mapping from control-plane events and use it to attribute data-plane activity, must not rely on a `harness` resource type existing, and should alert when a harness exists in an account where Transaction Search is off. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-operations.html#harness-cloudtrail

- **[AISPM] [MEDIUM] AgentCore harness IAM: `InvokeAgentRuntimeCommandShell` is the one invoke API that does not require `InvokeAgentRuntime`**: The newly published harness permissions table shows every harness API requiring permissions on both the harness resource and the underlying Runtime resource — `InvokeHarness` needs `InvokeHarness` **and** `InvokeAgentRuntime`, `InvokeAgentRuntimeCommand` needs its own action **and** `InvokeAgentRuntime`, and Create/Update/Delete each additionally require the matching `*AgentRuntime` **and** `*Memory` actions. `InvokeAgentRuntimeCommandShell` requires only `bedrock-agentcore:InvokeAgentRuntimeCommandShell`. A least-privilege policy written around `InvokeAgentRuntime` — the obvious chokepoint, and the one most existing AWS guidance names — therefore does **not** gate interactive shell access to the microVM, the highest-capability path into a harness session (persistent shells, 256 KB replayable buffered output, up to 10 concurrent shells, reported 2026-09-23). AISPM must add the two new ARN shapes (`.../harness/<id>` and `.../harness/<id>/harness-endpoint/<name>`) as inventory resource types, evaluate harness policies against the full 14-row action table rather than against Runtime actions alone, and raise a finding on any principal holding `InvokeAgentRuntimeCommandShell` without a corresponding `InvokeHarness` grant — that combination is shell access without the ability to use the agent normally. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html#harness-iam-permissions

- **[AISPM] [HIGH] ServiceNow Brazil (EA 2026-09-24) adds Autonomous Engineer — an unattended agent that builds and deploys ServiceNow applications**: A new ServiceNow release family is current, and its headline new entity is **Autonomous Engineer**: an agent that "runs on Build Agent and uses the same skills" but is explicitly designed for work handed off with "nobody... to sit and watch it happen." It is gated behind a **new AI Workflow Factory SKU** on top of Brazil EA, so its presence is separately entitled and separately detectable. The capability it inherits from Build Agent is the concerning part: full-stack application authoring across tables, flows, UI and scripts, **generating and executing** ATF test scenarios, and **deploying via update sets** — all "restricted to admin-level permissions only." An unattended, admin-privileged, natural-language-driven agent that emits promotable update sets is a code-to-production path with no human in the loop, and it composes with the global-scope authoring capability reported on 2026-09-18. Brazil also adds **Skills** and **Rules** as new Build Agent organizing constructs, six **playbook** changes including generate-and-deploy-as-a-unit, five new **Fluent/Now SDK** APIs (`RestMessage`, `Alias`, `AliasTemplate`, `RetryPolicy`, `DataLookup`) with domain-separation support and CI/CD CLI — `RestMessage` as a Fluent-declarable API means an agent-authored definition can create outbound HTTP integrations as code — and a redesigned **AI Agent Studio** that versions a combined agent/tool/workflow definition and emits update sets for promotion. AISPM needs Autonomous Engineer runs as an inventory and activity entity distinct from Build Agent sessions, the Skills/Rules constructs as the policy objects that constrain them, the AI Workflow Factory entitlement as a discovery signal, and update-set promotion as a provenance surface answering "which agent authored the code now running in production." Source: https://www.servicenow.com/docs/r/application-development/build-agent.html

- **[ENDPOINT] [MEDIUM] Dia Browser writes to Notion and aggregates across four governed systems into one document**: Dia 1.47.1 adds Notion as the first connected tool that is a **write destination** rather than a read source, and pairs it with cross-tool fan-out: a single natural-language request reads Slack DMs, email threads and Google Docs and concentrates the result into a Notion page. The vendor's own worked example is an employee performance dossier — "find me conversations where Susan's communication and leadership skills excelled this Summer, collecting it all in a Notion doc." This extends the Dia connector finding reported 2026-09-27 in a materially different direction: data does not just enter the browser, it leaves it into a fifth system, assembled client-side from four separately governed sources, with no DLP, retention or eDiscovery control in the path and no authorization model, admin control or audit surface documented on the release note. ENDPOINT must enumerate Dia tool connections including their direction (read vs. write) and treat a write-capable connector as an egress channel; AISPM should register the resulting Notion grant as a third-party app consent on the Notion workspace. Source: https://www.diabrowser.com/release-notes/Notion
