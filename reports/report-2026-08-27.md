## Executive Summary

**Five findings across two platforms. Both platforms moved on August 26, and the through-line is that Claude stopped being a model an enterprise calls and became an agent host that other vendors' data flows into — from inside Excel, and from inside Salesforce's CRM.**

**Anthropic's platform release notes advanced to August 26 and added two `product_surface` values to the Compliance API: `claude_science` and `office_agents/*`.** That is a small entry with a large implication. `office_agents` resolves to **Claude for Microsoft 365** — four Office add-ins (Excel, PowerPoint, Word, Outlook) that have been generally available since **May 7, 2026** and that **this monitor has never reported**. They are not a chat sidebar. Claude for Excel edits pivot tables, applies conditional formatting, rewrites cell values while preserving formula graphs and creates data-validation dropdowns; Claude for Word edits with tracked changes and replies in comment threads; Claude for Outlook triages the inbox and coordinates calendar availability across team members **through the Microsoft Graph mailbox and calendar API**, authenticated with Entra ID Nested App Auth. They share one conversation thread across all four apps over a WebSocket bridge, they carry connectors (**S&P Global, LSEG, Daloopa, plus any custom remote-MCP connector the org enables**), they run Skills, and they hold per-app persistent Instructions. Anthropic's own Excel documentation carries an unambiguous prompt-injection warning: *"Testing has identified scenarios where Claude for Excel can be manipulated to extract sensitive information, modify critical data, or perform destructive actions if allowed to act without verification."*

**The logging story is the coverage problem.** Chat history lives **locally in the browser's IndexedDB**, is not synced, is not on Anthropic's servers, and survives reinstalling the add-in. The add-ins **do not inherit the organization's custom data-retention settings**. And the product documentation still states — today, after the release note — that *"Activity is not included in Enterprise audit logs or the Compliance API."* The August 26 release note contradicts that. Either way the direction is clear: until yesterday this was an unlogged agent surface, and it is now logged only in beta, only for Claude Enterprise organizations, and only where the org is not on HIPAA readiness or zero data retention.

**Deployment is a cross-cloud identity edge provisioned by a Claude Code plugin.** Organizations that route AI through their own infrastructure install `claude-for-msft-365-install` from the `anthropics/financial-services` marketplace and run `/claude-for-msft-365-install:setup`. For the Bedrock path the wizard creates an **IAM OIDC identity provider trusting Microsoft Entra ID tokens** and a role carrying `bedrock:InvokeModel`. Two other commands matter more than the setup: `:update-user-attrs` writes **per-user configuration into Microsoft Graph extension attributes**, and `:bootstrap` builds **an endpoint that serves per-user MCP servers, Skills and dynamic config** — an org-controlled channel that pushes tool surfaces to individual users at runtime, with no artifact on the endpoint.

**On the same day, Salesforce and Anthropic announced Claudeforce, and it inverts the direction of every Salesforce finding this monitor has filed.** Historically Salesforce hosted the agent. **"Salesforce in Claude" is a plugin with 37 prebuilt sales skills that runs inside Claude**, lets sellers "reason over live revenue context, automate pipeline updates, and take governed action right from Claude," and reaches open beta in **September 2026**. In the other direction, Claude becomes the model **powering the Atlas Reasoning Engine and serving as the default for Agentforce Vibes and Agentforce Coworker**, and the intelligent backbone of Slack including Slackbot and Slack Code. Delivered through **Amazon Bedrock inside the Salesforce Trust Boundary** — Claude's traffic contained in Salesforce's VPC, which means neither vendor's control plane observes the whole path. Note that **Agentforce Coworker has never appeared in any report from this monitor** (zero hits across `reports/`), and it provisions automatically for eligible licences.

**Anthropic also put the Admin API in the `ant` CLI and seven SDKs under `client.beta.organization`**, covering workspaces, service accounts, API keys, rate limits, **workload identity federation issuers and rules**, and **customer-managed encryption keys** — and automated workloads authenticate through WIF with no interactive login at all.

Claude for PowerPoint builds slides inside the corporate template and generates native charts. - **[AIRT] [HIGH] Anthropic documents a working prompt-injection path into Claude for Excel — untrusted spreadsheets can drive data extraction and destructive edits, and the only control is a user confirmation click**: The Claude for Excel documentation carries a warning Anthropic wrote about its own product, and it is unusually direct. *"Only use Claude for Excel with trusted spreadsheets. Files from external sources can contain hidden instructions that manipulate the add-in into extracting data, modifying records, or performing destructive actions."* And then, on their testing rather than on theory: *"Testing has identified scenarios where Claude for Excel can be manipulated to extract sensitive information, modify critical data, or perform destructive actions if allowed to act without verification."* Anthropic names the delivery vehicles explicitly — **downloaded templates, vendor files and data imports**. **This is the highest-yield injection surface in the Office suite for three structural reasons.** **First, the carrier is a file format organisations receive constantly from outside and open without thought**, and a spreadsheet has abundant places to hide instruction text that a human reader will never see: distant cells, hidden rows and columns, defined names, comments, hidden sheets, and text in cells whose font colour matches the fill. A vendor pricing template or a downloaded model is a routine artifact, not a suspicious one. **Second, the agent reading the injected content also holds write authority over the same workbook and, in cross-app mode, over the open Word document, PowerPoint deck and Outlook thread as well** — so a payload landing in Excel can act in Outlook, which is where the exfiltration channel is. Cross-app mode being **default-on for Pro and Max** means the wide-blast-radius configuration is the one that ships enabled to the least-managed plans. **Third, the tool surface reachable from that context is not fixed**: whatever connectors the user has enabled in their Claude settings — S&P Global, LSEG, Daloopa, or an arbitrary **custom remote-MCP connector** — are available to the same reasoning loop, and MCP connectors reach outward by definition. **The documented mitigation is a per-operation user confirmation prompt**: "When Claude proposes a risky operation, you are asked to confirm before it runs." That is a click-through control, and the surrounding guidance ("review confirmations carefully, especially for files from external sources") concedes as much. There is no documented tenant-level policy, no content scanning of the workbook, and no notion of file provenance in the product. AIRT should build a purpose-made corpus against this surface and treat it as a distinct target from web and email injection: instructions hidden in non-visible cell regions, hidden sheets and defined names; payloads that exploit the agent's cited-answer behaviour by seeding the citation trail; payloads that trigger the **native operations** (a data-validation dropdown or conditional-formatting rule is an odd but real persistence and signalling mechanism inside a document that will be forwarded onward); **cross-app pivots** that read from a poisoned workbook and write to an Outlook draft or a Word document; attempts to reach an enabled connector from injected context; and payloads specifically shaped to make the confirmation prompt read as benign, since the prompt text is generated from the proposed operation. Test the Outlook direction too — an inbound email is an untrusted document reaching an agent that already holds a Graph token. Source: https://claude.com/docs/office-agents/excel

- **[AISPM] [MEDIUM] Deploying Claude for M365 through Bedrock creates a standing Entra→AWS federation edge, and a Claude Code plugin ships per-user MCP servers through a bootstrap endpoint and Graph extension attributes**: Organizations that route AI through their own infrastructure deploy the Claude Office add-ins without individual Claude accounts, over one of **four connection paths** the IT admin picks: an **LLM gateway** (LiteLLM, Portkey, Kong — Anthropic notes it "matches the pattern used by Claude Code"), **Bedrock direct**, **Vertex AI direct**, or **Foundry direct**. End users see an identical interface either way, which means the connection path is invisible from the client and must be read from configuration. **Each path plants a durable identity artifact.** **Bedrock direct requires an IAM OIDC identity provider trusting Microsoft Entra ID tokens**, plus a role holding **`bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream`** with a trust policy scoped to the Claude add-in's application ID — a permanent, cross-cloud federation edge from the Microsoft tenant into the AWS account, created so that a spreadsheet sidebar can call a model. **Foundry direct's keyless mode** needs a customer Entra app registration with the Azure Cognitive Services **`user_impersonation`** delegated permission, admin-consented, and users holding the **Cognitive Services User** role on the resource — user-impersonation delegation granted to an add-in. **Vertex AI direct** needs a Google OAuth client with the add-in's redirect URI. **The provisioning tool is itself the finding's second half.** All of this is set up by **`claude-for-msft-365-install`**, a **Claude Code plugin** installed from the `anthropics/financial-services` marketplace and run as `/claude-for-msft-365-install:setup`. Two of its commands create ongoing configuration channels rather than one-time setup. **`:update-user-attrs` writes per-user configuration into Microsoft Graph extension attributes** — Anthropic's stated use case is "different gateway tokens or AWS roles for different teams," which means **the AWS role a given user's add-in assumes is stored as a directory attribute** and changing that attribute changes what the add-in can reach. **`:bootstrap` builds "a bootstrap endpoint for per-user MCP servers, skills, and dynamic config"** — an org-controlled URL that serves **tool surfaces and skills to individual users at runtime**, with no local manifest, no marketplace entry and no artifact on the endpoint to inventory. A third command, **`:export-data`**, makes a read-only copy of a user's chat history, skills, **connector registrations** and settings, which is worth knowing because it is the documented way to enumerate what a given user's add-in actually holds. AISPM should discover these artifacts on the identity side, where they are durable and readable: an **IAM OIDC provider whose trust is an Entra tenant** and whose role grants Bedrock invoke, an **Entra app registration with admin-consented `user_impersonation` on Cognitive Services**, a Google OAuth client bound to an add-in redirect URI, and **Graph extension attributes carrying AI routing configuration** — the last of which will not look like AI configuration to a directory scanner unless it is specifically modelled. The bootstrap endpoint should be treated as an **MCP distribution channel** and inventoried as one: it determines each user's tool surface, it is per-user, and it leaves nothing behind on the device. Note also that in third-party mode the model list comes from the platform and the admin's configuration rather than from Claude.ai model-access settings, so **model governance moves to a different control plane than the one an Anthropic-side reviewer would check**. Source: https://claude.com/docs/office-agents/third-party-platforms

- **[AIDR] [MEDIUM] Anthropic's Compliance API now returns Claude Science and Claude for M365 transcripts and its Admin API moved into the CLI and seven SDKs — a new ingestion surface whose documented exclusions are the coverage map**: Two changes on **2026-08-26**. **First, the Compliance API session endpoints went GA for Cowork and Claude Code and gained two new `product_surface` families in beta**: `claude_science`, and `office_agents/excel` / `office_agents/powerpoint` / `office_agents/word` / `office_agents/outlook` (bare `office_agents` when the app is unidentified). No new key, scope, setting or client update is required — the existing **Compliance Access Key** with **`read:compliance_user_data`** covers it. The local endpoints are `GET /v1/compliance/apps/sessions/local`, `.../{session_id}` and `.../{session_id}/messages`, with IDs prefixed `clls_`. AIDR should ingest these as a first-class activity source and **branch on `product_surface`**, because an Office-agent session and a Claude Code session are different activity types with different risk shapes. Anthropic's own guidance is to build forward-compatible handlers that pass through unrecognised `product_surface` values, which is also the right ingestion posture — new surfaces will keep appearing here first, exactly as these two did. **Second, and equally useful: the Admin API is now available in the `ant` CLI (`ant beta:organization`) and in the Python, TypeScript, C#, Go, Java, PHP and Ruby SDKs under `client.beta.organization`**, covering organization info, members, invites, workspaces and workspace members, API keys, rate limits, service accounts, **workload identity federation issuers and rules**, and **customer-managed encryption keys**. That is a programmatic control-plane surface Zenity can read for posture — and one an attacker can read too, noting that **automated workloads skip interactive login entirely and authenticate through WIF**, with the SDKs performing the token exchange from federation environment variables. **The documented exclusions are where the real value is, because they define what this ingestion will never tell you.** The session endpoints **do not return**: Claude Code authenticated with a Console API key **or run through Bedrock, Vertex AI or Foundry** — which is precisely the deployment Claudeforce and the Office add-ins' third-party mode create; **Claude Code on the web**, which runs in Anthropic's cloud but is not a remote session; **all local sessions in organizations with HIPAA readiness enabled**, where nothing is captured at all; and any session under **zero data retention**. Within a captured transcript, **thinking blocks are never included**, the **system prompt is replaced by a marker**, and **tool definitions and MCP server configuration are not part of the transcript at all** — so Zenity can see that a tool was called but not what the agent was told the tool does. Non-text tool results (web search results, code-execution output) collapse to `[N non-text item(s) not shown]`, though **the matching `tool_use` with the query or code in its `input` is still returned**, which is the single most useful retained field. Tool inputs and result text truncate at **10,000 bytes** by default (`tool_use_input_max_bytes` / `tool_result_max_bytes`, `-1` for ~1 MiB), and **a truncated `tool_use` input is no longer valid JSON** — so parse tool inputs only from untruncated blocks or raise the cap and refetch. Two ingestion traps: `created_at` **advances** as old calls age past retention, so deduplicate on `id` rather than assuming stable ordering; and the `updated_at.gte` poll bound must be set **a few minutes before** the previous run's start, because a bound set to the exact previous time "silently and permanently drops a session whose final call was still indexing at that moment." Finally, `provenance.reason = not_captured` **does not mean nothing was recorded** — Anthropic states that content withheld from the Compliance API by its data-handling policies reports the same reason. Two smaller notes worth carrying: remote sessions can be **agent-owned** (`agent_id` prefix `cagt_`, with `started_by_user` naming the initiating human), and the `user_ids[]` filter **excludes agent-owned sessions entirely** — so filtering by user hides exactly the automated runs. And **Claude Science emits separate background sessions for its own reviewer and delegation tracks**, which is a documented confirmation that Claude Science runs sub-agents. Source: https://platform.claude.com/docs/en/manage-claude/compliance-sessions
