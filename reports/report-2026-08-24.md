The only new dated item anywhere was **Codex CLI 0.149.1 (Aug 24)** — "bug fixes and improvements" — which is below the bar.

The value of this scan is entirely in **the first-ever read of Kiro**, the source recommended on the last two scans and read here for the first time, and it produced the largest structural finding in weeks.

**The headline: there is now one open, vendor-neutral package format for agent extensions, and this monitor has been reporting it as several separate vendor features.** **Agent Plugins 1.0.0** shipped **August 6, 2026** — an openly-licensed specification with a Technical Steering Committee drawn from **AWS, Cursor, Microsoft, OpenAI and Vercel**, at `agent-plugins.org`. A plugin is a directory containing a `plugin.json` manifest, an optional `skills/` folder and an optional **`mcp.json`** — so a single portable bundle carries both instruction content and MCP server configuration. It is already supported by **ChatGPT, Codex, Cursor, GitHub Copilot, Kiro and VS Code**. On 2026-08-07 this monitor reported "Codex Agent Plugins" as an OpenAI-specific capability; it is not one. The consequence for coverage is direct: an artifact installed once is portable across six clients from five vendors, which means per-vendor extension inventory can no longer establish what an endpoint is actually running — and **the spec has no security-considerations section at all**, so trust, provenance and MCP enablement are left entirely to each client.

**The first client-specific consequence is already visible, in Kiro.** Kiro's implementation is called **Powers**, installable from a curated marketplace, **from any public GitHub repository URL**, or from a local folder. The sharp edge is a single documented sentence: for `plugin.json`-format plugins, "**MCP servers are managed internally by Kiro and are not added to your user-level `~/.kiro/settings/mcp.json` file**." The canonical MCP configuration file is therefore **no longer a complete inventory of an endpoint's MCP servers** — the legacy `POWER.md` format still registers there, the standard format does not. Any collector that reads `mcp.json` to enumerate MCP servers now under-reports by exactly the set installed through the new standard.

**Kiro's second surface is instruction injection with no gate.** Kiro **IDE 1.0.309 (Aug 13)** and **CLI 2.18.0 (Aug 12)** added `AGENTS.md` as steering context "from anywhere in your workspace tree," and the steering documentation states the two properties that matter together: `AGENTS.md` files "**do not support inclusion modes and are always included**," and Kiro "**automatically discovers them in subdirectories throughout your workspace**." Unlike Kiro's own steering files — which carry `always` / `fileMatch` / `manual` / `auto` modes — an `AGENTS.md` anywhere in a cloned tree is unconditionally loaded, with no trust prompt documented.

**Google has shipped a new IAM principal type for agents and it is not in Zenity's model.** **Agent Identity** gives every deployed agent a strongly-attested cryptographic identity based on **SPIFFE**, formatted `spiffe://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH` and appearing in IAM policy as a **`principal://`** identifier. Agents get an auto-provisioned **X.509 certificate rotated every 24 hours**, authenticate to **MCP servers, cloud resources and other agents** either on their own authority or on behalf of a user via 3-legged OAuth, and are governed by IAM allow/deny policies, **Principal Access Boundary**, VPC Service Controls and default Context-Aware Access policies enforcing **mTLS and DPoP token binding**. Administrators can now see an agent's SPIFFE ID on the Agent details page (**Public Preview**), falling back to the Agent Registry resource ID when the publisher does not publish one. This never appears in this monitor's reports; the "Agent Identity" reported on 2026-08-10 was Microsoft's Entra Agent ID, a different thing entirely.

### Kiro — first scan; three findings

Not in `sources.json`; read at `kiro.dev/changelog` and `kiro.dev/docs/*` after AWS named Kiro the migration target for the Amazon Q Developer IDE plugin population (retiring 2027-04-30).

- **Powers — Kiro's implementation of the Agent Plugins standard.** A power is "a dynamic plugin that bundles specialized knowledge, tools, and workflows," structured as `plugin.json` (required manifest, declares **activation keywords**), `skills/`, an optional **`mcp.json`**, and an optional `dev.kiro/` for Kiro-specific steering extensions. Three install paths: the curated marketplace at `kiro.dev/powers` (partners include **Datadog, Figma, Stripe**) via one-click "Add to Kiro"; **any public GitHub repository URL**, where "a single repository can contain multiple powers, each in its own directory"; and a local folder for private repos. Activation is dynamic — Kiro "reads the task description, evaluates installed powers against the task, and loads only relevant powers into context" — rather than loading everything at startup. Kiro's own guidance is the only stated control: "Kiro powers are third-party tools that may be subject to separate terms. Only install powers from trusted sources." Source: https://kiro.dev/docs/powers/installation/

Steering files live in `.kiro/steering/` (workspace) and `~/.kiro/steering/` (global, applies to *all* workspaces), with workspace winning on conflict. `AGENTS.md` is handled differently: it "**do[es] not support inclusion modes and [is] always included**," and Kiro "automatically discovers them in subdirectories throughout your workspace." Source: https://kiro.dev/docs/steering/

### Cross-vendor — Agent Plugins 1.0.0 (August 6, 2026)

- **An open, vendor-neutral specification for packaging agent extensions**, at `agent-plugins.org`, with the spec, JSON Schemas, governance and contribution process in a public GitHub repository (`agentplugins/agent-plugins-spec`). Version **1.0.0** is current; **1.1.0 is a working draft**. The Technical Steering Committee is drawn from **AWS, Cursor, Microsoft, OpenAI and Vercel** — "no single company's product roadmap sets the format's direction." Version 1.0.0 standardizes two component types: **Agent Skills** (reusable instructions and resources, each a folder with a `SKILL.md` carrying `name` and `description` frontmatter) and **MCP servers** (`mcp.json` describing **stdio, Streamable HTTP, or legacy HTTP+SSE** servers). The manifest's minimum is two fields — `$schema` and `name`. Clients discover components by scanning the directory structure; the spec **deliberately leaves installation, surfacing and distribution to each client**. Supported today by **ChatGPT, Codex, Cursor, GitHub Copilot, Kiro and VS Code**. Sources: https://agent-plugins.org and https://vercel.com/blog/introducing-agent-plugins
- **Agent Toolkit for AWS** — official AWS-supported MCP servers, skills and plugins, bundling **30+ curated skills** across service selection, CDK/CloudFormation, serverless (Lambda), containers, storage (S3, DynamoDB), IAM policy configuration, observability, billing, SDK usage and deployment, plus skills for **building agents on Bedrock and AgentCore** and for **data-lake/analytics/ETL work with S3 Tables, Glue and Athena**. Four install paths, including runtime retrieval through the AWS MCP Server with no local installation. Plugins ship for **Claude Code, Codex and Cursor**; Kiro consumes the same content as Powers. Source: https://docs.aws.amazon.com/agent-toolkit/latest/userguide/skills.html

### Google Gemini Enterprise Agent Platform — Agent Identity (coverage-gap recovery)

The Gemini Enterprise app release-note stream (the one that renders) tops at **August 20** and every entry there was reported or explicitly held on 08-21. The finding below came from following the Agent-details-page SPIFFE ID mention into the IAM and Agent Platform governance docs.

- **Agent Identity — a SPIFFE-based, per-agent cryptographic identity that is a first-class IAM principal.** Format: `spiffe://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH`, e.g. `spiffe://agents.global.org-123456789012.system.id.goog/resources/aiplatform/projects/9876543210/locations/us-central1/reasoningEngines/my-test-agent`; in IAM policy the same identity appears with a **`principal://`** prefix. On deployment, "Google Cloud assigns it a unique SPIFFE identity and an X.509 certificate," **auto-renewed every 24 hours**. Explicitly contrasted with service accounts: agent identities "are not shared by multiple workloads by default, can't be impersonated, and don't allow developers to generate long-lived service account keys." Agents authenticate to **MCP servers, cloud resources, other agents and external tools**, either on their own authority (bound access tokens for Google Cloud; 2-legged OAuth, API keys or HTTP basic for external services) or **on behalf of an end user via 3-legged OAuth**. Governance surfaces: IAM allow **and deny** policies, **Principal Access Boundary (PAB)**, VPC Service Controls, and default **Context-Aware Access policies enforcing mTLS and DPoP token binding**. Audit logs distinguish "when the agent is acting as itself and when it is acting on behalf of an end user." Administrator visibility of the SPIFFE ID on the Agent details page is **Public Preview**, with the Agent Registry resource ID as fallback. Source: https://docs.cloud.google.com/iam/docs/agent-identity-overview

## New Coverage Required

- **[ENDPOINT] [HIGH] Agent Plugins 1.0 — one open, vendor-neutral bundle format carrying skills *and* MCP server configuration, already live in ChatGPT, Codex, Cursor, GitHub Copilot, Kiro and VS Code**: On **August 6, 2026** AWS, Cursor, Microsoft, OpenAI and Vercel published **Agent Plugins 1.0.0** as an openly-licensed specification with a shared Technical Steering Committee, at `agent-plugins.org`, with schemas and governance in a public repo. A plugin is a directory: a **`plugin.json`** manifest (minimum two fields — `$schema` and `name` — plus, in practice, activation keywords), an optional **`skills/`** folder of `SKILL.md` files in the Agent Skills format, and an optional **`mcp.json`** describing **stdio, Streamable HTTP or legacy HTTP+SSE** MCP servers. **This monitor has been reporting the same thing under several vendor names, and that framing is now wrong.** On 2026-08-07 it reported "Codex Agent Plugins" as an OpenAI capability with an OpenAI-specific marketplace path; on 2026-08-23 it reported Foundry's Skills API and the `agentskills.io` specification; Kiro's Powers, the Agent Toolkit for AWS, and Vercel's implementation are the same format again. The single most important consequence is that **an extension artifact is now portable across six clients from five vendors**, so per-vendor extension inventory cannot establish what an endpoint is running — a plugin authored once, installed from one marketplace, appears in a developer's Codex session, their Cursor session, their VS Code/GitHub Copilot session and their Kiro session, and each vendor's own management surface sees only its own slice. **The second consequence is that the bundle is a tool-and-connection grant, not documentation.** Because `mcp.json` travels inside the plugin, installing a plugin installs MCP servers — and the spec **deliberately leaves installation, surfacing and distribution to each client** ("preserving their ability to differentiate"), which means there is no standard trust prompt, no standard provenance record and no standard enablement gate; each client invents its own, and one of them (see the next finding) does not write installed servers to its own config file at all. **Third: the spec has no security-considerations section.** Neither `agent-plugins.org`, the AWS announcement, the Vercel announcement, nor the spec repo contains one — so the format that now moves instruction content and MCP connections between six agent clients ships with no normative guidance on trust, signing, or provenance. **1.1.0 is already a working draft**, so the component set will grow, and a new component type will change the surface on six clients at once. ENDPOINT should model "Agent Plugin" as a **cross-vendor entity type with one identity and many install sites** rather than as N per-vendor features: enumerate plugin directories on developer machines, parse `plugin.json` for identity and `mcp.json` for the servers and transports each grants, resolve the origin (marketplace, git remote, local path) as provenance, and reconcile the same plugin observed across different clients as one artifact. AISPM should treat a plugin's `skills/` bodies as privilege-shaping instruction content and its `mcp.json` as a connection inventory, and should expect the vendor-side registries to be incomplete by design. AIRT should treat a plugin as a single vector that reaches every compliant client at once. Sources: https://agent-plugins.org and https://vercel.com/blog/introducing-agent-plugins

- **[ENDPOINT] [HIGH] Kiro installs plugin-format MCP servers *without* writing them to `~/.kiro/settings/mcp.json` — the canonical MCP config file is no longer a complete inventory**: Kiro's implementation of Agent Plugins is called **Powers**, and its installation documentation draws a distinction that breaks endpoint MCP discovery: for **Agent Plugins (`plugin.json`) format**, "**MCP servers are managed internally by Kiro and are not added to your user-level `~/.kiro/settings/mcp.json` file**," whereas for the **legacy `POWER.md` format**, "servers register in the `~/.kiro/settings/mcp.json` configuration file under the Powers section." So the same capability — an MCP server reachable by the agent — is visible in the config file or invisible in it **depending purely on which packaging format the power used**, and the newer, standard, marketplace-endorsed format is the invisible one. Any collector that enumerates MCP servers by reading `mcp.json` (the obvious and previously correct approach, and the one the 2026-08-23 memo recorded for Kiro) now systematically under-reports, and it under-reports in the direction of the format the whole industry is converging on. Three further specifics make this actionable. **The install surface is wide open**: powers install from the curated marketplace at `kiro.dev/powers` (Datadog, Figma and Stripe among the partners) with one click, **from any public GitHub repository URL** — where "a single repository can contain multiple powers, each in its own directory," so one URL can carry several tool grants — or from a local folder for private repos. **Activation is dynamic and content-driven**: Kiro "reads the task description, evaluates installed powers against the task, and loads only relevant powers into context," with activation keywords declared in `plugin.json`. That means *installed* and *active* are different sets, the active set changes per prompt, and which tools an agent holds at a given moment is a function of text the user typed — so point-in-time capability inventory is wrong for the same reason hot-reloading MCP config is, and the two compound. **The only documented control is advice**: "Kiro powers are third-party tools that may be subject to separate terms. Only install powers from trusted sources." No trust prompt, no signing, no approval workflow is documented. Urgency is inherited, not speculative: AWS is pushing the entire Amazon Q Developer IDE plugin population onto Kiro by **April 30, 2027**. ENDPOINT must enumerate Kiro powers from Kiro's own power storage rather than from `mcp.json`, parse each power's `mcp.json` for the servers and transports it grants, record install provenance (marketplace entry, GitHub URL, or local path) per power, treat the `plugin.json` activation keywords as the mapping from prompt text to tool availability, and continue to read `.kiro/agents` and both MCP config scopes for the hot-reload surface — while flagging that `mcp.json` alone is now an incomplete answer. Source: https://kiro.dev/docs/powers/installation/

- **[AISPM] [HIGH] Google Cloud Agent Identity — a SPIFFE-based per-agent identity that appears in IAM policy as a new `principal://` principal type**: Google has shipped a distinct identity primitive for agents, and it is not a service account. Every agent deployed on Google Cloud receives "a strongly attested, cryptographic identity … based on the SPIFFE standard," formatted `spiffe://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH` — e.g. `spiffe://agents.global.org-123456789012.system.id.goog/resources/aiplatform/projects/9876543210/locations/us-central1/reasoningEngines/my-test-agent` — together with an **auto-provisioned X.509 certificate that renews every 24 hours**. In IAM policy the identity is bound with a **`principal://` prefix**, and that detail is the first concrete action item: **any IAM policy parser that recognizes `serviceAccount:`, `user:`, `group:` and `domain:` members but not `principal://` will silently fail to attribute agent grants**, reading a policy as having no agent bindings when it has several. Google states the security properties as deliberate contrasts with service accounts — agent identities "are not shared by multiple workloads by default, can't be impersonated, and don't allow developers to generate long-lived service account keys" — which inverts the usual posture question: the finding is no longer "which agents share a service account and who can mint keys for it," but **"which agents still run on a service account instead of an agent identity,"** and that becomes a discoverable, alertable posture gap. The reach is broad and squarely in AISPM's remit: an agent identity authenticates to **MCP servers, cloud resources, other agents, and external tools and services**, either **on its own authority** (bound access tokens for Google Cloud; 2-legged OAuth, API keys or HTTP basic auth externally) or **on behalf of an end user via 3-legged OAuth** — so the same agent principal holds two materially different privilege envelopes, one bounded by the user's consent and one bounded only by the agent's own IAM, and the audit logs distinguish them ("clear audit logs both when the agent is acting as itself and when it is acting on behalf of an end user"). That distinction is the single highest-value signal here and AIDR should key on it: an agent operating under its own authority on data it only ever reached on a user's behalf is a privilege-escalation pattern that is visible in these logs and nowhere else. The governance surfaces are also new inventory: IAM **allow and deny** policies on agent principals, **Principal Access Boundary (PAB)** restricting which resources an agent may touch at all, VPC Service Controls, and **default Context-Aware Access policies enforcing mTLS and DPoP token binding** — a default that is worth reading as a baseline, because an agent whose CAA policy has been relaxed away from mTLS/DPoP is a downgrade Zenity can detect. Administrator visibility of the SPIFFE ID on the Gemini Enterprise Agent details page is **Public Preview**, and when a publisher does not publish a SPIFFE ID the console shows the **Agent Registry resource ID as a fallback** — so the console cannot be trusted as a uniform source of agent identity, and the presence of a fallback ID is itself a signal that an agent is running without an attested identity. **Note the mis-mapping hazard that caused this to be missed**: this monitor reported "Agent Identity" on 2026-08-10, but that was Microsoft's **Entra Agent ID**. The two are unrelated implementations of the same idea, and Zenity should model "attested per-agent identity" once with per-vendor bindings — Entra Agent ID, Google SPIFFE agent identity, and AgentCore's workload access tokens — rather than three unrelated features. AISPM should discover agent identities per project, parse `principal://` members out of IAM allow and deny policies, inventory PAB bindings and CAA policies per agent identity, flag agents still bound to service accounts, and flag any agent whose identity resolves only to a registry resource ID. Source: https://docs.cloud.google.com/iam/docs/agent-identity-overview

- **[AIRT] [MEDIUM] Kiro loads `AGENTS.md` from every subdirectory of a workspace, always, with no inclusion mode and no trust gate**: Kiro **IDE 1.0.309 (Aug 13)** and **CLI 2.18.0 (Aug 12)** added support for `AGENTS.md` as steering context "from anywhere in your workspace tree," and the steering documentation states the two properties whose combination is the finding: `AGENTS.md` files "**do not support inclusion modes and are always included**," and Kiro "**automatically discovers them in subdirectories throughout your workspace**." Contrast this with Kiro's own steering files, which live in `.kiro/steering/` and carry an explicit inclusion mode in YAML front matter — `always`, `fileMatch` (loaded only when working on matching files), `manual` (loaded only when referenced as `#steering-file-name`), or `auto` (loaded when the request matches the description). Those modes are a real, if coarse, scoping control, and `AGENTS.md` has none of them: a file placed in any directory of any repository the developer opens is unconditionally injected into the agent's context. Three properties make this a genuine injection vector rather than a configuration footnote. **It is repository-sourced**, so a dependency vendored into a subdirectory, a monorepo package owned by another team, or a cloned third-party project all carry instruction text that loads with no review — the same failure mode as Anthropic's repository-mounted skills (reported 2026-08-09), but with the scoping control removed rather than merely coarse. **`AGENTS.md` is a cross-vendor filename**, adopted well beyond Kiro, so a single file authored to steer one agent is read by whichever compliant agent opens the tree — the author of the file and the operator of the agent reading it need have no relationship. **And global steering compounds it**: `~/.kiro/steering/` "applies to all workspaces," so instruction content can be positioned once at user scope and reach every project the developer subsequently opens, with workspace files overriding on conflict. No trust prompt or approval mechanism for steering content is documented anywhere in the steering docs. AIRT should test whether instructions in a nested `AGENTS.md` — introduced through a dependency directory or a subrepo rather than the project root — steer tool selection, alter which powers activate, or suppress the agent's own safety behaviour, and should treat the nesting depth as part of the test because discovery is recursive. ENDPOINT should inventory every `AGENTS.md` in an open workspace tree plus the global `~/.kiro/steering/` directory, record content hashes and the git provenance of each file (authored locally, or arrived via a dependency or clone), and treat an `AGENTS.md` that appears in a directory the developer does not own as a distinct posture condition. Source: https://kiro.dev/docs/steering/

- **[AISPM] [MEDIUM] Agent Toolkit for AWS — 30+ AWS-authored skills plus official MCP servers, reaching four agent clients, with one install path that leaves nothing on disk**: AWS publishes an official first-party bundle of "MCP servers, skills, and plugins to help AI agents build on AWS," carrying **30+ curated skills** across service selection, **CDK/CloudFormation**, serverless (**Lambda**), containers, storage (**S3, DynamoDB**), **IAM policy configuration**, observability, billing, SDK usage and deployment — plus dedicated skill sets for **building agents on Bedrock and AgentCore** and for **data-lake/analytics/ETL work with S3 Tables, Glue and Athena**. Plugins ship today for **Claude Code, Codex and Cursor**; Kiro consumes the same content as Powers. Three things make this worth its own inventory line rather than a footnote to the Agent Plugins finding. **It is the concrete, high-privilege instance of the portable-bundle problem**: this is not a formatting utility but a package that equips an IDE agent to operate real AWS infrastructure — provisioning via CDK/CloudFormation, S3 and DynamoDB access, Lambda deployment, IAM policy authoring, billing data — and it reaches four different agent clients from one authoring source, so the same AWS-operating capability can arrive on a developer machine through whichever client that developer happens to use. **There are four install paths and one of them leaves nothing on disk.** Skills arrive bundled with a plugin; downloaded individually from the GitHub repo into the agent's skills directory; through an AWS CLI wizard (`aws configure agent-toolkit`) that "**detects supported agents on your system and installs skills into each agent's configuration directory**" — one command that fans a single grant out to every agent client on the machine; or **discovered at runtime through the AWS MCP Server "without any local installation,"** where the agent calls `search_documentation` to find a skill and `retrieve_skill` to load it into context. That last path is the one that matters most for coverage: **an agent can acquire and act on AWS-operating instructions with no on-disk artifact to inventory at all**, so file-based endpoint collection cannot see it and only MCP-call telemetry can — `retrieve_skill` is therefore a named activity type AIDR should record, not just a tool call. **And skills load on demand and are then released** ("after the task is complete, your agent releases the skill content from context"), so installed, loaded and active are three different sets and the agent's effective AWS capability at any moment is not a static property. The privilege that matters is not the skill text but the credential the agent already holds: instruction content that competently drives CDK, IAM and Lambda turns an ambiently-available AWS credential on a developer laptop into an infrastructure-change path — exactly the toxic combination of broad local credentials plus capable tooling that AISPM exists to flag. AISPM should treat the Agent Toolkit as a named, discoverable installed component per endpoint, resolve which of its plugins/skills are present and which client hosts them, and correlate its presence against the AWS credentials and assumed roles available on that machine — an endpoint with the toolkit installed and a long-lived administrative AWS credential is a materially different posture than one with either alone. ENDPOINT should record the toolkit's MCP servers alongside the plugin-format caveat in the Kiro finding above, since on Kiro these servers will not appear in `~/.kiro/settings/mcp.json`. Source: https://docs.aws.amazon.com/agent-toolkit/latest/userguide/skills.html
