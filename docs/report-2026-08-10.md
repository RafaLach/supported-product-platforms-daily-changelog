## Platform Details

### Microsoft Foundry / Microsoft 365 — backlog recovery (agent identity & control plane)

None of the following has appeared in any prior report from this monitor. It is not new *to the platform* — it is new to Zenity's coverage. The `whats-new-foundry` roll-up is still titled "What's new for **June 2026**" (ms.date 2026-07-08), which is why this was invisible; the Foundry **blog** names features the roll-up does not.

- **Microsoft Agent 365 — generally available since May 1, 2026** for the Commercial segment, licensed per user (Microsoft E5 recommended; at least one qualifying Agent 365 / M365 Copilot license required). Microsoft's enterprise **control plane for AI agents**, built on Entra Agent ID, organised as observe / govern / secure. Five capabilities: **Registry** (tenant-wide inventory of Foundry agents, Copilot Studio agents, admin-registered agents and **shadow agents discovered in the tenant**, with ownership tracking for attestation; plus Registry sync and **Agent Map**), **Access control** (Entra RBAC + ABAC and risk-based Conditional Access), **Visualization** (connections between agents, people and data; real-time behaviour monitoring), **Interoperability** (access to M365 apps and org data; can connect to Work IQ), and **Security** (Microsoft Defender threat detection, Microsoft Purview information protection, DLP and compliance controls on agent activity). A set of **pre-integrated ecosystem partner agents** is deployable directly from the Microsoft 365 admin center. Source: https://learn.microsoft.com/en-us/microsoft-agent-365/overview
- **Agent Registry in the Microsoft 365 admin center** — the concrete inventory. Four agent types (Microsoft, external partner-built, published by your org, shared by creator); tenant-wide counters for **Total agents**, **Agents without owners** and **Unmanaged agents** ("created or managed outside of Agent 365, without its risk protection and observability"); filters on status, publisher type, **channel** (Copilot, Teams, Outlook, M365 apps, SharePoint), **platform**, and **data source** (embedded knowledge, fine-tuned models). A **Risks** column aggregates high-severity risk across Entra, Defender and Purview, with a documented ten-type taxonomy: **Shadow agent** (Critical — no registry entry, no owner, or no Entra Agent ID), **No owner assigned** (Critical), **Excessive permissions** (Critical — access rights exceed declared function), **Security misconfiguration** (High), **Prompt injection** (High — AI Prompt Shield flags/blocks at runtime), **Sensitive data access** (High — labeled data accessed without a matching DLP exception), **Conditional access violation** (High), **Pending approval** (Medium), **Operational exceptions** (Medium), **Compliance/retention gap** (Medium). Export to Excel carries **over 30 attributes per agent**. Source: https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-registry
- **Package Management API — programmatic agent inventory and control (partly preview)** — a "package" represents an agent in the organization catalog. `GET /copilot/admin/catalog/packages` lists every agent in the organisation, filterable by **host** (Copilot, Outlook, Teams), **platform** (Copilot Studio, M365 Copilot Agent Builder), last-updated time, and **element types contained in the package** (bots, declarative agents and more); `GET /copilot/admin/catalog/packages/{id}` returns detailed metadata including `declarativeAgent` / `customEngineAgent` element objects. Four **write** operations are in preview: `PATCH .../{id}` (update metadata), `POST .../{id}/block`, `POST .../{id}/unblock`, and `POST .../{id}/reassign` (reassign package ownership). Resources: `copilotPackage`, `copilotPackageDetail`. **Access requires a Microsoft Agent 365 license**; the registry docs state the API works with the **AI Administrator** role. Source: https://learn.microsoft.com/en-us/microsoft-365-copilot/extensibility/api/admin-settings/package/overview
- **Autopilot agents (preview) and autopilot publishing from Foundry** — a new agent *category*. Each autopilot receives its own **Entra Agent ID user account with a productivity license, email, calendar, OneDrive and Teams presence**, and is designed for shared spaces such as Teams group chats rather than 1:1 chat. The interaction model shifts from prompt→response to **goal → ongoing execution → checkpoints → collaboration**: it surfaces progress, requests approvals and escalates to a human natively inside Teams and M365. A Foundry **Hosted** agent is published as an autopilot; the publish submits a request that creates an **agent blueprint** in the Microsoft 365 admin center, an **AI Administrator or Global Administrator** approves it, and it then appears in the Agent 365 registry and can be instantiated in Teams. Provisioning footprint includes an **Azure Bot Service** resource (Foundry-scoped roles do not carry `Microsoft.BotService/*`), Container Registry, and Application Insights + Log Analytics. Enablement requires a M365 Copilot license **plus enrollment in the Frontier preview program**, and a global admin accepting terms. Reference implementation is the **Workstream Manager** sample. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/agent-365
- **Foundry ↔ Agent 365 data flow, logging and residency** — published Foundry agents sync automatically into the Agent 365 registry. Per-Foundry-resource logging is governed by the **`agent365Config` resource provider configuration**, and no data flows without both a valid license and accepted terms even when the ARM property is enabled. Critically, **Foundry follows the Azure region of the resource for data residency while Agent 365 follows the Entra tenant's storage location** — activity data crossing from Foundry into Agent 365 moves between two different residency models. Individual Foundry resources can be opted out. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-365-integration
- **New Foundry agent object model (replaces Agent Applications)** — collapses the **Agent Application** and **Deployment** control-plane objects into the **Agent** object. New agent properties: `agent_endpoint` (stable endpoint), `protocol_configuration`, `authorization_schemes`, `version_selector`, `blueprint`, `instance_identity`, and **`agent_card`** (surfaces the agent's details and capabilities to consumers and to **A2A**). Every newly created agent now receives a unique **Entra Agent Blueprint and Entra Agent Identity by default, at creation** — creating an agent is the only step needed to get a stable endpoint and a unique identity, and "publishing" now means only distribution to M365/Teams. Legacy agents are identified by a **null `instance_identity` / `agent.identity`**, share the project identity, and cannot be published via the stable endpoint; there is **no in-place upgrade** — you must recreate the agent. Endpoint format changed from `/applications/{app}/protocols/openai` to `/agents/{agent}/endpoint/protocols/openai/responses`. Agent Application deprecation is **planned**, end of support TBD. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/migrate-agent-applications
- **Agent Applications (legacy) as ARM resources** — types `Microsoft.CognitiveServices/accounts/projects/applications` and `.../applications/agentDeployments`, with properties including `agentIdentityBlueprint`, `defaultInstanceIdentity`, `authorizationPolicy`, `trafficRoutingPolicy`, `isEnabled`, and deployment `state` / `deploymentType` (`Hosted` | `Managed`) / `minReplicas` / `maxReplicas`. Exposes either the **Responses** protocol (stateless `POST /responses` only) or the **Activity Protocol**, one at a time; **API-key auth is not supported**. Microsoft states plainly: **"Foundry Agent Applications are not registered in the Microsoft Entra agent registry."** Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/agent-applications
- **Foundry agent identity framework** — an **agent identity** is a special Entra **service principal**; an **agent identity blueprint** is an Entra object governing a whole *class* of agent identities and holding the OAuth credentials (client secret, certificate, or **federated credential** via the project's managed identity) used to mint them. A four-stage OAuth 2.0 token exchange runs automatically per tool call, scoped to a downstream **audience**. Agents authenticate either **attended** (on-behalf-of, bounded by the user's consent) or **unattended** (client-credentials, bounded only by the agent's own RBAC and Graph app permissions — no human involved). Blueprints enable Conditional Access, bulk disable/revoke and audit at the agent-*class* level. Tenant-wide inventory lives at **Entra admin center → Entra ID → Agent ID → All agent identities**, covering Foundry *and* Copilot Studio agents. Only **MCP** and **A2A** tools currently support agent-identity auth (connection auth type `AgenticIdentityToken`). **Permissions do not transfer when an agent is published.** Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity
- **Foundry RBAC roles renamed, and agent-scope role assignments** — **Azure AI User / Owner / Account Owner / Project Manager** are now **Foundry User / Owner / Account Owner / Project Manager** (role IDs and permissions unchanged; Microsoft explicitly advises using role definition GUIDs rather than names during rollout). A **Foundry Agent Consumer** least-privilege role exists for principals that only invoke agents. Roles can now be assigned at the scope of an **individual agent** (`.../projects/{project}/agents/{agent}`), though such assignments are currently evaluated only for agent endpoint access. Source: https://learn.microsoft.com/en-us/azure/foundry/concepts/rbac-foundry

## New Coverage Required

- **[AISPM] [HIGH] Microsoft Agent 365 — a GA, tenant-wide agent control plane with its own shadow-agent discovery**: Microsoft Agent 365 has been generally available since **May 1, 2026** and this monitor has never reported it. It is Microsoft's enterprise control plane for AI agents, built on Entra Agent ID, and it maintains a **tenant-wide registry of every agent in the organisation regardless of where it was built** — Foundry agents, Copilot Studio agents, admin-registered agents, pre-integrated third-party partner agents deployable straight from the M365 admin center, and **shadow agents it discovers in the tenant itself**. It layers on Entra RBAC/ABAC and risk-based Conditional Access, Purview information protection and DLP, and Defender threat detection over agent activity. Two things make this urgent rather than merely interesting. First, it is a **new inventory surface Zenity must discover and reconcile**: an agent that exists in the Agent 365 registry but not in Zenity's inventory is a coverage gap, and the reverse is a governance gap Zenity can report on. Second, it **overlaps AISPM's own function** — a customer with Agent 365 enabled already has a partial agent inventory with ownership and risk signals, so Zenity needs to know what Agent 365 does and does not see (notably: it is licence-gated, requires a global admin to accept terms, and its own docs concede that "unmanaged agents" created outside it lack its risk protection and observability). AISPM should discover whether Agent 365 is enabled per tenant, ingest its registry as a comparison inventory, and treat divergence between the two inventories as a finding in its own right. Source: https://learn.microsoft.com/en-us/microsoft-agent-365/overview

- **[AISPM] [HIGH] Microsoft 365 Agent Registry — a formal agent risk taxonomy and inventory schema Zenity should reconcile against**: The Agent 365 registry in the Microsoft 365 admin center exposes a concrete, documented inventory model that maps almost one-to-one onto AISPM's own concerns, and Zenity is not currently reading it. It classifies agents into four publisher types, filters them by **channel** (Copilot, Teams, Outlook, M365 apps, SharePoint), **platform**, and **data source** (embedded knowledge files uploaded by the maker, and **fine-tuned models** produced by M365 Copilot Tuning), and exports **over 30 attributes per agent**. It carries tenant-level counters for **agents without owners** and **unmanaged agents**, and a **Risks** column aggregating high-severity risk from Entra, Defender and Purview against a ten-type taxonomy that includes **Shadow agent** (Critical — defined as having no registry entry, no owner, or no Entra Agent ID), **Excessive permissions** (Critical — access rights exceeding declared function, i.e. a least-privilege violation), **Prompt injection** (High — flagged by AI Prompt Shield at runtime), **Sensitive data access** (High — labeled data accessed without a matching DLP exception), and **Conditional access violation** (High). This is both an opportunity and a competitive baseline: these are the exact toxic combinations AISPM reports, now computed natively by the platform. AISPM should ingest the registry's attributes as inventory enrichment (especially channel, platform, embedded-knowledge and fine-tuned-model flags, and owner), map Microsoft's risk types onto Zenity's violation rules so findings can be deduplicated rather than duplicated, and specifically target the gaps — Microsoft surfaces only **high**-severity risks in this column, with up to an hour of lag, and its shadow-agent definition is Entra-registration-based, so agents with a valid Entra Agent ID but no real ownership or oversight will not trip it. Source: https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-registry

- **[AISPM] [HIGH] Microsoft 365 Package Management API — a tenant-wide agent inventory endpoint that also blocks agents and reassigns their ownership**: Microsoft has put the Agent 365 agent catalog behind a Graph-style admin API where a "package" is an agent. `GET /copilot/admin/catalog/packages` returns every agent in the organisation — filterable by **host** (Copilot, Outlook, Teams), **platform** (Copilot Studio, M365 Copilot Agent Builder), last-updated time, and the **element types inside the package** (bots, declarative agents and more) — and `GET /copilot/admin/catalog/packages/{id}` returns per-agent metadata including the `declarativeAgent` and `customEngineAgent` element objects. This is the single most useful integration point in this report: it is how Zenity can enumerate Microsoft-side agents across every host surface in one call instead of inferring them per product, with element-level detail that reveals what an agent actually contains. It needs a posture rule as well as an integration, because the API is **not read-only**: `PATCH /{id}`, `POST /{id}/block`, `POST /{id}/unblock` and `POST /{id}/reassign` (reassign ownership to a different user) are all available in preview. Combined with the registry docs' statement that the API works with the **AI Administrator** role, that means an AI Administrator can enumerate the entire agent estate *and* disable agents or transfer their ownership — a privileged, low-friction control path that deserves both access review and activity monitoring. AISPM should adopt the list/detail endpoints as a discovery source for the Microsoft estate, inventory AI Administrator assignments as a privileged role, and treat block/unblock/reassign calls as auditable agent-lifecycle events. Note the whole API requires a **Microsoft Agent 365 license**, so it is unavailable in unlicensed tenants — Zenity's Microsoft discovery cannot depend on it alone. Source: https://learn.microsoft.com/en-us/microsoft-365-copilot/extensibility/api/admin-settings/package/overview

- **[AISPM] [HIGH] Microsoft Foundry autopilot agents — agents provisioned as licensed Entra users with a mailbox, calendar, OneDrive and Teams presence**: Foundry Hosted agents can now be published as **autopilots** into Agent 365, and an autopilot is not a bot behind an endpoint — it is an **Entra Agent ID user account carrying a productivity licence, an email address, a calendar, OneDrive storage and a Teams presence**, living inside shared spaces like group chats. Its interaction model is explicitly **goal → ongoing execution → checkpoints → collaboration**: it is assigned an objective, works continuously, requests approvals and escalates to humans on its own initiative. This collapses the distinction Zenity's inventory relies on between "identities" and "agents": an autopilot must be modelled simultaneously as an agent (with a Foundry-side tool, memory and toolbox configuration) and as a **mailbox-bearing directory principal** that can receive mail, hold meetings and store files — a data-exfiltration and phishing surface no agent-shaped entity previously had. Three concrete inventory items follow: the **Entra Agent ID user account and its licence**, the **agent blueprint** created in the Microsoft 365 admin center and the identity of the AI/Global Administrator who approved it, and the **Azure Bot Service resource** in the publish path (notable because Foundry-scoped roles deliberately exclude `Microsoft.BotService/*`, so publishing requires a separate, broader Owner/Contributor grant at resource-group scope). AISPM should discover autopilots as a distinct entity type, join the Foundry-side capability graph to the M365-side user account, flag autopilots whose mailbox or OneDrive is reachable from outside the tenant, and treat the approval record as the authorisation artifact to audit. AIRT should test whether content delivered to an autopilot's mailbox or a Teams group chat is treated as trusted instruction. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/agent-365

- **[AISPM] [HIGH] Microsoft Foundry replaced its agent object model — every agent now gets a unique Entra identity and an A2A-discoverable agent card at creation**: Foundry has **collapsed the Agent Application and Deployment control-plane objects into the Agent object itself**, and the consequences reach directly into how agents must be inventoried. Every newly created agent now receives a **unique Entra Agent Blueprint and Entra Agent Identity by default, at creation** — previously identity was only minted at publish and unpublished agents shared one project identity. Agents gained `agent_endpoint` (a stable endpoint that exists from creation, with no publish step), `authorization_schemes`, `protocol_configuration`, `version_selector`, `instance_identity`, and **`agent_card`**, which advertises the agent's details and capabilities to consumers **and to A2A** — meaning every agent is now potentially discoverable and callable by other agents by default. Zenity must handle the resulting **three-population problem**: new agents (non-null `instance_identity`, unique identity, all features), legacy agents (**null `instance_identity`**, sharing the project identity, backfilled with the new properties but unpublishable), and surviving Agent Applications as separate resources — and because Microsoft provides **no in-place upgrade**, customers will migrate by recreating agents, producing duplicate logical agents with different identities and endpoints during the transition. AISPM should key Foundry agent discovery on `instance_identity` to segment these populations, inventory `agent_card` contents as the agent's advertised capability set, treat a null identity as a posture finding (shared-identity blast radius), and detect the old and new endpoint URL forms as the same logical agent. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/migrate-agent-applications

- **[AISPM] [HIGH] Microsoft Foundry Agent Applications are ARM resources that Microsoft states are NOT in the Entra agent registry**: Published Foundry agents exist as first-class Azure resources — `Microsoft.CognitiveServices/accounts/projects/applications` with child `agentDeployments` — each wrapping an agent version with its own dedicated endpoint (`baseUrl`), its own `agentIdentityBlueprint` and `defaultInstanceIdentity`, an `authorizationPolicy`, and a `trafficRoutingPolicy`. The finding is Microsoft's own explicit statement that **"Foundry Agent Applications are not registered in the Microsoft Entra agent registry."** That is a documented blind spot at the centre of Microsoft's own agent governance story: an organisation relying on the Entra Agent ID registry or the Agent 365 registry for its agent inventory **will not see agents published this way**, even though each one is a live, independently addressable, internet-reachable endpoint running with its own identity. Zenity can close a gap the platform vendor has admitted to. AISPM should enumerate these ARM resources directly via Azure Resource Manager rather than relying on any Entra- or Agent-365-derived inventory, resolve each application's identity and deployment state, record `authorizationPolicy` (noting that **API-key auth is not supported**, so every caller is an Entra principal that can be resolved) and `trafficRoutingPolicy`, and flag applications that are enabled with a running deployment but absent from the tenant's agent registry. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/agent-applications

- **[AISPM] [HIGH] Microsoft Foundry agent identity blueprints — class-level credentials that mint agent identities, and unattended app-only agent auth**: Foundry's identity model introduces two Entra object types Zenity should treat as first-class inventory. An **agent identity** is a special service principal representing one agent at runtime; an **agent identity blueprint** is the governing object for an entire *class* of agents, and it **holds the OAuth credentials — client secret, certificate, or federated credential — used to create and impersonate every agent identity beneath it**. A blueprint is therefore a high-value credential whose compromise implies control of a whole class of agents, and its credential type is a posture signal (Microsoft recommends federated/managed identity precisely to avoid stored secrets, but client secrets and certificates are supported and require manual rotation). Blueprints are also the correct enforcement point: Conditional Access, bulk disable and revocation all apply at blueprint level. Separately, agents authenticate in one of two modes, and the distinction is the finding: **attended** (on-behalf-of, so the agent can only reach what the user consented to) versus **unattended** (client-credentials/app-only, where **no human is involved and access is bounded only by the agent's own RBAC and Graph app permissions**). An unattended agent with broad role assignments is an autonomous, fully-privileged actor. AISPM should inventory blueprints and their credential types, map each agent identity to its blueprint, record which agents run unattended, resolve `agentIdentityId` role assignments across downstream resources to compute effective reach, and flag the documented failure mode that **permissions do not transfer when an agent is published** — which in practice pushes operators toward over-granting on the new identity. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity

- **[AISPM] [HIGH] ServiceNow MCP Server Console — a ServiceNow instance becomes a governed MCP server exposing workflows as agent tools**: The Australia release adds an entirely new application, **MCP Server Console** (plugin `sn_mcp_server`, v1.3), that turns a ServiceNow instance into an MCP server any MCP-compatible AI agent can call. Its significance is what becomes a *tool*: administrators can expose **Subflows, Actions, REST APIs, Knowledge Graphs and Now Assist skills** as MCP tools, with a preconfigured Quickstart Server for incident and case record operations. That means arbitrary ServiceNow automation — approvals, catalog actions, record mutation, workflow execution — is now reachable by external agents, and vendor coverage confirms the **Action Fabric MCP Server is GA across every Now Assist and AI Native SKU** with **Anthropic Claude integration live**. Each MCP server is a new inventory entity with an endpoint, an **embedded OAuth client registration**, an authentication configuration that can delegate to a **third-party IDP**, and a tool list whose blast radius is defined by the underlying subflow or REST API rather than by anything visible on the MCP surface. **MCP apps** additionally allow interactive, client-side-rendered tool interfaces, which is a UI-injection surface. AISPM should discover MCP servers and their registered tools on ServiceNow instances, resolve each tool back to the subflow/action/API it wraps and the privileges that carries, record the OAuth client and IDP binding, and flag write-capable tools reachable by external agents. AIRT should treat these tools as a prompt-injection-to-privileged-action path, since a compromised agent conversation now maps directly onto ServiceNow workflow execution. Source: https://www.servicenow.com/docs/r/release-notes/mcp-server-console-rn.html

- **[AISPM] [HIGH] ServiceNow AI Control Tower (Australia) — cross-cloud agent governance that can deactivate agents in AWS Bedrock and GCP Vertex AI**: The long-held AI Control Tower question is resolved: it ships in the **Australia release** via the ServiceNow Store, substantially redesigned, and **AI Gateway is deprecated and no longer supported**. - **[AISPM] [MEDIUM] Microsoft Foundry RBAC roles renamed, plus new per-agent role assignment scope**: Foundry's built-in roles have been renamed — **Azure AI User / Owner / Account Owner / Project Manager** are now **Foundry User / Owner / Account Owner / Project Manager** — with role IDs and permissions unchanged, and Microsoft explicitly advises using role definition GUIDs instead of names because both sets of names are in circulation during rollout. Any Zenity discovery rule, policy or report that matches Foundry permissions on **role name** will silently miss renamed assignments and under-report privilege; this is a small change with a quiet failure mode, which is why it is worth a finding. Two associated details matter for least-privilege analysis: a **Foundry Agent Consumer** role now exists for principals that only invoke agents (so seeing Foundry User where Agent Consumer would suffice is an over-grant worth flagging), and roles can now be assigned at the scope of an **individual agent** (`.../projects/{project}/agents/{agent}`) — a new, finer scope Zenity's permission model should represent, with the caveat that Microsoft currently evaluates agent-scope assignments **only** for endpoint access and not for control-plane operations, so an agent-scoped assignment can look more restrictive than it behaves. - **[AIDR] [MEDIUM] Microsoft Agent 365 activity ingestion and the Foundry→Agent 365 data-residency crossing**: Enabling Agent 365 causes **agent activity data from Foundry to be ingested into the Agent 365 control plane**, where it powers the registry, analytics dashboards and security features — making Agent 365 a new, retained activity stream covering agents across the tenant and therefore an AIDR ingestion candidate. Two properties make it more than a feed. First, ingestion is governed per Foundry resource by the **`agent365Config` resource provider configuration**, and the whole pipeline is additionally gated on tenant licensing and a global administrator having accepted terms — so **an agent can be fully governed on paper while its activity is silently not being collected**, and the state of that per-resource config is a posture signal rather than a detail. Second, **Foundry and Agent 365 use different data-residency models**: Foundry follows the Azure region of the resource, Agent 365 follows the **Entra tenant's storage location**, so activity data crossing between them moves from region-scoped to tenant-scoped residency and may leave the geography the Foundry resource was deliberately placed in. Microsoft's mitigation is per-resource opt-out, which means residency compliance here is a per-resource setting nobody is likely to audit. AIDR should ingest Agent 365 activity as an agent-behaviour source; AISPM should record `agent365Config` state per Foundry resource, flag resources where governance is assumed but collection is disabled, and treat the residency crossing as a data-flow finding for regulated tenants. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-365-integration
