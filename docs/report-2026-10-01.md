## Platform Details

### ChatGPT Enterprise (OpenAI) — primary

- **Agents API** — a managed agent runtime distinct from the Responses API. Object model is **Agent** (model, instructions, tools, MCP servers), **Environment** (sandbox), **Session** (durable, server-retained state across turns) and **Events/items**. Sessions are created at `POST https://api.openai.com/v1/agents/sessions` behind the `OpenAI-Beta: agents=v1` header. Supports **subagent delegation** (up to 4 concurrent in documented examples), MCP servers over HTTP transport, web search, code execution, file editing and command execution. OpenAI manages orchestration, context compaction and recovery. US-only data residency; **Zero Data Retention is not supported, even with self-hosted sandboxes**. Entered public beta 2026-09-10 and was not caught by prior scans. Source: https://developers.openai.com/api/docs/guides/agents-api/overview
- **Computer use in the Agents API** (2026-09-29) — agents drive a browser in an **OpenAI-hosted environment**, with per-origin approval and in-band credential collection. Source: https://developers.openai.com/api/docs/changelog
- **Dots** (2026-09-29) — always-on autonomous agents in ChatGPT, powered by GPT-6 Astra. Each dot has **its own cloud computer and browser**, runs while the user is offline, reaches 4,000+ apps through plugins, and delegates to background subagents. Off by default; enabled per workspace by an administrator. Source: https://learn.chatgpt.com/docs/dots
- **Local computer access for dots and Work Cloud** — a cloud-orchestrated agent executing on the user's own machine, gated by a new **Agent Security** admin surface. Source: https://learn.chatgpt.com/docs/enterprise/cloud-local-access
- **ChatGPT Space** (2026-09-29) — collaborative pages where agents are invoked inline, in comments and via slash commands. New entity set: Spaces, Members, Agents, Connectors, Files. Source: https://learn.chatgpt.com/docs/space/agents
- **Decisions API** (2026-09-29) — a new constrained-output decision endpoint backed by GPT-6 Luna; limited preview, GA announced on the OpenAI API and Microsoft Foundry. Source: https://openai.com/index/devday-2026-recap/
- *(Not reported — version/perf only:* GPT-6.1 Sol, the `service_tier: "ultrafast"` latency tier, Responses API latency improvements, Codex CLI 0.159.x UI changes.*)*

## New Coverage Required

- **[AISPM] [HIGH] OpenAI Agents API — a managed agent runtime with server-held sessions, sandbox environments and subagents**: OpenAI now runs the agent loop itself rather than leaving orchestration to the customer's code. Four new entity types enter the inventory — **Agent** (model + instructions + tools + attached MCP servers), **Environment** (an execution sandbox, OpenAI-hosted or self-hosted), **Session** (a *durable* agent instance whose conversation state, compaction and recovery are retained server-side by OpenAI), and **Events/items**. Agents may attach arbitrary **remote MCP servers over HTTP**, run **code execution, file editing and shell commands** inside the environment, and **delegate to subagents**, so one inventoried agent can fan out into a tree of executions the customer never registered. Two properties make this materially riskier than the Responses API surface Zenity already maps: session state is a **new OpenAI-side data store** that holds full conversation history, and **Zero Data Retention is not supported at all — even when the customer supplies their own sandbox**, so ZDR-contracted enterprises silently lose that guarantee the moment a team adopts the Agents API. Data residency is US-only. This went to public beta on 2026-09-10 and was missed for three weeks. AISPM must discover Agents, Environments and Sessions as first-class resources, enumerate each agent's MCP server attachments and tool grants, and flag ZDR-contracted tenants with Agents API usage. Source: https://developers.openai.com/api/docs/guides/agents-api/overview

- **[AIRT] [HIGH] Computer use in the Agents API — end-user passwords and verification codes are submitted into an OpenAI-hosted browser, and approval is per-origin, not per-action**: The Agents API now runs a full browser inside an OpenAI-controlled environment. Two documented properties are direct attack surface. First, **approval granularity is the origin, not the action**: a `computer_use_approval_request` of type `browser_origin_access` is raised once per new origin, and OpenAI's own documentation states that origin approval "does not enforce confirmation before individual actions" — so a single approval of a trusted domain authorises every subsequent purchase, deletion or data export the agent performs there, which is precisely the payoff an indirect prompt injection on that page is reaching for. Second, **the credential path is in-band**: for authenticated tasks the hosted browser raises a `browser_authentication` request and the application collects the user's email, password and verification codes and submits them through the **session events endpoint** — live human credentials and OTPs flowing into an OpenAI-hosted browser session. Passkeys and QR sign-in are not supported, which pushes tenants toward the weaker shared-secret path. Screenshots of authenticated pages are returned to the application and OpenAI warns they must be kept out of logs. AIRT should build injection and over-approval scenarios against origin-scoped consent; AISPM should inventory which agents carry the `computer_use` tool with the `openai_hosted` environment and treat them as credential-handling systems. Source: https://developers.openai.com/api/docs/guides/agents-api/tools/computer-use

- **[AISPM] [HIGH] OpenAI Dots — always-on autonomous agents with their own cloud computer, 4,000+ app reach and background subagents**: Dots, announced at DevDay on 2026-09-29, are persistent agents that **keep working after the user logs off**. Each dot is powered by GPT-6 Astra and is provisioned with **its own cloud computer and browser**, can act across **4,000+ apps via plugins already connected to the account**, and spawns **background subagents** to run tasks in parallel. Governance is a layered custom-rules model — read-only background research, four levels of Custom Rules, mandatory human takeover for passwords and money transfers, and an automatic pre-action auto-review — all of which are **per-dot configuration that an enterprise has no inventory of today**. Dots are off by default and enabled by a workspace administrator, which makes enablement state itself a posture signal. This is a new non-human identity class on the OpenAI surface: long-lived, self-directed, inheriting the user's full connector grants, and executing with no human in the session. AISPM must inventory dots per workspace, their Custom Rules level, their enabled plugin/connector reach, and flag dots whose inherited connector scope exceeds their owner's need; AIDR needs dot activity as a distinct, user-absent activity type. Source: https://learn.chatgpt.com/docs/dots

- **[ENDPOINT] [HIGH] Local computer access for dots and Work Cloud — OpenAI-orchestrated agents executing on employee machines, with audit split across two incompatible pipelines**: A new **"Allow local computer access"** permission lets a cloud-orchestrated dot or Work task execute on the user's own machine: running local repositories and developer tools, driving **desktop applications and the local browser**, and implementing changes and builds against local files. This is a managed-endpoint agent, governed through a new **Agent Security** admin surface with a Global baseline and per-environment overrides (approval policies and web search mode are Global-only and cannot be overridden). It requires ChatGPT desktop 26.929+. The audit story has documented holes Zenity should treat as coverage requirements rather than assurances: **local execution telemetry only leaves via OpenTelemetry export to the customer's own collector**, while **cloud orchestration records go to the Compliance API** — the two never meet, and **cloud OTel events do not reach legacy collectors**. OpenAI further documents that **MCP hooks do not provide complete audit trails** and that callback failures (timeouts, malformed responses) **can occur without blocking the action**, i.e. the agent proceeds while the control plane is blind. A `enforce_residency` cloud policy disables the feature, and it is unavailable for FedRAMP, EKM and UAE-residency workspaces. ENDPOINT must detect the desktop local executor and its permission state; AIDR must correlate the OTel local stream against Compliance API cloud records to find actions that executed with no corresponding audit record. Source: https://learn.chatgpt.com/docs/enterprise/cloud-local-access

- **[AISPM] [MEDIUM] ChatGPT Space — a collaborative document surface with embedded agents and connector reach**: Space introduces shared pages where agents are invoked inline (`@ChatGPT`, `@dot`), from comments, from a conversation sidebar and through slash commands. It brings a new entity set — **Spaces, Members (with differing permission levels), Agents including custom dots, Connectors, and Files** — and the agents available inside a Space inherit whatever tools the workspace has enabled. The security-relevant shape is a **multi-tenant collaborative container where an agent reads shared member content and reaches enterprise connectors**: content pasted into a Space by one member becomes agent-readable context for every agent invoked there, which is both a data-boundary question and an indirect prompt injection path. AISPM should inventory Spaces, their membership and permission levels, which agents and connectors are reachable from each, and flag Spaces whose connector reach crosses data-classification boundaries. Source: https://learn.chatgpt.com/docs/space/agents

- **[AISPM] [MEDIUM] OpenAI Decisions API — a new constrained-choice endpoint that routes agent control flow**: The Decisions API, introduced at DevDay on 2026-09-29, lets an application hand a narrow repetitive choice to GPT-6 Luna: the caller supplies context as text or images plus a **fixed set of predefined answers**, and the model selects among them. It is explicitly positioned for classifying content, routing requests, and **choosing an agent's next action** — which makes it a control-flow component, not a content-generation one, and therefore an unmonitored decision point inside agent pipelines Zenity otherwise maps. It is distinct from Structured Outputs (which constrains response *shape*, not the answer set). Announced GA on the OpenAI API and **Microsoft Foundry**, currently limited preview with no public endpoint schema yet; AISPM should add it to the OpenAI API inventory now and revisit when the reference publishes, since a Foundry-side surface means it will also appear on a Microsoft primary-tier platform. Source: https://openai.com/index/devday-2026-recap/
