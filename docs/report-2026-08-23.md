## Executive Summary

**This scan covers a 2-day gap** — the previous run was 2026-08-21 — and the live-movement delta is correspondingly small. Only **one platform published genuinely new dated content** in the window (AgentCore, one entry). The value of this scan is therefore concentrated in **two closed watch items** and **three sources that had never been read**.

The four that matter:

- **The `claude-mythos-5` watch item is closed, and the answer is worse than expected.** Flagged on 2026-08-21 as "never yet reported, chase this next scan," Mythos 5 turns out to be, in Anthropic's own words, "**the same model as Claude Fable 5 but with cyber safeguards lifted**" — not a separately-trained model. Fable 5 runs three real-time safety classifiers that route sensitive queries; on Mythos 5 those classifiers are removed. Access is granted only to approved Project Glasswing customers, and the request path runs through "**your Anthropic, AWS, or Google Cloud account team**" — so the entitlement is reachable from three clouds, not one. Launch partners include AWS, Apple, Broadcom, Cisco, CrowdStrike, Google, JPMorganChase, the Linux Foundation, Microsoft, NVIDIA and Palo Alto Networks, and the Mythos 5 rollout expanded the programme to roughly **150 organizations across 15+ countries**. A model tier whose safety classifiers are absent by design invalidates the assumption that guardrail behaviour is a property of the model rather than of the deployment.

- **AgentCore Memory now ingests non-conversational JSON into long-term memory.** The August section of the AgentCore release notes grew from eleven entries to **twelve**; the new one adds a **`json` payload type to `CreateEvent`**, accepting up to **100 KB per payload** of "behavioral events, activity logs, and system events" — and critically, **JSON payloads are extracted into long-term memory** across the semantic, user-preference, summarization and episodic strategies. Blob payloads are not. So any system that can emit an event can now write durable, LLM-extracted agent memory without ever producing a conversational turn.

- **OpenAI's official Python SDK added Bedrock Runtime endpoint support (v3.2.0, Aug 17).** Last scan reported this for Codex CLI and called it a per-vendor observability break. It is now in the **SDK**, so it is not a coding-agent quirk — any application built on `openai-python` can route to Bedrock, on an endpoint that as of last scan also serves the Anthropic Messages API. The SDK release stream had not been read since v3.0.0 and four releases (v3.1.0–v3.3.1) were unexamined.

- **Devin Desktop's ACP surface is larger than the changelog line suggests.** v3.8.20 adds a setting controlling whether "terminal and user-edit activity share with ACP agents." Terminal output and pre-commit edits flowing to a third-party agent process is an endpoint egress channel, not an agent convenience.

### Microsoft Foundry — no new release content; one never-read API surface

The roll-up at `/azure/foundry/whats-new-foundry` is **unchanged** ("July 2026", `ms.date` 2026-08-12, `updated_at` 2026-08-13) and the blog has nothing after Aug 17. - **The Foundry Skills API (`{endpoint}/skills`) — preview.** A skill is a `SKILL.md` file following the [agentskills.io](https://agentskills.io) specification (YAML front matter `name` + `description`, Markdown body that "becomes the skill's injected instructions"), stored centrally through a **versioned API**. Creating a version auto-creates the parent skill; **every update creates a new immutable `SkillVersion`**, and the parent `Skill` tracks `default_version` and `latest_version`. Full CRUD plus content download as a ZIP: `POST|GET|DELETE {endpoint}/skills[/{name}[/versions[/{v}]]]`, `GET .../content`. All calls require the **`Foundry-Features: Skills=V1Preview`** header and a bearer token scoped `https://ai.azure.com/.default`; RBAC is **Foundry User** on the project. Two delivery modes: **attach to a toolbox**, where skills surface as **MCP Resources** under the SEP-2640 Skills extension so any client calling `resources/list`/`resources/read` — "GitHub Copilot, Claude Code, or your own agent harness … without any Foundry SDK" — discovers and loads them; or **download directly** into a hosted or local agent project for per-session context injection. The VS Code Toolkit ships a **prebuilt skill catalog** (`docx`, `pptx`, `xlsx`, `pdf`, `canvas-design`, `algorithmic-art`, `brand-guidelines`, `theme-factory`, `doc-coauthoring`, `internal-comms`, `slack-gif-creator`). Limitations worth recording: **the Skills API is not reachable over a private endpoint**, so a Foundry resource with public network access disabled cannot use skills at all; and `azd ai skill create --force` **deletes the existing skill and all of its versions** before uploading. Microsoft's own caution: "Customers are responsible for understanding the behaviors of any skills deployed and the data handling practices of any external endpoints receiving data." Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/skills

## New Coverage Required

- **[AIRT] [HIGH] Claude Mythos 5 is Fable 5 with its cyber safeguards lifted, entitled per-organization through Anthropic, AWS *or* Google Cloud**: The watch item opened on 2026-08-21 resolves into the most consequential finding of this scan, and Anthropic states the core fact directly: Mythos 5 is "**the same model as Claude Fable 5 but with cyber safeguards lifted**." The mechanism is **classifier removal** — Fable 5 runs three real-time safety classifiers that route sensitive queries, and on Mythos 5 those classifiers are absent, which is precisely what permits unrestricted offensive security analysis for legitimate defensive work. Three consequences follow, and the first strikes at an assumption inside Zenity's own product. **Guardrail behaviour is a property of the deployment, not of the model.** Any AIRT baseline, any AIDR detection tuned to "what this model refuses," and any posture rule that infers safety posture from a model family is wrong for this tier — two entitlements to the *same weights* behave differently, and nothing but the model identifier `claude-mythos-5` distinguishes them. Refusal-based guardrail probes will silently report a pass on a model that has no guardrail to bypass. **Access is a gated, auditable, multi-cloud entitlement.** Mythos 5 "is offered only to approved customers in Project Glasswing," requires an Anthropic invitation, a **signed NDA**, and approval coordinated with the **US government** — and, critically for discovery, the documented request path is to "contact your **Anthropic, AWS, or Google Cloud account team**." So the entitlement can arrive through a hyperscaler relationship rather than a direct Anthropic contract, meaning an organization may hold classifier-free model access that never appears in its Anthropic tenant at all. Zenity must look for it on all three surfaces. The population is not hypothetical: Glasswing's launch partners are **AWS, Apple, Broadcom, Cisco, CrowdStrike, Google, JPMorganChase, the Linux Foundation, Microsoft, NVIDIA and Palo Alto Networks**, and the Mythos 5 rollout expanded the programme to roughly **150 organizations across more than 15 countries** — a meaningful share of large enterprises, several of them likely Zenity customers. **And it is the direct structural analogue of OpenAI's Daybreak Red / GPT-5.6-Cyber tier** reported 2026-08-14, where OpenAI's own evaluation showed **95%** compliance on advanced offensive prompts versus **1.5%** for the default-protected model. This is now a **cross-vendor pattern**, so Zenity should model "safeguard-lifted / cyber-capable model entitlement" once as an entity type and map it per vendor rather than treating each programme as bespoke. AIRT should build a distinct baseline for safeguard-lifted tiers and stop treating refusal as a signal on them. AISPM should discover which models an organization is actually entitled to across Anthropic, Bedrock and Vertex/Gemini, treat `claude-mythos-5` and the GPT-5.x-Cyber tiers as privileged entitlements requiring named ownership and written justification, and flag any agent, API key or workspace configured against one. Note the discovery hazard that caused this to be missed for months: **Mythos 5 appears in ordinary model-availability lists alongside Fable 5, Opus 5 and Sonnet 5**, so it reads as one more model rather than as a control-stripped tier. Source: https://www.anthropic.com/claude/mythos

- **[AIDR] [MEDIUM] AgentCore Memory now extracts non-conversational JSON — activity logs and system events become durable agent memory**: `CreateEvent` accepts a new **`json` payload type** carrying "non-conversational, JSON-formatted data—such as behavioral events, activity logs, or system events—**up to 100 KB for each payload**," and the API reference is explicit about the consequence: "**Conversational and JSON payloads are extracted into long-term memory. Blob payloads are stored in short-term memory only and are not extracted.**" JSON payloads run through the **semantic, user-preference, summarization and episodic** strategies. This is an extension of an existing API rather than a new service, but it changes the shape of the memory-poisoning problem in three specific ways. **The write path no longer requires a conversation.** Until now, durable agent memory grew from turns — something a user or an agent said. Now any system that can emit a `CreateEvent` writes memory directly, so the set of principals able to influence what an agent believes expands from conversational participants to every telemetry producer wired into the memory store — and the natural implementations here (activity logs, behavioural event streams, system events) are exactly the sources nobody classifies as attacker-influenceable. **It is machine-scale.** 100 KB per payload of structured data, streamed continuously, is a far higher-bandwidth channel into LLM-driven extraction than conversational turns, and extraction is the step where stored content becomes agent belief. **And the blob/JSON asymmetry is the detection rule.** A blob is inert — short-term only, never extracted; a JSON payload of the same bytes is extracted into long-term memory and will shape future sessions. So the payload *type* field is what determines whether stored data can influence the agent later, and it is the field a detection must key on rather than the payload size or source. AIDR should treat `CreateEvent` with a `json` payload as a distinct activity type from a conversational one, record the emitting principal rather than only the `actorId`, and monitor volume and provenance — a spike in JSON events from a non-conversational source is memory growth no human authored. AISPM should enumerate which memory stores accept JSON payloads, resolve which identities hold `CreateEvent` permission on each, and flag stores whose write population is broader than their conversational population; a memory store fed by system telemetry and shared across agents is a cross-agent influence channel. AIRT should test whether crafted values inside a JSON activity-log payload survive extraction into long-term memory and steer a later session. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/short-term-create-event.html

AISPM should enumerate skills and versions through `/skills`, record `default_version` versus `latest_version` and which references are pinned, read skill bodies as privilege-shaping instruction content, and reconcile Foundry-registered skills against skills observed loading in external MCP clients; AIRT should treat skill content as a persistent injection vector and specifically test whether a default-version promotion changes agent behaviour with no agent-side change. **Note: this is a coverage-gap recovery, not new platform movement** — the page carries `ms.date` 2026-08-05. - **[ENDPOINT] [MEDIUM] Devin Desktop shares terminal output and pre-commit edits with third-party ACP agent subprocesses**: Devin Desktop **v3.8.20 (Aug 21)** adds settings that "control whether **terminal and user-edit activity share with ACP agents**." What is new is the *control*, and the control is what makes the underlying flow legible — but the receiving side is the finding. **Agent Client Protocol is JSON-RPC 2.0 over stdin/stdout, and the editor launches the agent as a subprocess**, so an ACP agent is a local process with a live feed from the IDE. Devin Desktop supports **Codex, Claude Agent, OpenCode and any other ACP-compatible agent, "including agents built by your team in-house,"** and those third-party agents appear in the Kanban view **alongside** Devin, **share the Spaces context layer**, and "operate with the same controls as native sessions" — i.e. they are peers of the first-party agent, not sandboxed guests. Two data classes are therefore leaving the endpoint to a party the vendor does not operate. **Terminal output** is among the highest-value content on a developer machine: it routinely carries environment variables, connection strings, tokens echoed by CLI tools, and the contents of failed authentication attempts. **User-edit activity** is a live stream of proprietary source *before* it reaches version control, so it bypasses every control anchored to the SCM. Because ACP is an open protocol and in-house agents are explicitly supported, the destination is not enumerable from the vendor's surface — the setting's state on a given machine is the only local evidence that the flow is active, which makes it a required collection target rather than a nice-to-have. Two adjacent v3.8.20 items sharpen the scope picture: **workspace trust prompts now appear when needed to activate local agents**, confirming that local agent activation is gated on a per-workspace trust decision a developer makes unilaterally and that Zenity can read as a posture signal; and **multi-root workspaces with virtual filesystem folders** widen what one agent session can see, since a virtual root can compose directories that no single project boundary contains. Reported despite Windsurf's watching tier because this is an endpoint egress channel, not an agent convenience. ENDPOINT should detect the ACP sharing setting's state per install, enumerate attached ACP agents and resolve who operates each, treat enabled terminal-sharing on a machine holding production credentials as a high-risk condition, and inventory per-workspace trust decisions and multi-root workspace composition as agent scope attributes. Source: https://docs.devin.ai/desktop/acp

- **[AIDR] [MEDIUM] OpenAI's official Python SDK now supports the Bedrock Runtime endpoint — the cross-provider observability break is no longer confined to Codex CLI**: `openai-python` **v3.2.0 (Aug 17)** adds "**Bedrock Runtime endpoint support (SDK-290)**." On 2026-08-21 this monitor reported the same capability arriving in **Codex CLI 0.148.0** and framed it as a coding-agent quirk that compounded two known blind spots. Its arrival in the **SDK** changes the scope of that finding materially: it is no longer a property of one client that developers choose to install, but of **the library any application uses to call OpenAI**, so cross-provider routing is now available to arbitrary production workloads rather than to interactive coding sessions. The compounding facts are unchanged and worth restating because they now apply far more broadly.
