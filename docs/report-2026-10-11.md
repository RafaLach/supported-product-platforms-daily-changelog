## Platform Details

### Claude Enterprise (Anthropic)

- **Dynamic workflows and `workflow_run` as a resource type** (2026-10-09, beta,
  `managed-agents-2026-04-01`). The agent writes a *workflow* — a program that runs many agents in
  phases and combines their results — and the Anthropic server executes it in the background as a
  **workflow run**. Turned on with `multiagent: {"type": "multiagent_20261001", "workflows":
  {"type": "enabled"}}`. New `workflow_run.*` event family: `workflow_run.created`,
  `workflow_run.status_running`, `workflow_run.phase_started`, `workflow_run.status_ended`.
  Source: https://platform.claude.com/docs/en/managed-agents/workflow-runs
- **No start and no stop API for a run.** "Only the agent starts a run. No event you send ends one;
  archiving the session can." To stop one, Anthropic's documented procedure is to "send a
  `user.message` asking the agent to stop its runs." Run threads are **exempt from the session's
  child-thread limit**. Source: https://platform.claude.com/docs/en/managed-agents/workflow-runs
- **Inline agents are enabled by default** under both `subagents` and `workflows` — the agent (or a
  workflow it wrote) defines agents itself and writes their system prompts. `predefined_agents` is
  empty by default on both lists. "You can't limit an inline agent" to specific MCP servers.
  Source: https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration#predefined-and-inline-agents
- **Self-hosted sandbox environments** — `{"config": {"type": "self_hosted"}}` on
  `POST /v1/environments` turns the environment into a work queue served by a customer-run
  **environment worker**, authenticated by a new credential type, the **environment key**
  (`ANTHROPIC_ENVIRONMENT_KEY`, Console-only issuance). Tool execution, files and egress move to
  customer infrastructure; orchestration stays with Anthropic.
  Source: https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes
- **`read_only` memory stores are not read-only inside a self-hosted sandbox.** "A store attached
  with `read_only` access is protected from upload, not from local modification." The agent's `bash`
  tool, custom tools, and sandbox-served MCP servers can all rewrite the local copy at
  `/mnt/memory/`, and later tool calls in that session read the changed copy.
  Source: https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-security
- **`auto` permission policy — server-side per-call evaluation.** A third policy type alongside
  `always_allow` / `always_ask`: the server evaluates each tool call against the tool, its input and
  the session's content so far, and allows, denies, or pauses it. Emits
  `evaluated_permission` with `reason_code` values (`high_risk`, `indeterminate`). Denials cannot be
  overridden by the client. **The agent toolset still defaults to `always_allow`.**
  Source: https://platform.claude.com/docs/en/managed-agents/permission-policies
- **`advisor` setting formalized in the `multiagent` block** — `{"type": "enabled", "model": "..."}`,
  disabled by default. This is the configuration surface for the server-side advisor model already
  reported on 2026-09-17; noted here for completeness, not re-reported.
- *Held below the reporting bar:* Compliance API can now download Claude Docs documents as Word
  files (2026-10-08) — an export format on an already-reported endpoint expansion. Also held:
  Anthropic Cyber Mission and 2026 Usage Policy update (2026-10-08) — policy, not surface.

## New Coverage Required

- **[AISPM] [HIGH] Anthropic Managed Agents dynamic workflows and workflow runs**: An agent can now author a *program* that the Anthropic server executes in the background, spawning an unbounded set of agent threads across phases. Enabled with `multiagent: {"type": "multiagent_20261001", "workflows": {"type": "enabled"}}` — and with that type, **`workflows` and `subagents` are both on by default**. This introduces a new inventory entity, the **workflow run** (states running / idle / ended; `result` types `completed`, `stopped`, `program_error`, `thread_limit_error`, `timeout_error`), plus the run's **phases** and its per-agent **session threads**, which are explicitly *exempt from the session's child-thread limit*. The run is started by model judgment from the text of a `user.message`, with no API call, and Anthropic states that permission policies "apply to the tools that a run's agents call, not to starting the run" — so no approval gate exists on the run itself. AISPM must inventory `multiagent` configuration per agent, enumerate open workflow runs, and flag `multiagent_20261001` agents whose `workflows` setting was never explicitly disabled, since `null` reads as enabled. Source: https://platform.claude.com/docs/en/managed-agents/workflow-runs

- **[AIRT] [HIGH] Inline agents are enabled by default — the agent writes its own subagents' system prompts**: Under `multiagent_20261001`, both `subagents.inline_agents` and `workflows.inline_agents` default to enabled while `subagents.predefined_agents` and `workflows.predefined_agents` are both **empty by default**. The practical result is that an agent — or a workflow program the agent wrote — defines agents at runtime and authors a system prompt for each, with no operator-reviewed definition anywhere. Anthropic states plainly that "you can't limit an inline agent" to a declared set of MCP servers; the only scoping available is setting `inline_agents` to `{"type": "disabled"}` under *both* settings and listing at least one predefined agent in each. This is a prompt-injection amplifier: content the primary agent read can determine both the existence and the instructions of agents that then run tools. AIRT needs inline-agent definition as an injection target, and AISPM needs "inline agents enabled with an empty predefined list" as a toxic-combination rule. Source: https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration#predefined-and-inline-agents

- **[AISPM] [HIGH] Self-hosted sandbox environments, environment workers and environment keys**: `POST /v1/environments` with `{"config": {"type": "self_hosted"}}` creates an environment that acts as a **work queue** rather than an Anthropic-run sandbox. A customer-operated **environment worker** (shipped in the `ant` CLI and the Python/TypeScript/Go SDKs, with vendor builds from AWS Lambda MicroVMs, Cloudflare, Daytona, E2B, Fly.io, GKE Agent Sandbox, Modal, Namespace, Superserve, Vercel and Blaxel) claims work items and executes every tool call on customer infrastructure. Three new things to inventory: the `self_hosted` environment, the worker fleet (`workers_polling` is readable via `ant beta:environments:work stats`), and a **new credential type — the environment key** (`ANTHROPIC_ENVIRONMENT_KEY`, issuable only in the Console even for API-created environments), plus a per-work-item `secret` that is the only credential accepted by the memory-store endpoints. Anthropic states its security boundary stops at the sandbox: "Anthropic does not inspect your sandbox image or runtime," egress is entirely the customer's VPC policy, and "once session content reaches your worker, it is outside Anthropic's data lifecycle controls." On Claude Platform on AWS the worker instead authenticates with SigV4 under the `AnthropicSelfHostedEnvironmentAccess` managed policy — an IAM principal that must be inventoried as an agent-execution identity. Source: https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes

- **[AIRT] [MEDIUM] `read_only` memory stores are writable from inside a self-hosted sandbox**: Anthropic documents that a memory store attached with `read_only` access "is protected from upload, not from local modification." The worker's `write` and `edit` tools refuse it and the memory-store endpoints reject writes made with the session `secret` — but the agent's own `bash` tool, any custom tool, and any MCP server served from the sandbox run with the worker's permissions and can rewrite the local copy under `/mnt/memory/`. Later tool calls in that session then read the modified copy. The documented mitigation is to disable `bash` entirely and grant no filesystem-writing custom tool. This is a self-poisoning path for agent memory that leaves no trace in the authoritative store, and it sits directly alongside the AgentCore `IngestData` silent-memory-write gap. AIRT should treat in-session mutation of a nominally read-only memory store as a test case; AISPM should flag any agent that holds both a `read_only` memory store and an enabled `bash` tool. Source: https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-security

- **[AIDR] [MEDIUM] `auto` permission policy — a server-side per-call tool evaluator emitting a new decision record**: A third permission policy type joins `always_allow` and `always_ask`. Under `auto`, Anthropic's server evaluates every server-executed tool call against the tool, the call's input, and the session's content up to that point, then allows it, pauses it for approval, or denies it outright — and "your client cannot override the denial" (a `user.tool_confirmation` against a denied call returns 400). Each decision lands on the session event stream as an `evaluated_permission` with a machine-readable `reason_code` (`high_risk`, `indeterminate`), which Anthropic explicitly describes as "a value for your client to branch on and keep in audit records." That is a new, high-fidelity detection surface AIDR should ingest as an activity type: server-side risk verdicts on individual agent tool calls, including denials the customer never saw requested. The inventory half matters too — **the agent toolset still defaults to `always_allow`** while MCP toolsets default to `always_ask`, so any agent left on defaults runs its built-in tools, including `bash`, with no evaluation at all. Source: https://platform.claude.com/docs/en/managed-agents/permission-policies
