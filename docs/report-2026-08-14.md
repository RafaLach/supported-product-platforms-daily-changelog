## Executive Summary

**This scan covers a 4-day gap** — the previous run was 2026-08-10 — and unlike that scan, this one is driven by **live changelog movement rather than backlog recovery**. Five of the six platforms below moved on their own dated release streams within the window. Sixteen findings, four of them on surfaces that did not exist the last time this monitor ran.

The three most consequential:

- **Anthropic put local agent sessions behind a compliance API (Aug 11).** The Compliance API now returns **transcripts of Cowork and Claude Code sessions running on users' own machines** — three new endpoints, reusing the existing Compliance Access Key with no new scope or client update. Transcripts include tool calls and tool results, with MCP tool calls normalized into the same shape. This is simultaneously the single best AIDR ingestion surface Anthropic has shipped and a map of its own blind spots: Claude Code routed through **Bedrock, Google Cloud or Microsoft Foundry is not captured at all**, nor is Claude Code on the web, nor anything in HIPAA-readiness or ZDR organizations.

- **Microsoft Foundry agents can now be called by other agents (Aug 12–13).** `enable-agent-to-agent-endpoint` is the freshest document in this entire scan. A Foundry agent can be exposed as an **A2A server** with a published, discoverable agent card — and Foundry **serves A2A v0.3 by default when a caller doesn't specify a version**, so the effective protocol on an endpoint is not determined by its configuration. Alongside it, the Foundry what's-new roll-up **finally advanced from June to July** after being frozen across two prior scans, surfacing four more new surfaces including **managed MCP servers powered by connector namespaces** — over 1,000 catalog connectors, each auto-provisioned as a Foundry-hosted MCP server whose actual endpoint lives on `logic.azure.com`.

- **OpenAI shipped a general-purpose desktop activity recorder and an offensive-security model tier (Aug 10–13).** **Computer History** turns everything a user does across every Mac app and website — clicks, typing, keyboard shortcuts, app switching, via macOS accessibility APIs — into memories, and does it by **periodically starting an ephemeral Codex session with access to the raw interaction-event stream**. Separately, **Daybreak Red** grants access to **GPT-5.6-Cyber**, which by OpenAI's own published evaluation answers **95% of advanced exploit-development prompts against 1.5% for the standard model**.

**Also new**: Amazon's **`bedrock-mantle`** endpoint — a second, parallel Bedrock inference surface serving the OpenAI Responses, OpenAI Chat Completions and Anthropic Messages APIs with built-in tool use and stateful conversations, which AWS now recommends over `bedrock-runtime` for new applications and which has never appeared in this monitor. Google shipped **Gemini Enterprise Skills** (shareable packages containing a `SKILL.md` plus **scripts and files**) and took the **GitHub connector to GA with write actions** including merge-pull-request and push-file. ServiceNow's AI Control Tower reached **Australia Patch 4** with an agent map covering MCP servers and cross-cloud providers.

**Nothing new above the bar on**: Amazon Bedrock AgentCore (two new August entries, but a quota consolidation and a region expansion), Amazon Q (frozen — Q Business closed to new customers, Q Developer's doc history unmoved for ~3 months), Microsoft Copilot Studio (still June 2026), Microsoft Copilot M365, Power Apps / Automate / Pages, Salesforce, Cursor, Windsurf (Devin Desktop), Perplexity, Dia.

**Held below the bar this scan**: Cursor Cloud Agents **builds** (cached environment snapshots — a performance optimization, though a build is a new artifact if Cloud Agents ever enter inventory scope); Devin Desktop v3.7.16's **sanitized-transcript share links** and **permission-rule deny-precedence model** (both worth remembering if Devin Desktop enters ENDPOINT scope); Perplexity's four new Agent API models; AgentCore's GovCloud and Ireland/Tokyo expansions; Gemini Omni Flash and Gemini 3.7 Flash; OpenAI Python SDK v3.0.0's HTTPX2 migration; Foundry's WebSocket mode and `azure.yaml` authoring; Azure Content Understanding's GPT-5 support.

**Held items carried forward.** OpenAI **`gpt-realtime-2.1` / `-mini`** is absent for a fifth consecutive scan (open since ~2026-07-06). Salesforce **Winter '27** release notes are still unpublished — Salesforce is expected to post them **August 19**, with sandbox preview **August 28** and Dreamforce **September 12–14**, so a large Agentforce delta should be expected on the next two scans. **Dia** is unreadable for a fourth consecutive scan.

**Source-config debt: nine outstanding fixes, unchanged.** Of the 16 findings below, **two** came from a URL as configured in `sources.json` (the Bedrock and ServiceNow family pages) — and the ServiceNow one only because the per-application page was reached from it. ### Microsoft Foundry — roll-up unfroze; five new agent-platform surfaces

The `whats-new-foundry` roll-up is now titled **"What's new for July 2026"** (ms.date 2026-08-12, updated_at 2026-08-13), having been stuck on "June 2026" for the two prior scans. The `sources.json` Foundry URL still resolves to the frozen *classic* Azure OpenAI page.

- **Enable incoming A2A on a Foundry agent (preview)** — ms.date 2026-08-12, updated 2026-08-13, the freshest item in this scan. Exposes an agent **as** an A2A server; this monitor had previously only covered the outgoing direction. Enabled by a single PATCH setting `agent_card` plus `agent_endpoint.protocol_configuration.a2a`; **not available in the Foundry portal**, REST/SDK only. Serves **both A2A v1.0 and v0.3 on the same base path**, with version chosen by agent-card discovery, the `A2A-Version` header, or `?a2a-version=` — and **v0.3 is served by default when unspecified**. Cards are published at `…/protocols/a2a/agentCard/v1.0` and `…/agentCard/v0.3`, carrying description, version and a **`skills[]`** array. All A2A URLs require Entra ID auth (**anonymous agent-card access is not supported**) and the caller needs **Foundry Agent Consumer** or higher. Callers authenticate either **on-behalf-of the end user** or with a **service identity**. v1.0 is JSONRPC-only; text modality only; no streaming. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/enable-agent-to-agent-endpoint
- **Managed MCP servers powered by connector namespaces (preview)** — ms.date 2026-07-28. The Foundry Tools Catalog carries **over 1,000 connectors**; adding one makes Foundry provision a **managed MCP server**. Every Foundry account has a **Connector Namespace** hosting connector runtimes and MCP servers, with **each project mapped to an environment** in it. Only selected connector *actions* become tools; triggers are unsupported. Auth is **OAuth2 with a one-time per-end-user consent** minted via `listConsentLinks`. The project connection is `authType: OAuth2`, `category: RemoteTool`, `metadata.type = gateway_connector`; `target` begins as the literal `https://placeholder` and is rewritten to a **`logic.azure.com/api/connectorGateways/…/mcp` gateway URL**. Four publisher tiers with explicitly different data responsibility, down to **independent publishers at a "lower certification bar"**. Critically: **only validated connectors are gated in the portal — the REST/SDK/`azd` path has no gating at all.** Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/connectors
- **Restrict access to sensitive content in Foundry traces (preview)** — ms.date 2026-07-21. Seven OpenTelemetry gen-AI attributes are classed as sensitive — `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, **`gen_ai.tool.definitions`**, **`gen_ai.tool.call.arguments`**, **`gen_ai.tool.call.result`**, `gen_ai.evaluation.explanation` — and routed to a dedicated **`AppGenAIContent`** Log Analytics table that can be set Protected, readable only by the **Privileged Monitoring Data Reader** role. **From September 30, 2026 these values stop being written to `AppDependencies`/`AppTraces`/`AppEvents`**, leaving only a pointer. Source: https://learn.microsoft.com/en-us/azure/foundry/observability/how-to/traces-sensitive-content
- **Microsoft Foundry Canvas (preview)** — ms.date 2026-07-21. A **GitHub Copilot App extension** (Settings > Plugins > `microsoft-foundry`) that designs, configures, tests and deploys Foundry **hosted agents** from an editor side panel. Signs in to Azure, enumerates subscriptions and projects, browses the project's deployed models, **toolboxes, tools, skills and guardrails**, runs the agent locally in an embedded **Agent Inspector**, and publishes with **Deploy to Foundry** — both backed by `azd` commands. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/foundry-canvas
- **Microsoft Foundry Notification Center** — ms.date 2026-07-09. In-portal aggregated alert feed spanning **Microsoft Defender for Cloud security alerts** (malicious activity, content-safety violations), **Azure Policy and Foundry guardrail compliance violations**, and run completion/failure events. Source: https://learn.microsoft.com/en-us/azure/foundry/concepts/concept-notification-center

## New Coverage Required

- **[AIDR] [HIGH] Anthropic Compliance API now exposes transcripts of Cowork and Claude Code sessions running on employee laptops**: Three new endpoints — `GET /v1/compliance/apps/sessions/local`, `.../local/{session_id}`, and `.../local/{session_id}/messages` — return the full conversation of agent sessions that execute **on users' own machines**, for Claude Enterprise organizations. Transcripts carry user prompts, assistant text, and **`tool_use` and `tool_result` blocks, with MCP tool calls and most server tool calls normalized into those same shapes**, so an agent's actual tool invocations and their returned data are readable. `product_surface` distinguishes `cowork` from `claude_code`, `CLAUDE.md` project instructions appear as ordinary user content, and skill content appears when the client sends it. This is the richest AIDR ingestion surface Anthropic has published and it requires **no new credential** — it reuses the same Compliance Access Key and `read:compliance_user_data` scope Zenity may already hold, and no client-side deployment. Two things demand equal attention. First, **the documented blind spots are a coverage map in themselves**: Claude Code authenticated with a Console API key or routed through **Amazon Bedrock, Google Cloud or Microsoft Foundry** is not captured, nor is Claude Code on the web, nor anything in organizations with **HIPAA readiness** or under **ZDR**, and under **CMEK** sessions list but their content is withheld — so an enterprise can believe it has full local-agent visibility while its Bedrock-routed developers are entirely invisible. Second, **what is deliberately omitted from every transcript matters for detection**: thinking blocks, the system prompt, and — most significantly — **tool definitions and MCP server configuration**, meaning a transcript shows that a tool was called but never what that tool was permitted to do or which MCP server backed it. AIDR should ingest local sessions as a first-class agent-activity stream keyed on `product_surface`, join `user.id` to identity, and treat the excluded populations as explicit gaps to close by other means; AISPM should discover whether HIPAA/ZDR/CMEK settings are suppressing capture, since each silently disables it. Source: https://platform.claude.com/docs/en/manage-claude/compliance-sessions#retrieve-local-sessions

- **[AISPM] [HIGH] Microsoft Foundry agents can now be published as callable A2A servers with discoverable agent cards**: Foundry has added **incoming A2A** — the ability to expose an agent **as** an Agent2Agent endpoint that other agents discover and call — updated two days before this scan and the freshest change in it. Every prompt agent supports it by default, and enabling it takes a single PATCH that sets `agent_card` and adds `a2a` to `protocol_configuration`; it is **not exposed in the Foundry portal at all**, so it can only be turned on via REST or SDK and will be invisible to anyone auditing through the UI. The agent then publishes cards at `…/protocols/a2a/agentCard/v1.0` and `…/agentCard/v0.3` advertising its description and a **`skills[]` capability list** to any authorized caller. The finding Zenity most needs is the **version-negotiation default**: Foundry serves **both v1.0 and v0.3 on the same base path**, and **when a caller specifies no version, it serves v0.3** — so the protocol actually spoken on an endpoint is chosen by the *caller*, not by the endpoint's configuration, and an inventory that records "A2A v1.0" from the configuration will be wrong for any client that doesn't negotiate. The authorization model is the second half: all A2A URLs require Entra ID (**anonymous agent-card access is explicitly unsupported**, which is a genuine control worth verifying rather than assuming), callers need only **Foundry Agent Consumer** on the hosting project, and they may authenticate either **on-behalf-of an end user** or **with a service identity** — the latter meaning an agent-to-agent call chain with no human in it and no user context to scope against. AISPM should discover which agents have `a2a` in their `protocol_configuration`, inventory each published `agent_card` and its `skills[]` as the agent's advertised attack surface, enumerate every principal holding Foundry Agent Consumer as a potential caller, and flag agents reachable by service identity. AIRT should treat a published agent card as a discovery primitive and test whether inbound A2A content is handled as trusted instruction. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/enable-agent-to-agent-endpoint

- **[AISPM] [HIGH] Microsoft Foundry connector namespaces turn 1,000+ SaaS connectors into auto-provisioned managed MCP servers hosted on logic.azure.com**: Adding any connector from the Foundry Tools Catalog now causes Foundry to provision a **managed MCP server** on the customer's behalf. Every Foundry account has a **Connector Namespace** — a managed service hosting connector runtimes and MCP servers — with **each project mapped to its own environment** inside it, and the namespace owns server hosting, tool definitions, authentication, credential management and lifecycle. Three properties make this a first-order inventory problem. First, **scale and provenance**: over 1,000 connectors span four publisher tiers with explicitly different data-handling — Microsoft internal (SharePoint, Teams, Dynamics 365), Microsoft external (GitHub), verified third-party (Docusign, Databricks, Box), and **independent publishers at what Microsoft calls a "lower certification bar"** — so the publisher tier of each attached connector is a posture signal, and Microsoft's own page warns that auth keys and prompt content may be passed to third-party tools and that "MCP implementations are vulnerable to attacks, cascading failures, and loss of human oversight." Second, **the endpoint is not where you would look for it**: the connection's `target` is rewritten from a literal `https://placeholder` to a **`logic.azure.com/api/connectorGateways/<envId>/mcpServerConfigs/<name>/mcp`** URL, so the real MCP endpoint lives on Logic Apps infrastructure, not on the Foundry project endpoint, and the connection is identifiable by `metadata.type = gateway_connector` with `category: RemoteTool`. Third, **the portal's safety rail does not exist in code**: only *validated* connectors surface the managed-MCP experience in the portal, but the docs state plainly that via REST, SDK or `azd` **"there's no gating — you can use any connector in the catalog."** Add that each end user must complete a **per-user OAuth consent**, so the effective reach of a tool is the union of every consenting user's permissions in the target SaaS. AISPM should enumerate project connections of type `gateway_connector`, resolve each to its connector, publisher tier and **registered operation list** (`mcpserverConfigProperties`), record the logic.azure.com gateway target as an inventory endpoint, flag connectors added through the code-first path that would not have passed portal validation, and treat write-capable operations as privileged. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/connectors

- **[ENDPOINT] [HIGH] OpenAI Computer History records everything a user does on macOS and feeds it to an ephemeral Codex agent**: ChatGPT's macOS desktop app has shipped an opt-in feature that converts **activity across all apps and websites** into memories and a timeline usable by ChatGPT and Codex. It records interaction events exposed through **macOS accessibility APIs** — clicks, typing, keyboard shortcuts, and app switching — which means keystrokes and UI interactions inside applications that have nothing to do with ChatGPT, including other security tools, terminals, password managers and internal business systems. The architecture is the finding: events are buffered on the Mac for up to 48 hours, and Computer History then **periodically starts an ephemeral Codex session with access to the raw interaction-event stream** to summarize it into memories; those temporary event files are **processed on OpenAI's servers** before the resulting **plain-text memory files are written back to local disk**, where they persist until deleted. So a general-purpose agent session is granted a feed of the user's entire desktop activity, and a durable plain-text derivative of it sits on the endpoint. It replaces the Chronicle preview and is a genuine rebuild — Chronicle captured screenshots, this does not, and it also excludes screen recordings, microphone and system audio — but the accessibility-event stream is arguably more sensitive than screenshots because it captures typed content directly. Governance hooks exist and should be inventoried: it is **off by default**, Pro users may self-enable, and **Business and Enterprise workspaces require an administrator to grant access before any member can turn it on**; users choose which apps and websites contribute and can pause collection from the menu bar; it is unavailable in the EEA, Switzerland and the UK. ENDPOINT should detect the ChatGPT macOS app's Computer History state per device, inventory the local memory files as a sensitive on-disk artifact, and alert when it is enabled on endpoints with access to regulated systems; AISPM should track the workspace-level admin grant as a tenant control; AIRT should consider whether content typed in one application can shape agent behaviour in another through the resulting memories. Source: https://learn.chatgpt.com/docs/customization/computer-history

- **[AIRT] [HIGH] OpenAI Daybreak Red grants access to GPT-5.6-Cyber, a model that answers 95% of exploit-development prompts**: OpenAI has added two tiers to its Daybreak "Trusted Access for Cyber" program. **Daybreak Blue** covers approved defensive workflows — secure code review, vulnerability triage, detection engineering, incident response, malware analysis, patch validation — on GPT-5.6 Sol with system-level safeguards. **Daybreak Red** goes further, covering advanced defensive **and offensive** cyber tasks with access to the purpose-trained **GPT-5.5-Cyber and GPT-5.6-Cyber** models for vulnerability research, exploit validation and security testing. The number that matters for Zenity is OpenAI's own published evaluation: **GPT-5.6-Cyber handled 95% of advanced cybersecurity prompts** spanning exploit-chain development, authentication bypass and privilege escalation, **while GPT-5.6 Sol with default protections answered 1.5%**. That is an explicit, vendor-documented ~63x differential in offensive capability gated only by program membership, and it changes the threat model in both directions. Defensively, a tenant where some identity holds Daybreak Red access has a materially different risk profile from one that does not, and that entitlement is a posture attribute Zenity should be able to discover and attest — including which users or service accounts hold it and whether their use is logged. Offensively, this is directly relevant to AIRT's own mandate: the capability differential defines a realistic upper bound for what an attacker with a compromised Red-tier credential could do against a customer's agents and infrastructure, and it makes the Daybreak entitlement itself a high-value credential worth protecting like any other. AIRT should incorporate the Blue/Red capability distinction into red-team scenario design and use the published differential to calibrate assumed adversary capability; AISPM should inventory Daybreak tier membership as a privileged entitlement on the OpenAI organization alongside admin roles. Source: https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview

- **[AISPM] [HIGH] Amazon Bedrock has a second inference endpoint — `bedrock-mantle` — serving OpenAI and Anthropic APIs with stateful conversations, and AWS now recommends it over `bedrock-runtime`**: `bedrock-mantle.<region>.api.aws`, powered by "Project Mantle", is a distributed inference engine running in parallel to `bedrock-runtime` and serving three API shapes Zenity's Bedrock coverage was not built for: the **OpenAI Responses API**, the **OpenAI Chat Completions API**, and the **Anthropic Messages API**. It adds **built-in tool use and stateful conversation management**, and AWS's stated migration pitch is that an existing OpenAI SDK codebase moves onto Bedrock by changing only the base URL and API key. AWS **recommends bedrock-mantle for new applications**, which means new Bedrock workloads will default onto it. This is a coverage gap rather than a fresh launch — it surfaced only because an August 11 cost-allocation note named it, but PrivateLink support for these endpoints landed in February 2026 and dedicated CloudWatch metrics and a redesigned console in June 2026, so the surface has been building for roughly six months while every scan looked at `bedrock-runtime` and the Agents APIs. Three consequences follow.
