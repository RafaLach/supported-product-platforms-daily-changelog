## New Coverage Required

- **[AISPM] [HIGH] Copilot Studio Copilot node — a workflow step that delegates a whole Cowork task while running as a named Microsoft 365 user**: A new (preview) workflow node lets any Copilot Studio workflow call **Copilot Chat** or **start/resume a Cowork task**. Two properties make this a first-class inventory requirement. First, **identity**: the node runs under a stored Microsoft 365 **connection**, and Microsoft's own documentation states plainly that "whatever that user can see in Microsoft 365, the workflow can use" — the node grounds in that user's mail, files, calendar and chats. A workflow built by one maker can therefore be configured against a different, more privileged user's connection, and every downstream step inherits that reach. Second, **delegation depth**: through Chat the node can target Microsoft-built agents (**Researcher**, **Analyst**) or any agent the tenant published in **Agent Builder**, each carrying its own instructions, knowledge and tools; through Cowork it can start a long-running, multi-app task or **resume an existing Cowork task by ID**, meaning a workflow can inject instructions into work already in flight. AISPM must inventory Copilot nodes, resolve the connection identity each one runs as, enumerate the agents reachable from the Agent dropdown, and flag workflows whose connection account is more privileged than the workflow's maker. AIDR needs Cowork task start/resume as a distinct activity type, since the resuming caller is a workflow rather than the task's original owner. Source: https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/microsoft-365-copilot-node-workflow

- **[AISPM] [HIGH] Copilot Studio Dataverse tables as a knowledge source, with unstructured reasoning over Multiline Text and File columns**: Agents can now be grounded directly in Dataverse, up to 15 tables per knowledge source. The security-relevant part is the preview that extends retrieval **beyond structured columns into `MemoType` (Multiline Text) and `FileType` (File) columns** — so case notes, free-text descriptions and **attached documents** become agent-answerable. This is a new class of data flow: the business records Zenity already treats as structured suddenly expose their unstructured payload to an LLM. The enabling act is a **Power Apps change, not a Copilot Studio change** — a maker or admin marks those columns `Searchable` and adds them to the table's **Quick Find View** — so the posture change happens on a surface outside the agent's own configuration and will not show up in an agent-only inventory. Microsoft notes retrieval may backfill for up to two days after that view edit, meaning exposure can begin without any agent being touched. The source does require `Authenticate with Microsoft` (so Dataverse security roles are enforced at retrieval), which makes the agent's authentication mode a posture signal worth asserting. AISPM should inventory Dataverse knowledge sources, the specific tables bound to each, whether unstructured column reasoning is on, and which Multiline Text/File columns are marked searchable. Source: https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/knowledge-add-dataverse-tables

- **[AIRT] [HIGH] Codex Guardian / auto-review — an agent reviewer that replaces human approval at the sandbox boundary**: Codex now supports `approvals_reviewer = "guardian_subagent"`, under which a **reviewer subagent intercepts approval requests that would otherwise require human confirmation** for shell execution, file writes, network access and MCP tool invocations, and approves or denies them against a risk policy. Codex CLI 0.160.0 (2026-10-01) extended it with two opt-in capabilities: the Guardian can now **retrieve earlier user instructions** and **receive context selected from agent handoffs** — both disabled by default. The policy itself is customizable **per enterprise** via `guardian_policy_config` and **per user** via a local `[auto_review].policy`, and the upstream repository carries open issues reporting that `auto_review.policy` can *silently replace* the catalog security policy and that `auto_review.extra_policy` is silently omitted under the current catalog template. The result is a security control whose effective policy is not reliably what the administrator configured, deciding privileged operations with no human in the loop — and now reading prior user instructions as input, which is precisely the channel an indirect prompt injection would use to talk the reviewer into an approval. AIRT should build injection scenarios targeting the Guardian's context inputs (handoff context, retrieved user instructions) rather than only the primary agent; ENDPOINT must detect Codex installations where `approvals_reviewer` is set to the Guardian subagent and capture the effective policy, not the configured one. Source: https://learn.chatgpt.com/docs/sandboxing/auto-review

- **[AISPM] [HIGH] Gemini Enterprise federated query mode — agents query AlloyDB, BigQuery, Cloud SQL and Spanner in place, over MCP, with each end user's own credentials**: Data Cloud connectors can now run in **federated query mode**, where Gemini Enterprise queries operational and analytical data **in place, without copying or ingesting it into a data store**. Each connector is backed by a **first-party MCP server**; the request is authenticated with the **end user's own IAM permissions or OAuth 2.1 credentials**, and the agent formulates SQL and invokes the connector's MCP tools against the live database. Attaching a connector in this mode **automatically enables Knowledge Catalog** on the app's Assistant tab, giving the root agent read-only tools to search data assets and pull back tables, schemas, business glossary terms and enriched metadata. Three things change for coverage: there is **no data store artifact to inventory** — the old "what did this agent ingest" question no longer answers "what can this agent read"; the reachable data set is now **per-user and dynamic**, so entitlement review has to be evaluated against each caller rather than the app; and **Knowledge Catalog turns on implicitly**, adding a metadata-discovery surface the admin did not explicitly enable. Preview across AlloyDB for PostgreSQL, BigQuery, Cloud SQL and Spanner. AISPM must discover federated-mode connectors, their backing MCP servers, the databases they reach and the Knowledge Catalog enablement state. Source: https://docs.cloud.google.com/gemini/enterprise/docs/connectors/connect-data-cloud

- **[AISPM] [MEDIUM] Copilot Studio extract node — model-selectable document parsing inside workflows**: A new workflow node processes invoices, contracts, receipts, bank statements, reports and financial statements across PDF, Word, Excel and PowerPoint, returning named values and tables as dynamic content for later steps. The extraction schema can be inferred from an uploaded sample document, chosen from a template, or defined by hand, and the **model powering extraction is selected by the maker** from a dropdown. For coverage this is a new data-transformation point where unstructured documents — frequently the most sensitive artifacts in a tenant — are read by an LLM and emitted as structured tokens that flow onward into Dataverse records, approvals, emails and Teams messages. The document itself arrives from a trigger (a mailbox attachment, a SharePoint library), so the node is a standing conduit from inbound untrusted files into the workflow's execution context — an indirect prompt injection path worth AIRT attention as well. AISPM should inventory extract nodes, their configured input source, selected model and output field schema. Source: https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/extract-node-workflow

- **[AISPM] [MEDIUM] Copilot Studio content safety test method — a new configurable guardrail threshold surface in agent evaluation**: Agent evaluation gained a **content safety** test method, added separately per content type across hatefulness/unfairness, sexual content, violence and self-harm. Each is configured with a **severity threshold on a 0–7 scale, where 0 is strictest and 7 is the most permissive and allows graphic or extreme content to pass**. This is a per-agent, maker-controlled safety configuration — meaning the threshold a given agent is validated against is now an inventoried posture attribute, and an agent whose content-safety tests are set to a permissive level (or absent entirely) is a measurably weaker configuration than its neighbour. Microsoft explicitly warns the evaluations "don't guarantee that an agent is safe or appropriate for every scenario." AISPM should capture the configured thresholds per agent and flag permissive or missing content-safety evaluation as a violation rule. Source: https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-overview

- **[AISPM] [MEDIUM] AgentCore Gateway private certificate authority support for targets**: AgentCore Gateway now accepts TLS server certificates signed by **private CAs** on MCP server, OpenAPI and HTTP proxy (passthrough) targets. Previously the gateway trusted only publicly-issued certificates, which in practice forced private targets behind an Application Load Balancer. An operator now registers a PEM-encoded CA certificate held in **Amazon S3 or AWS Secrets Manager** as the trust anchor, and the gateway connects **directly to private endpoints inside the customer VPC powered by Amazon VPC Lattice**. The coverage consequence is that AgentCore agents can now reach internal, non-internet-facing services with no load balancer in the path — removing the network chokepoint that previously made that egress observable, and introducing two new inventory attributes per target: the trust-anchor location (an S3 object or a Secrets Manager secret) and the VPC Lattice private endpoint it authorises. AISPM should enumerate gateway targets using a private CA and map the internal services each one reaches. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-vpc-egress.html

- **[ENDPOINT] [MEDIUM] Codex CLI MCP authentication surfaces — OAuth client secrets and WebSocket bearer tokens**: Codex CLI 0.158.0 (2026-09-28) added **OAuth client-secret support for MCP servers** and **WebSocket bearer-token authentication**, and 0.160.1 (2026-10-05) fixed preservation of Windows environment variables for remote MCP servers. Together these mean a developer's local Codex configuration now holds long-lived credentials for remote MCP servers, authenticates over WebSocket transports, and sources secrets from the Windows environment. ENDPOINT must extend Codex MCP discovery to capture the authentication method per server (OAuth client secret vs. bearer token vs. none), the transport, and whether credentials are inlined in config or drawn from environment variables. Source: https://learn.chatgpt.com/docs/changelog

- **[AISPM] [MEDIUM] OpenAI API key governance controls at organization and project level**: OpenAI added an **API Key Governance** section in platform settings (2026-09-15) letting organization and project administrators restrict which key types may be created — **service-account keys only, user-owned project keys only, or no new keys at all** — with organization-level restrictions always taking precedence over project settings, and existing keys unaffected. A companion change (2026-09-10) lets administrators enforce a **maximum API key lifetime**, requiring new keys to expire within a configured limit. These are new tenant posture attributes on a primary-tier platform: an organization permitting user-owned keys with no lifetime cap is materially weaker than one restricted to expiring service-account keys, and the "existing keys unaffected" carve-out means a restriction can be in force while long-lived legacy keys remain valid behind it. AISPM should read the governance setting at both levels and flag organizations with unrestricted or unexpiring key issuance. Source: https://developers.openai.com/api/docs/guides/production-best-practices

- **[AISPM] [MEDIUM] Gemini Enterprise resource-level IAM for apps and data stores**: Administrators can now grant **Gemini Enterprise Admin, Viewer or User roles on an individual app or data store** rather than across the whole Google Cloud project, and can build custom project-level roles for restricted administrators, viewers and end users. Until now, a project-level grant applied uniformly to every Gemini Enterprise app and data store in the project — so entitlement could be reasoned about at project granularity. It no longer can: effective access is the union of project-level and per-resource bindings, and the per-resource grants are configurable through the console, gcloud **and the REST API**. AISPM's Gemini Enterprise entitlement model must be re-derived per app and per data store, and flag resources whose resource-level bindings widen access beyond the project grant. Source: https://docs.cloud.google.com/gemini/enterprise/docs/iam-policy-for-apps-and-data-stores

- **[AISPM] [MEDIUM] Perplexity Decisions API and Agent API document/image tooling**: Perplexity shipped a **Decisions API** at `POST https://api.perplexity.ai/v1/decisions`, powered by a dedicated model (`pplx-decider-v1-27b`) that returns a **probability distribution over a fixed answer set** instead of generated text — supporting yes/no, pick-one-of-N, and rubric-score question types over text, JSON or images. This is the second vendor in two scans to ship a constrained-decision endpoint (OpenAI's Decisions API was reported 2026-10-01), confirming a **cross-vendor pattern: model-driven control flow that routes an agent's next action and produces no inspectable text output to monitor**. Alongside it, the Agent API gained **native document ingestion** (`input_file` accepting PDF/DOC/DOCX/TXT/RTF, inline or by public HTTPS URL — note that a public URL means Perplexity fetches the document server-side) and a new **`image_search`** tool. AISPM should add the decisions endpoint and the new Agent API tools to the Perplexity inventory and treat decision calls as unmonitored control-flow points; AIDR needs the document-ingestion path as a data-egress activity type. Source: https://docs.perplexity.ai/docs/decisions/quickstart
