### Claude Enterprise (Anthropic)

All four dated **August 7, 2026**, published after the previous scan's capture.

- **Session budgets for Claude Managed Agents** — a hard cap on a session's spend, priced at public list rates. A session that reaches its budget pauses with the `budget_reached` stop reason instead of starting new model requests; changing or removing the budget resumes it. Deployments accept the same budget and apply it to every session they start. Source: https://platform.claude.com/docs/en/managed-agents/budgets

- **Skills loaded from a GitHub repository** — when a Managed Agents session mounts a repository, any skills in its root `.claude/skills` directory are **discovered automatically at session start** and available to the agent for that session. Source: https://platform.claude.com/docs/en/managed-agents/skills#load-skills-from-a-github-repository

### Microsoft Foundry (Azure AI Foundry) — backlog recovery

None of the following has appeared in any prior report from this monitor. They are not new *to the platform* — they are new to Zenity's coverage, surfaced by reading `/azure/foundry/whats-new-foundry` for the first time after discovering the configured source resolves to the frozen *classic* page.

- **Toolboxes and tool search (preview)** — a **versioned, first-class toolbox resource** that presents a set of tools to hosted agents through a **single managed MCP consumer endpoint**. Supported tool types inside a toolbox: MCP, web search, Azure AI Search, code interpreter, file search, OpenAPI, **agent-to-agent (A2A)**, **browser automation**, **Fabric IQ**, **Work IQ**, tool search, and skills. Each tool carries its own auth configuration and a `require_approval` setting (including `"never"`); a guardrail (RAI policy) attaches per toolbox; RBAC spans the developer identity, the agent's runtime managed identity, and end-user identities proxied through OAuth or Entra token passthrough. Versions are published and promoted, and the first version becomes default automatically. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox
- **Routines (preview)** — project-native trigger→agent automation. A routine has one trigger and one action, plus input, lifecycle state, and run history. Trigger types are **timer** (one-shot), **recurring** (cron-style), and **event** — in preview, `github_issue`, firing when an issue is opened or closed in a watched GitHub repository via a Foundry-provisioned GitHub connector connection in the account's connector namespace. Separately, a hosted agent can **schedule itself** to run again later by calling a built-in reminder tool exposed through a toolbox: the agent chooses the delay and the service re-invokes it on the same conversation. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/routines
- **Fabric IQ tool (preview)** — Foundry agents delegate natural-language tasks to the Microsoft Fabric IQ workload, which unifies OneLake data behind an **ontology** (entity types, properties, relationships, and bindings to lakehouses, eventhouses and Power BI semantic models), plus Fabric data agents and Power BI semantic models, with an NL2Ontology layer translating business-language questions into structured queries. Requests use the connection's configured identity and honour Fabric permissions; auth is delegated user authentication through a BYO Entra app or a managed OAuth connection. Microsoft's own docs warn that data may be sent outside the Azure compliance boundary. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/fabric-iq
- **Work IQ tool (preview)** — connects Foundry agents to Microsoft 365 emails, meetings, files, chats and business-system signals. Foundry routes the request to Work IQ **as a peer agent over the Agent-to-Agent (A2A) protocol** using On-Behalf-Of authentication, so retrieval runs in the signed-in user's context and honours M365 permissions, sensitivity labels and information barriers. Setup requires a Global Administrator to provision the Work IQ service principal (app ID `fdcc1f02-fc51-4226-8753-f668596af7f7`) and grant **tenant-wide admin consent for the delegated `WorkIQAgent.Ask` scope** to a single-tenant Entra app whose client secret is held in the Foundry connection. Only "bring your own Entra app" (OBO) is supported; app-only auth is not. Inside a toolbox the tool fans out to Copilot Chat, Teams, Word, Outlook Calendar, Outlook Mail, the Microsoft 365 user profile, SharePoint and OneDrive via MCP endpoints, with Work IQ Chat on the A2A endpoint. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/work-iq
- **Memory in Foundry Agent Service (preview) and the Memory Store API (preview)** — managed long-term memory stores holding three extracted memory types, **all enabled by default**: user profile memory, chat summary memory, and **procedural memory** (reusable how-to routines inferred from prior interactions). LLM-driven extraction, consolidation and conflict resolution; item-level CRUD, store-level default TTL, and direct remember/forget commands; a scope model capped at 100 scopes per store and 10,000 memories per scope. **VNet integration is not supported for memory stores.** The docs name prompt injection and memory corruption as explicit risks. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/what-is-memory
- **Agent optimizer (preview)** — a closed-loop evaluate→mutate→rank service that automatically rewrites an agent's **instructions**, **skills** (`SKILL.md` bodies), **tool and parameter descriptions**, and **model selection**, then lets you promote the winning candidate to a new agent version. Uses two models (an eval model and an optimization model). Microsoft's own warning: during a run the optimizer invokes the agent against every task in the dataset, so **external tool calls really execute**. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-optimizer-overview
- **Trace Replay (preview) and traces-to-evaluation-datasets (preview)** — replay a recorded agent conversation step by step from any Conversation ID or Trace ID, in a Trajectories view (hierarchical span tree covering LLM invocations, tool execution, user prompts and **sub-agent orchestrations**, with waterfall bars by duration or token cost) or a User view (chat reconstruction of what the end user saw), with playback controls, span-type and token-range filters, raw JSON metadata and inline evaluation results. Backed by the project's Application Insights resource; requires a Log Analytics reader role. Traces can additionally be converted into registered evaluation datasets. Source: https://learn.microsoft.com/en-us/azure/foundry/observability/how-to/trace-agent-replay
- **Publish agents to Microsoft 365 Copilot and Microsoft Teams** — including from agents running inside a virtual network. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/publish-copilot

## New Coverage Required

- **[AISPM] [HIGH] Microsoft Foundry toolboxes — a versioned tool bundle behind one MCP endpoint**: Foundry Agent Service introduces the **toolbox**, a first-class versioned resource that hands a hosted agent an entire set of tools through a single managed MCP consumer endpoint. A toolbox can contain MCP servers, web search, Azure AI Search, code interpreter, file search, OpenAPI targets, **agent-to-agent (A2A) connections**, **browser automation**, **Fabric IQ**, **Work IQ**, tool search and skills — each with its own authentication and its own `require_approval` setting, including `"never"`. This is a new inventory entity class (toolbox, toolbox version, per-tool configuration, attached guardrail/RAI policy) and it breaks the assumption that an agent's capabilities are enumerable from the agent object: the agent references an endpoint, and the toolbox version behind that endpoint determines what it can actually do. AISPM must discover toolboxes and their versions, resolve which agents consume which version, expand each toolbox into its constituent tools, and flag tools set to `require_approval: never` — especially browser automation, code interpreter and A2A. Version promotion is also a change-control surface worth alerting on: promoting a new default version silently changes every consuming agent's capability set. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox

- **[AISPM] [HIGH] Microsoft Foundry routines — agents that fire on a schedule or a GitHub event, and can reschedule themselves**: Routines make agent execution autonomous and project-native. A routine binds a trigger — a one-shot timer, a cron-style recurring schedule, or an **event** (`github_issue`, firing when an issue is opened or closed in a watched repository) — to an agent invocation, with its own input, lifecycle state and run history. Two properties make this materially different from an agent that waits to be called. First, an **externally controlled event can start an agent**: anyone who can open an issue in the watched repository can cause a Foundry agent to run with attacker-influenced input, which is a prompt-injection entry point with no human in the loop. Second, a hosted agent can **schedule itself** to run again later through a built-in reminder tool exposed via a toolbox, choosing its own delay, so an agent loop can persist beyond any single human interaction. AISPM must inventory routines as agent-attached objects, record trigger type and the connected external system, and identify agents reachable from an external event trigger; AIDR should treat routine run history as an activity source and alert on self-scheduled re-invocation chains. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/routines

- **[AISPM] [HIGH] Microsoft Foundry Work IQ tool — Foundry agents reaching the full Microsoft 365 estate over A2A**: The Work IQ tool lets a Foundry agent delegate natural-language tasks to Work IQ **as a peer agent over the Agent-to-Agent (A2A) protocol**, with Work IQ retrieving and reasoning over the signed-in user's emails, meetings, files, chats and business-system signals. Inside a toolbox the tool fans out further, exposing Copilot Chat, Teams, Word, Outlook Calendar, Outlook Mail, the M365 user profile, SharePoint and OneDrive as MCP endpoints. Three properties make this a distinct HIGH finding rather than a variant of the Fabric IQ one. It is authorised by a **tenant-wide admin consent grant of the delegated `WorkIQAgent.Ask` scope**, made once by a Global Administrator to a single-tenant Entra app — so a single consent decision governs whether any Foundry agent in the organisation can reach M365 at all, and that consent grant is exactly the object AISPM should inventory and alert on. The app's **client secret lives in a Foundry connection**, making that connection a high-value credential joining two products. And because the path is A2A over OBO rather than a direct Graph call, this M365 data access will not appear in whatever discovery relies on Graph permissions on the agent. AISPM must inventory Work IQ connections per project, resolve the consented Entra app and its secret lifecycle, enumerate which sub-tools a toolbox exposes, and reconcile Foundry-side M365 reach against the M365-side agent inventory. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/work-iq

- **[AISPM] [HIGH] Microsoft Foundry Fabric IQ tool — agents reasoning over the whole OneLake estate through an ontology**: The Fabric IQ tool lets a Foundry agent delegate natural-language questions to Microsoft Fabric IQ, which unifies data across OneLake behind an **ontology** — enterprise entity types, properties, relationships and bindings to lakehouses, eventhouses and Power BI semantic models — with an NL2Ontology layer that turns business-language questions into structured queries. This is a cross-product data-access edge of a scale Zenity does not currently model on the Foundry side: an agent's effective data reach becomes the reach of the connection identity across a whole Fabric estate, expressed in business vocabulary rather than in tables an inventory could enumerate. Access is delegated user authentication through a BYO Entra app or a managed OAuth connection, so the blast radius depends entirely on which identity the connection carries. Microsoft's own documentation warns data may be sent outside the Azure compliance boundary. AISPM should discover Fabric IQ connections per agent and per toolbox, resolve the connection identity and what Fabric items it can read, and map the ontology as the data-reach boundary — an agent grounded in an ontology inherits reach over every source bound to it, not just the ones it has queried. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/fabric-iq

- **[AISPM] [HIGH] Anthropic Managed Agents — skills auto-loaded from a mounted GitHub repository**: When a Claude Managed Agents session mounts a repository, any skills in that repository's root `.claude/skills` directory are **discovered automatically at session start** and become available to the agent for that session. This makes an agent's capability set a function of repository contents rather than of its declared configuration: whoever can merge to the mounted repository can add a skill, and it takes effect on the next session with no change to the agent object and no separate grant. That is a supply-chain path directly into agent behaviour, and it defeats point-in-time capability inventory in exactly the way the mid-conversation tool changes finding (2026-08-07) does, but sourced from version control instead of from the API caller. AISPM must resolve, for every Managed Agents agent, which repositories its sessions mount and enumerate the skills present in each repository's `.claude/skills` directory as inventory entities, attributing them to the repository and its write-access population rather than to the agent. AIRT should test whether a skill introduced this way is trusted equivalently to a declared one. Source: https://platform.claude.com/docs/en/managed-agents/skills#load-skills-from-a-github-repository

- **[AISPM] [HIGH] Google Gemini Enterprise — custom MCP server data stores reach GA**: Organizations can now connect their own MCP server to Gemini Enterprise as a data store, reaching private company data, custom internal tools and MCP-compliant third-party systems, and MCP servers can additionally be imported from the Agent Registry. This is a new entity class for a secondary-tier platform Zenity already tracks — custom MCP server data stores, their endpoint URLs, their auth mode (none or OAuth 2.0) and the tools they expose — and it is a genuine expansion of Gemini Enterprise's surface area, not a refinement. Two details deserve rules of their own. The capability is **off by default behind an organization-policy constraint requiring administrator approval**, so the state of that constraint is a first-class posture signal and the documented override path is a privilege-escalation route worth watching. And **"no authentication" is a supported option** on an endpoint that serves private company data. AISPM should discover custom MCP server data stores, record whether the org policy constraint is enforced or overridden, flag unauthenticated servers, and expand each server's tool list into the agent capability graph. Source: https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server

- **[AISPM] [MEDIUM] Microsoft Foundry agent memory and the Memory Store API**: Foundry Agent Service adds managed long-term memory stores that extract three memory types from conversations — user profile, chat summary, and **procedural memory** (reusable how-to routines inferred from prior interactions) — with **all three enabled by default**. The stores support item-level CRUD, a store-level default TTL, direct remember/forget commands, and a scope model capped at 100 scopes and 10,000 memories per scope. This is a new persistent data store to inventory on a primary platform, and three properties make it more than that: memories are **LLM-extracted**, so the store accumulates organisational and personal content nobody explicitly wrote there; procedural memory persists *behaviour* rather than facts, which means a poisoned procedural memory is a durable change to how the agent operates across future sessions; and **VNet integration is not supported for memory stores**, so a network-isolated project still has this data path outside the perimeter. Microsoft's documentation names prompt injection and memory corruption as risks without offering a platform control beyond content filtering. AISPM should discover memory stores and their scopes, record which memory types are enabled and the configured TTL, and treat a store with no TTL as an indefinite retention finding; AIRT should build memory-poisoning cases specifically against procedural memory. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/what-is-memory

- **[AIRT] [MEDIUM] Microsoft Foundry agent optimizer — automated rewriting of agent instructions, skills and tool descriptions**: The agent optimizer runs a closed-loop evaluate→mutate→rank cycle that automatically generates and promotes new agent **instructions**, **skill bodies**, **tool and parameter descriptions**, and **model selections**, ranked by a composite score. Two things make this security-relevant rather than an ops convenience. First, an agent's system prompt and skills become **machine-authored and versioned by score**, so the guardrails a human wrote into the instructions can be silently optimised away in pursuit of a task-success metric that does not measure them — a candidate that scores 0.94 by ignoring a safety instruction wins. Second, Microsoft explicitly warns that during a run the optimizer **invokes the agent against every task in the dataset, so external tool calls really execute**: an optimization run is a bulk, automated exercise of the agent's full tool set against production connections. AIRT should test whether optimizer-generated instructions preserve declared safety and data-handling constraints, and AISPM should treat optimization runs as change events requiring provenance on which agent version was machine-generated versus human-authored. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-optimizer-overview

- **[AISPM] [MEDIUM] Anthropic Managed Agents session advisor — a second model inside the agent loop**: A Managed Agents session can be given an **advisor**: a model at least as capable as the agent's own that the session's primary thread consults mid-turn for strategic guidance, configured as a `{"type": "advisor"}` entry in the agent's multiagent roster. This adds a new roster entry type to inventory and changes agent attribution: the reasoning that drives a session's decisions may originate from a model that is not the agent's configured model, so "which model is this agent running" is no longer answerable from the `model` field alone. Because the advisor must be at least as capable as the agent, an agent nominally pinned to a cheaper or more constrained model can consult a frontier one. AISPM should enumerate multiagent roster entries by type, record advisor model IDs as a distinct attribute on the agent, and reconcile them against whatever model-approval policy the organisation applies. Source: https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration#give-the-session-an-advisor

- **[AISPM] [MEDIUM] Anthropic Managed Agents `inference_geo` — per-agent and per-session data residency**: Where model inference runs for a Managed Agents agent is now configurable via `inference_geo` inside the `model` object at agent creation, **and overridable for a single session**. Data residency becomes a mutable per-invocation property rather than an organisation-level setting, which means an agent that is compliant by configuration can be made non-compliant for one session by a caller who can set the override, leaving no trace in the agent object. AISPM should record `inference_geo` as an inventory attribute on every Managed Agents agent, detect agents with no explicit geo, and — more importantly — treat session-level overrides as an activity to capture rather than a configuration to read, since the agent-level value will not reflect where inference actually ran. Source: https://platform.claude.com/docs/en/manage-claude/data-residency

- **[AISPM] [MEDIUM] Anthropic Managed Agents session budgets**: A Managed Agents session can carry a hard cap on its spend at public list rates; a session that reaches the cap pauses with the `budget_reached` stop reason instead of starting new model requests, and changing or removing the budget resumes it. Deployments accept the same budget and apply it to every session they start. This is a new per-session and per-deployment control object to inventory, and it is the first documented mechanism that bounds how long an autonomous Claude agent can keep running — which makes its absence a posture signal in its own right: a deployment with no budget has no documented ceiling on unattended agent execution. It cuts the other way too, since anyone able to raise or remove a budget can resume a paused session, so budget mutation is a privileged action worth auditing. AISPM should record budgets on agents, deployments and sessions, and flag long-running deployments with none. Source: https://platform.claude.com/docs/en/managed-agents/budgets

- **[AISPM] [MEDIUM] Google Gemini Enterprise — 17 new third-party connectors in public preview**: Gemini Enterprise added connectors for Attio, Cohesity, Descript, Fiscal.ai, Gamma, iManage, Moody's, NetDocuments, Nexla, Oracle NetSuite, Pylon, S&P Global, Sanity, Supabase, Supermetrics, SurveyMonkey and Wix, plus a new Freshservice "create ticket note" action. Each connector is a discoverable inventory entity that widens the platform's data reach, and the set is weighted toward systems that hold exactly the content Zenity's customers care about: **iManage and NetDocuments** are document-management systems for legal and professional-services firms, **Cohesity** is backup and recovery data, **Supabase** is an application database, and **Oracle NetSuite** is ERP. A connector into a backup estate or a legal DMS gives an assistant a retrieval path into content whose access controls were designed around a very different consumption model. AISPM should add these connector types to Gemini Enterprise discovery, resolve the identity each connector authenticates as, and prioritise the DMS and backup connectors for data-reach analysis. The Freshservice action is separately notable as a **write** action rather than a read. Source: https://docs.cloud.google.com/gemini/enterprise/docs/connectors/introduction-to-connectors-and-data-stores

- **[AIDR] [MEDIUM] Google Gemini Enterprise — `execute_tool` and `invoke_connector` trace spans**: Gemini Enterprise added two trace spans for data connectors, `execute_tool` and `invoke_connector`, giving end-to-end parent-child relationships from the assistant prompt through to the third-party API call. This is a new detection surface that closes a specific gap: until now the connector leg of a Gemini Enterprise interaction was not separately traceable, so a prompt could be observed and a third-party API call could be observed but the two could not be reliably joined. With these spans, AIDR can attribute an outbound third-party API invocation back to the originating user prompt and the specific tool the model chose — which is the primitive needed to detect a prompt causing an unexpected connector call, the core indirect-prompt-injection signal on this platform. AIDR should ingest both span types and build prompt→tool→connector→API chains as a first-class activity record. Source: https://docs.cloud.google.com/gemini/enterprise/docs/release-notes

- **[AIDR] [MEDIUM] Microsoft Foundry Trace Replay and traces-to-evaluation-datasets**: Foundry observability adds **Trace Replay**, which reconstructs a recorded agent conversation from any Conversation ID or Trace ID as a hierarchical span tree covering LLM invocations, tool execution, user prompts and **sub-agent orchestrations**, with a parallel User view showing what the end user actually saw, plus span-type and token-range filters and inline evaluation results. Traces are backed by the project's Application Insights resource, so Foundry agent behaviour is a **retained, queryable, per-span record** rather than a transient debugging view — which makes it a usable AIDR ingestion source, and specifically one that exposes sub-agent orchestration, the hardest part of an agent interaction to observe from outside. The companion traces-to-dataset path is the posture half of the finding: it materialises trace contents, including whatever user and organisational data flowed through the interaction, into registered evaluation datasets that persist independently of trace retention. AIDR should ingest Foundry traces as an activity stream; AISPM should treat trace-derived evaluation datasets as a data store whose classification inherits from the conversations that produced it, not from the project it lands in, and note that Log Analytics reader is sufficient to read the whole conversation corpus. Source: https://learn.microsoft.com/en-us/azure/foundry/observability/how-to/trace-agent-replay

- **[AISPM] [MEDIUM] Microsoft Foundry agents publishable into Microsoft 365 Copilot and Teams**: Foundry agents can be published directly into Microsoft 365 Copilot and Microsoft Teams, including from agents running inside a virtual network. This creates a cross-product agent identity problem Zenity should model explicitly: the same logical agent now exists as a Foundry resource *and* as an agent surfaced in the M365 Copilot tenant, discovered by two different inventory paths that will not obviously reconcile. An agent published this way reaches end users through Copilot and Teams while its tools, connections, memory and toolbox live on the Foundry side — so an M365-side inventory sees a Copilot agent with no visible tool configuration, and a Foundry-side inventory sees an agent with no visible user population. AISPM must link the two representations into one entity and carry the Foundry-side capability graph through to the Copilot-side exposure. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/publish-copilot
