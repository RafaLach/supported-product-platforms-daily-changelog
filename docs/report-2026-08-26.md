## Executive Summary

**Eight findings across four platforms, and the two biggest are both about the same structural shift: the boundary where an agent's capabilities are decided is moving off the platform and onto the page.**

**OpenAI shipped site tools — its implementation of WebMCP — on August 25.** A website now declares tools to a visiting agent by calling `document.modelContext.registerTool()` in ordinary page JavaScript, and ChatGPT Work or Codex running in the desktop app's built-in browser **discovers and invokes them automatically**. There is no install step, no marketplace, no config file and no server: the tool surface is a property of the page, materialising at navigation time and vanishing when the tab closes. OpenAI's own documentation states the security position plainly — "**Website-provided tool definitions and results are untrusted content**", "tool names alone don't prove function or scope", and the checks it does apply "reduce risk; they don't make a website or its output trustworthy." Tools execute against the site's **already-authenticated session**, so a site tool inherits whatever the logged-in user can do. Supported on GPT-5.6 Sol and Terra; **withheld from Enterprise and Education workspaces**, which means the population running it is Plus/Pro/Business — the least governed tier.

**The same day, OpenAI made scheduled tasks event-driven.** A task can now fire on **a new Gmail message (filterable by sender or subject), a new message in a watched Slack channel, or pull-request activity on an authorized github.com repository** — reviews, comments, commit updates and merges. Time-based schedules and event triggers are mutually exclusive, and clustered events may be combined into a single run. This closes the loop that has been forming for months: an agent that an outsider can cause to run, on content that outsider wrote. Anyone who can email the user, post in a watched channel, or comment on a PR is now an upstream trigger for an authenticated agent run.

**AWS added cross-account sharing to the AWS Agent Registry.** A registry of agents, tools, skills and MCP servers can now be shared to other accounts through AWS RAM under one of **four managed permissions** — and two of the four (`ForConsumer`, `ForPublisher`, `ForAdmin`) grant **`agent-registry:InvokeRegistryMcp`**, so the share is not a read grant but a live tool-invocation grant. **Inside an AWS Organization with RAM org-sharing enabled, acceptance is automatic — no invitation, no consumer-side action.** The two record-level condition keys AWS provides are explicitly **not evaluated on `SearchDiscoverableRegistryRecords`, `ListRegistryRecords` or `ListDiscoverableRegistryRecords`**, so enumeration leaks across the boundary even where record access is scoped.

**Microsoft Agent Framework was read for the first time and it is a large coverage gap.** Two features stand out, and both are governance primitives Zenity should know exist because customers will point at them. **Agent Hooks** (`.NET 1.19.0`, Aug 22; experimental in Python) implements **AGENT-HOOKS-0.1**, a framework-neutral interception contract published at `github.com/responsibleai/agent-hooks`, with **eight named interception points** from `agent_startup` through `agent_shutdown`, verdicts of allow/deny/transform/**escalate**, and an explicit `enforce` vs **`evaluate_only`** mode. The documentation names its own bypasses: **provider-executed hosted tools never reach `pre_tool_call`/`post_tool_call`**, middleware registered before the bundle sits **outside** the enforcement boundary, and the contract is "cooperative rather than a process isolation boundary." **FIDES** (Flow Integrity Deterministic Enforcement System, experimental, shipping in `agent-framework-core`) is information-flow control: every `Content` item carries an **integrity** label (trusted/untrusted) and a **confidentiality** label (public/private/user_identity), labels propagate most-restrictive-wins through tool calls, and sinks declare `accepts_untrusted: False` and `max_allowed_confidentiality` so a privileged tool is refused *before* it runs. FIDES has been documented since **June 23** and this monitor has never reported it.

**Google's Gemini Enterprise stream moved twice** — and note that the 08-24 scan recorded this stream as topping at August 20, so both dated entries below are new. **August 21** added **seven data stores** (Atlan, Bitly, FactSet AI-Ready Data, FullStory, Globalping, Pendo, Stripe) plus new **write actions** on existing connectors, including a Supabase action set that is squarely infrastructure control: **apply migration, deploy edge function, execute SQL, pause project, restore project**. **August 24** added the **D&B Commercial Graph** data store (Preview) and extended data-connector telemetry with `tool_id` / `engine_id` / `response_code` dimensions plus a new `request_latencies` metric (Beta).

### Microsoft Agent Framework — first scan; two findings

Not in `sources.json`. Read at `github.com/microsoft/agent-framework/releases` and `learn.microsoft.com/en-us/agent-framework/*` after the August release stream surfaced two governance primitives this monitor had never recorded. Release cadence is roughly twice weekly across two language SDKs: **dotnet-1.19.0 (Aug 22)**, **python-1.15.0 (Aug 21)**, **dotnet-1.18.0 (Aug 18)**, **python-1.14.0 (Aug 13)**.

- **Agent Hooks — a first-class, fail-closed interception contract.** Implements the framework-neutral **AGENT-HOOKS-0.1** specification (`github.com/responsibleai/agent-hooks`). Eight interception points: `agent_startup`, `input`, `pre_model_call`, `post_model_call`, `pre_tool_call`, `post_tool_call`, `output`, `agent_shutdown`. Verdicts: `allow`, `warn`, `deny`, **`escalate`** (deny pending an approval resolver), and `transform` (rewrite a value under a `$target` path). Runtime guarantees: **fail closed** (invalid contexts, invalid verdicts, interceptor failures and enforcement failures all block rather than bypass), **transform write-back**, **buffered streaming** (no update reaches the caller until the complete response passes `output`), **verdict-gated persistence**, and **complete bundle installation** (agent + chat + function parts install as one unit). Configuration includes `mode` (`enforce` vs **`evaluate_only`**), `composition` (default sequential `first_deny`), `identity_provider` (default `jcs-sha256`), a 5-second per-interceptor `timeout`, and a `record_sink` that receives **payload-free** `InterceptionRecord`s. **Python only and experimental**; not implemented in .NET or Go. Source: https://learn.microsoft.com/en-us/agent-framework/agents/agent-hooks
- **FIDES — deterministic information-flow control against prompt injection and exfiltration.** Every `Content` item carries a `security_label` with **integrity** (`trusted` / `untrusted`) and **confidentiality** (`public` / `private` / `user_identity`); `combine_labels` picks the most restrictive of each axis. Four parts: `ContentLabel`, `LabelTrackingFunctionMiddleware`, `PolicyEnforcementFunctionMiddleware`, and `quarantined_llm` + `ContentVariableStore`. Sinks annotate `accepts_untrusted: False` and `max_allowed_confidentiality`; sources annotate per-item labels or a tool-level `source_integrity`. `SecureAgentConfig` wires it up as a **context provider**, with `auto_hide_untrusted` (default **True** — untrusted results are replaced in the main context by a `var_<id>` reference), secure-by-default `default_integrity=UNTRUSTED`, `allow_untrusted_tools`, `block_on_violation`, `approval_on_violation`, `enable_audit_log` and `enable_policy_enforcement`. `quarantined_llm` processes untrusted variables against a separate chat client **with no tools attached**, and labels its own output untrusted. Experimental, **Python only**, documented since **ms.date 2026-06-23** (`updated_at` 2026-08-25). Source: https://learn.microsoft.com/en-us/agent-framework/agents/security
- *(Held: `python-1.15.0` optional **A2UI** support for agent-generated interfaces — A2UI itself was reported 2026-08-21; A2A preview consent URLs; Foundry Hosted Agents steering/retry/recovery; `dotnet-1.19.0` session-persisted chat routing, Azure Blob Storage session persistence, hosted agent state in Foundry, and the breaking migration of MCP long-running task support to the **2026-07-28 Tasks extension**; `dotnet-1.18.0` A2A task store isolation and a Cosmos chat-history retrieval API.)*

## New Coverage Required

- **[AIRT] [HIGH] OpenAI site tools (WebMCP) — any website can hand tools to a visiting ChatGPT or Codex agent, with no install, no config file, and tool definitions that OpenAI documents as untrusted**: On **August 25, 2026** OpenAI shipped **site tools**, its implementation of the proposed **WebMCP** standard, in the ChatGPT desktop app's built-in browser and in ChatGPT Sites. A page registers a tool by calling **`document.modelContext.registerTool()`** in ordinary JavaScript, supplying a name, a description, an input schema, an **execute handler that calls the application's existing logic**, and annotations such as `readOnlyHint`. A compatible agent — **ChatGPT Work or Codex** — **discovers the available tools automatically when the page loads** and invokes the relevant ones while completing the user's task. **Every assumption behind existing tool inventory breaks here.** There is no installation event, so nothing is ever written to disk or to a settings file; there is no marketplace or registry, so there is no catalogue to enumerate; there is no server, so there is no endpoint to inspect out-of-band; and the tool set **exists only for the lifetime of the page**, which means an agent's capability set is now a function of navigation history rather than configuration. This is a different problem from the Agent Plugins/`mcp.json` gap reported on 08-24 — that was an artifact in the wrong file, this is **no artifact at all**. OpenAI's own documentation supplies the threat model in its own words: "**Website-provided tool definitions and results are untrusted content**", "**tool names alone don't prove function or scope**", "website instructions don't grant permission for unrelated actions", and, on its mitigations, "**these checks reduce risk; they don't make a website or its output trustworthy**." Three specifics make this actionable. **First, tools run inside the site's existing authenticated session** — the execute handler is the site's own code calling its own logic with the logged-in user's permissions, so a site tool's blast radius is exactly what the user can do on that site, reached without the user clicking anything. **Second, the mitigations are per-invocation and local**: each invocation gets a safety review, the browser ties invocations to the originating page, normal website-access and confirmation policies still apply for consequential actions (sending messages, purchases, deleting data, changing permissions), and users can inspect the tool list via a **"Site tools" button in the address bar** or disable the feature under **Settings > Browser > Permissions** — all of which are user-facing controls with no tenant-level policy surface documented. **Third, and most important for coverage: it is withheld from Enterprise and Edu workspaces**, and it requires **GPT-5.6 Sol or Terra** (Luna has it disabled). So the population that has it is Plus/Pro/Business on a personal or unmanaged-tier account — precisely the population an enterprise sees least. AIRT should treat a WebMCP-enabled page as a first-class injection and tool-abuse vector, and test the specific shape this creates: a tool whose *description* is adversarial (the model chooses tools by description, and the description is attacker-authored), a tool whose *name* implies a benign scope while its handler does something else (OpenAI names this failure explicitly), a `readOnlyHint` annotation that is simply false, and tool *results* used to steer subsequent turns. ENDPOINT must stop treating tool availability as static endpoint state: capability now arrives per-navigation, so the signal to collect is browsing-plus-invocation telemetry from the desktop app, not a file inventory. AISPM should model "site tool" as an ephemeral tool entity bound to an origin rather than to an agent or an install, and treat the **origin** as the provenance record it will never get from a manifest. Source: https://learn.chatgpt.com/docs/webmcp

- **[AIDR] [HIGH] ChatGPT scheduled tasks can now be triggered by inbound Gmail, Slack and GitHub events — an outsider who can email the user can cause an authenticated agent to run**: Also on **August 25, 2026**, OpenAI made scheduled tasks event-driven. A task can now fire on **a new Gmail message** (optionally filtered by sender or subject), **a new message in a watched Slack channel**, or **pull-request activity in an authorized github.com repository** — including reviews, comments, commit updates and merges. The user connects the account under **Settings > Apps**, describes the event and the action in Work, then reviews a **Trigger, Condition and Prompt** triple and completes authorization. The **ChatGPT Slack app must be a member of every watched channel** and the **GitHub app needs repository access**, so the trigger carries its own standing integration grant. Time-based schedules and event triggers **cannot coexist** on a single task, and **clustered events may be combined into a single run**. Available on Plus, Pro, Business, Enterprise and Edu, plus ChatGPT for Healthcare workspaces. **The security consequence is a change in who initiates agent activity.** Until now an agent run in ChatGPT was traceable to a human action — a prompt, or a schedule that a human set. An event trigger inverts this: **the initiating party is whoever authored the triggering content**, and for the three named sources that party is frequently external. Anyone who can send the user an email, post in a Slack channel the ChatGPT app has joined, or comment on a pull request in an authorized repo can now cause an authenticated agent run to happen, at a time of their choosing, on text they wrote. That is the classic indirect-prompt-injection precondition with the delivery problem solved for the attacker: they no longer need the user to paste anything or open anything. **The filters are the attack surface, not the control** — "filter by sender or subject" is attacker-observable and attacker-satisfiable, and a sender filter is only as strong as the absence of spoofing and forwarding. Two second-order properties matter for detection. **Event clustering** means one agent run may correspond to several triggering messages, so the mapping from external content to agent action is many-to-one and cannot be reconstructed from the run alone. And because triggers are configured per task with their own connected app, **the standing grant outlives the user's attention**: a task configured once keeps consuming external content indefinitely with no session for a human to be present in. AIDR should treat event-triggered task runs as a distinct activity type from user-initiated and schedule-initiated runs, capture the triggering source (Gmail sender/subject, Slack channel and author, GitHub repo/PR/actor) as first-class attribution, and alert on the shape that matters: an externally-triggered run that subsequently touches internal data or invokes a write-capable connector. AISPM should inventory event-triggered tasks as standing automations with an external trigger surface, record which apps each is bound to and which channels/repos are watched, and flag tasks whose trigger is broad (any new Gmail message, a high-traffic public channel, a repo with external contributors). Source: https://learn.chatgpt.com/docs/automations

- **[AISPM] [HIGH] AWS Agent Registry can now be shared across accounts via RAM, and three of the four managed permissions grant live MCP invocation — with automatic acceptance inside an Organization**: AWS added **cross-account sharing to the AWS Agent Registry** through **AWS Resource Access Manager**. The registry — the "private, governed catalog of agents, tools, skills, MCP servers, and custom resources" reported on 2026-08-07 — is now a shareable RAM resource type (`agent-registry:Registry`), and the owner selects one of four AWS managed permissions that RAM enforces through a resource-based policy it manages. **The permission tiers are the finding.** `AWSRAMDefaultPermissionAgentRegistryReadOnly` (the default when no permission is specified) grants control-plane reads plus data-plane discovery but **explicitly not** MCP invocation. `AWSRAMPermissionAgentRegistryForConsumer` grants discovery **plus `agent-registry:InvokeRegistryMcp`** — and AWS's own tip recommends it as the default choice: "We recommend the **Consumer** permission for typical sharing scenarios." `AWSRAMPermissionAgentRegistryForPublisher` adds `CreateRegistryRecord`, `UpdateRegistryRecord`, `DeleteRegistryRecord` and `SubmitRegistryRecordForApproval`. `AWSRAMPermissionAgentRegistryForAdmin` adds **`UpdateRegistryRecordStatus`** — approve, reject or deprecate records — so **curation authority over a registry can be delegated to a different AWS account** while `UpdateRegistry`/`DeleteRegistry` stay with the owner. Read together: the recommended sharing posture is not "let another account look at the catalogue", it is "**let another account's agents invoke tools through my registry's MCP endpoint**", and the most permissive tier lets a foreign account decide which records are approved for everyone. **The consent model is the second half.** For accounts outside the owner's Organization, RAM sends an invitation the consumer must accept. **For accounts inside the same Organization with RAM org-sharing enabled, acceptance is automatic — no invitation, no consumer-side action, no event for the consumer to notice.** So in the common enterprise case, a registry share simply appears, and any Zenity model that expects a two-sided handshake will miss it entirely. Revocation is likewise **eventually consistent, with up to ~30 seconds of continued access after `disassociate-resource-share`**. **Third, the fine-grained controls have a documented enumeration hole.** The two service condition keys — **`agent-registry:RecordCreatorAccount`** and **`agent-registry:RecordSourceAccount`** — are resolved at authorization time from the stored record and cannot be set from request input (good), but AWS states they are **not evaluated** on `CreateRegistryRecord`, nor on **`SearchDiscoverableRegistryRecords`, `ListRegistryRecords` or `ListDiscoverableRegistryRecords`**, which "return summaries for all matching records regardless of condition-key restrictions." AWS's own remediation is to withhold search and list from the share — which almost nobody will do, because discovery is the point. So a consumer scoped by condition key to its own records can still **enumerate the full catalogue of another account's agents, tools and MCP servers**. AISPM should treat a shared registry as a cross-account trust edge, not an attribute: discover RAM resource shares over `agent-registry:Registry`, resolve which managed (or customer-managed) permission each carries, and materially distinguish shares that include `InvokeRegistryMcp` from those that don't. Flag `ForAdmin` shares as delegated curation authority, flag org-internal shares as having no acceptance event, flag any customer-managed permission that grants list/search alongside condition keys as an enumeration exposure, and correlate registry records against the consumer accounts that can reach them so a "private, governed catalog" is not scored as single-account when it is not. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-cross-account-sharing.html

- **[AISPM] [HIGH] Microsoft Agent Hooks — a framework-neutral, fail-closed agent interception contract with eight named control points and three documented bypasses**: Microsoft Agent Framework has shipped **Agent Hooks**, described by Microsoft as "a first-class Agent Framework capability for applying governance and runtime controls at well-defined points in an agent's execution," and it implements **AGENT-HOOKS-0.1**, a **framework-neutral contract** published at `github.com/responsibleai/agent-hooks` so that "policy engines, approval gateways, budget guards, content filters, and egress controls can target one common control surface." It reached first-class experimental status in **.NET 1.19.0 on August 22** and is experimental in the Python SDK; the doc pages were refreshed **2026-08-25**. **Why this is a coverage item and not just a competitor feature:** Agent Hooks is where an enterprise's agent controls will increasingly live, so Zenity needs to inventory it, read its verdicts, and know exactly where its guarantees stop. **The control surface is eight named interception points** — `agent_startup`, `input`, `pre_model_call`, `post_model_call`, `pre_tool_call`, `post_tool_call`, `output`, `agent_shutdown` — each with a defined transform target (messages to the model, tool arguments, tool results, final response content). **The verdict vocabulary is five-valued**: `allow`, `warn`, `deny`, **`escalate`** (a liftable deny resolved through an approval channel), and `transform` (rewrite a value at a `$target` path). Microsoft states the runtime guarantees explicitly: **fail closed** — "invalid contexts, invalid verdicts, interceptor failures, and enforcement failures don't silently bypass controls"; **transform write-back**, where a transform that can't be applied fails the run; **buffered streaming**, where no update reaches the caller until the full response has passed `post_model_call` and `output`; **verdict-gated persistence**; and **complete bundle installation**, so "an incomplete enforcement boundary can't be configured accidentally." **The three bypasses Microsoft documents are the highest-value part of this finding, because each is a place where a customer will believe they are protected and not be.** (1) **Provider-executed hosted tools do not pass through the function-invocation seam at all** — their calls and outputs surface at `post_model_call`, but `pre_tool_call` and `post_tool_call` "can't block the provider's server-side execution." An agent whose tools are hosted by the model provider therefore has *no* enforceable tool gate, only after-the-fact visibility. (2) **Middleware registered before the bundle is outside the boundary** — "treat outer position as outer trust" — so ordering, not presence, determines coverage, and a misordered stack silently reduces the enforcement surface. (3) **The contract is "cooperative rather than a process isolation boundary"**: interceptors run in the host process, receive the full content, and are not sandboxed — "only register interceptors you trust", and "code paths that bypass the guarded agent pipeline aren't covered." A fourth, subtler gap sits in persistence: with `require_per_service_call_history_persistence=True`, each model exchange is persisted once its `post_model_call` verdict permits it, and **"a later `output` deny doesn't roll back that already permitted history"** — so an output-only egress policy leaves model content durable. **And the mode flag is a posture attribute in its own right**: `evaluate_only` runs every interceptor and records every verdict while **allowing every action**, with Microsoft warning "don't describe an `evaluate_only` deployment as enforced governance." An agent with hooks installed in `evaluate_only` looks governed and is not — exactly the kind of false-assurance state AISPM exists to surface. Note also the availability asymmetry: **Python only**; .NET and Go agents are directed to plain middleware, tool approval and Agent Safety instead, so within one customer's fleet the same nominal control exists on some agents and not others. AISPM should discover which Agent Framework agents have an Agent Hooks bundle installed, record the **mode** (`enforce` vs `evaluate_only`), the **composition** profile (default is sequential `first_deny`), whether a `resolver` is configured (without one, every `escalate` is simply a deny), the interceptor set and its **order relative to other middleware**, and whether the agent uses provider-hosted tools — because that last fact converts a nominally complete boundary into an incomplete one. The **`record_sink` `InterceptionRecord` stream** is a first-class ingestion target for AIDR: it carries decision, reason, interceptor summary, mode, identity and sequence, deliberately **without the intercepted payload**, which makes it high-signal and low-sensitivity — but also means Zenity cannot reconstruct *what* was blocked from the record alone. Source: https://learn.microsoft.com/en-us/agent-framework/agents/agent-hooks

- **[AIRT] [HIGH] Microsoft FIDES — deterministic information-flow control with trust and confidentiality labels on agent content, shipping in Agent Framework and never reported by this monitor**: **FIDES** (Flow Integrity Deterministic Enforcement System) is information-flow control as first-class middleware in Microsoft Agent Framework, based on the [FIDES paper by Costa et al.](https://arxiv.org/abs/2505.23643), shipping in `agent-framework-core` behind `agent_framework.security` as an experimental feature. It has been documented since **ms.date 2026-06-23** — this is a **two-month coverage gap**, surfaced only because the page was refreshed **2026-08-25**. Microsoft's framing is a direct attack on the heuristics Zenity's customers currently rely on: defensive system prompts and hand-rolled allow-lists "are heuristic… they don't make the next attack impossible," sanitization "is lossy," and "pre/post-hoc monitoring detects damage; it doesn't prevent it." **The mechanism is a two-axis label on every piece of content.** **Integrity** is `trusted` (developer-controlled: system prompt, internal database, signed config) or `untrusted` ("anything the model could have been tricked into ingesting — issue bodies, emails, scraped pages, third-party API responses"). **Confidentiality** is `public`, `private`, or `user_identity` (PII, credentials, per-user secrets). Labels combine **most-restrictive-wins** (`untrusted` beats `trusted`; `user_identity` > `private` > `public`) and propagate automatically through tool calls via `LabelTrackingFunctionMiddleware`. **Sinks declare what context they will run in**, and these two annotations are the enforcement primitive worth internalizing: **`accepts_untrusted: False`** refuses a tool outright when anything untrusted is in scope (intended for "file writes, destructive operations, anything that mutates production state"), and **`max_allowed_confidentiality`** caps what a sink may leak (`public` for anything that publishes externally). `PolicyEnforcementFunctionMiddleware` checks each invocation **before the tool runs**. There is also a strong-isolation mode: with **`auto_hide_untrusted=True` (the default)**, untrusted tool results never reach the main model at all — they are stashed in a `ContentVariableStore` and replaced in context by a **`var_<id>` reference**, and the agent must call **`quarantined_llm`** to process them, which dispatches an isolated completion against a separate chat client **with no tools attached** and labels its own output untrusted. **Three things make this directly actionable for Zenity.** **First, it is a ready-made vocabulary for findings Zenity already produces.** "Untrusted content reached a privileged sink" and "private content reached a public sink" are now *named, vendor-documented* conditions with a deterministic definition, on a Microsoft-supported runtime. Zenity's own toxic-combination model should adopt this framing — an agent whose reachable tool set contains a sink with no `accepts_untrusted` declaration, or whose `max_allowed_confidentiality` cap is looser than its data sources, is a computable posture defect rather than a judgement call. **Second, its configuration surface is a posture surface with real false-assurance states.** `enable_policy_enforcement=False` is the documented **dry-run mode**: labels still propagate, the audit log still fills, and **no sink is ever blocked** — an agent in this state produces governance telemetry while enforcing nothing. `approval_on_violation=True` converts blocks into human approval prompts, which means the control's effectiveness collapses to user click-through behaviour. `allow_untrusted_tools` is an explicit per-tool exemption list. And **`default_integrity` can be flipped from the secure-by-default `UNTRUSTED` to `TRUSTED`**, which silently relabels every unannotated tool's output as safe. Each of these is a discoverable configuration Zenity should read and score. **Third, its documented limitations are a coverage map.** Labels are **opt-in per data source** — "a tool you forget to label" falls back to defaults; propagation is conservative, so "once an untrusted issue body enters the context, the rest of the run is untrusted unless you explicitly drop it" (and the *drop* is where a bypass would live); approvals are coarse and don't expose the label algebra to the approving user; `quarantined_llm` is **single-turn and tools-free**, so multi-turn quarantined processing is unsupported. It is also **Python only** — .NET and Go agents get Agent Safety guidance and tool approval instead. AIRT should build test cases directly against this model: content that acquires a `trusted` label it shouldn't (a tool that returns third-party data without `source_integrity`), a sink reachable in untrusted context because it was never annotated, an exfiltration path through a sink whose cap is `user_identity`, label-laundering through a transformation tool, and injection delivered through `quarantined_llm` output — which is labeled untrusted but is still text the main model reasons over. AISPM should inventory FIDES adoption per agent, extract the label declarations on sources and sinks, and flag the four false-assurance configurations above. Source: https://learn.microsoft.com/en-us/agent-framework/agents/security

- **[ENDPOINT] [MEDIUM] ChatGPT's browser extension now covers Edge, Brave, Opera and Vivaldi, and the cloud browser can collect website credentials on web and mobile**: Two extensions of the browser-control surface reported on 2026-08-07, both **August 25**. **The extension footprint quadrupled**: ChatGPT's browser extension now works in **Microsoft Edge, Brave, Opera and Vivaldi** alongside Chrome, installed through **Settings > Computer Use** in the desktop app (with a "More browsers" expansion for browsers not listed), selected per chat by `@`-mention against the specific browser profile where the extension was installed. All five support tab mentions and browser control; Opera lacks side chat. The coverage consequence is concrete: any ENDPOINT collector that detects ChatGPT browser control by looking for the Chrome extension ID, or that enumerates one browser's extension inventory, now under-reports on four additional browsers — and it under-reports on the **profile** dimension too, since the grant is per-browser-profile and the same machine can hold several. ENDPOINT should enumerate the ChatGPT extension across all five browsers and all profiles, read the per-browser allowlist/blocklist as policy state, and treat cloud-browser website sign-in as an off-endpoint session grant that must be inventoried from the ChatGPT side because it is invisible locally. Sources: https://learn.chatgpt.com/docs/chrome-extension and https://learn.chatgpt.com/docs/browser

- **[AIDR] [MEDIUM] Gemini Enterprise data-connector telemetry now identifies which connector tool an agent invoked and how long it took — an ingestion opportunity with a six-week retention cliff**: On **August 24** Google extended Cloud Monitoring telemetry for Gemini Enterprise data connectors in two ways. The existing count metric **`discoveryengine.googleapis.com/dataconnector/request_count`** gained three dimensions on top of its existing `status`: **`tool_id`** — "the identifier of the connector tool invoked" — **`engine_id`**, the Gemini Enterprise app identifier, and **`response_code`**, the gRPC response status. And a **new metric, `discoveryengine.googleapis.com/dataconnector/request_latencies` (Beta)**, reports "the distribution of tool invocation latency" in milliseconds with dimensions `status`, `response_code`, `tool_id` and `engine_id`. **The `tool_id` dimension is the part that changes what Zenity can see.** Until now this metric answered "how many connector requests, and did they succeed"; it now answers "**which connector tool, in which app, with what result**" — which is per-tool invocation attribution on a platform where the previous best signal was the `execute_tool` / `invoke_connector` trace spans reported on 2026-08-09. Paired with the previous finding, this is the detection layer for exactly the risk that finding describes: a Supabase `execute SQL` or `deploy edge function` invocation is now distinguishable by `tool_id` from a benign read, and attributable to a specific `engine_id`. Source: https://docs.cloud.google.com/gemini/enterprise/docs/access-metrics
