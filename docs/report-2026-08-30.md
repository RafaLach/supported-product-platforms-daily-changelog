## Executive Summary

**Nine findings. The single most consequential one is that Anthropic shipped a specification for agents to operate physical laboratory and manufacturing hardware — and the second is that Microsoft has quietly built a full agent-security product that this monitor has never once read.**

**Anthropic previewed the Model Hardware Standard on August 27.** MHS is a shared specification for AI agents to safely operate physical devices, co-developed with HHMI Janelia. It defines a standardized driver layer with two primitives — `read` and `write` — a standardized device-discovery format so agents and instruments find each other across a network with no custom translator, and driver-embedded natural-language device metadata carrying weight, capabilities and **safety limits**. Agents drive it through three interfaces: **MCP, command-line interfaces, and code file APIs**. The demonstrated device classes are liquid handlers, 6-DoF robotic arms, microplate readers, two-photon and light-sheet microscopes, thermocyclers, qPCR instruments, centrifuges, incubators, cameras, sensors and laser systems. Preview partners are Genentech, UW's Baker and Pinglay labs, Carnegie Mellon, HHMI Janelia, QuEra Computing and Tetsuwan Scientific; **AWS/Strands, Tecan, QIAGEN and Universal Robots are building native MHS support into their platforms**. It is model-agnostic and Anthropic plans to open-source it. This is the first time an agent tool invocation in Zenity's threat model can move a robot arm or set a laser's power, and the only documented controls are driver-enforced device limits plus a human confirmation prompt.

**The larger coverage story is Microsoft.** Following the `office_agents` thread from the August 26 Anthropic release note into Defender's own documentation surfaced **an entire Microsoft agent-security product line that produces zero hits across `reports/`**: Defender for Endpoint **local AI agent discovery**, Defender for Endpoint **AI agent runtime protection**, Defender XDR **Security for AI** with real-time protection rules, the **Copilot Studio external threat detection provider** webhook, and the **Agent 365 SDK/CLI** with Entra agent identity blueprints. Four separate specifics matter for Zenity:

- **Microsoft now publishes an enumerated taxonomy of 25+ local AI agents** it discovers on Windows and macOS endpoints — Claude Code, Codex CLI, Gemini CLI, GitHub Copilot CLI, Junie CLI, Kiro CLI, OpenCode, Warp, Antigravity CLI, ChatGPT/Claude/Codex/Goose/Ollama/Perplexity/Poe Desktop, Hermes Agent, Cursor, Devin Desktop, Kiro IDE, Antigravity IDE, six VS Code extensions, and **OpenClaw, Clawpilot, QClaw and Claw/Nanobot** — together with their **local and remote MCP server configurations**. Several of these names have never appeared in a Zenity report.
- **Defender inspects agent-to-LLM network traffic.** `AiAgentNetworkInspection` extends prompt-injection blocking to agents with no vendor hook interface by inspecting the agent's LLM traffic in transit — and Microsoft documents the bypass in one sentence: it **"doesn't support agents that use certificate pinning or HTTP/3."**

### Claude Enterprise (Anthropic) — Model Hardware Standard, announced 2026-08-27

- **The Model Hardware Standard (MHS)**, a research preview opened to a first group of scientific research labs and advanced manufacturers, co-developed with **HHMI Janelia Research Campus**. ## New Coverage Required

- **[AIRT] [HIGH] Anthropic's Model Hardware Standard puts agent tool calls on the other side of a robot arm, a laser and a centrifuge**: On **August 27, 2026** Anthropic opened a research preview of the **Model Hardware Standard**, "a shared specification for AI agents to safely operate physical devices," co-developed with HHMI Janelia and being adopted natively by **AWS/Strands, Tecan, QIAGEN and Universal Robots**. The architecture matters more than the announcement. A **standardized driver** exposes exactly two primitives — **`read`** and **`write`** — to any device with a programmable interface. **Device discovery is standardized**, so "agents and instruments locate each other across networks" with no custom translator program, meaning the set of devices an agent can reach is a *network* property, not a configuration file. Drivers embed **natural-language metadata including the device's safety limits**, which is simultaneously the safety control and a machine-readable description of exactly what the limits are. Orchestration runs over **MCP, CLIs and code file APIs** — so the same MCP transport AIRT already models for data exfiltration now carries actuation. The demonstrated device set is liquid handlers, **6-DoF robotic arms**, microplate readers, two-photon and light-sheet microscopes, thermocyclers, qPCR instruments, centrifuges, incubators, cameras, sensors and **laser systems**. The documented controls are thin and explicitly probabilistic: driver-enforced device limits, plus an agent that "**often** stopped to wait for human confirmation before performing an action it deemed even slightly risky" — a model-judgement gate, not a policy gate. Carnegie Mellon's validation covers *hardware-state* failures (missing plate, rotated plate, reader busy, disconnected camera, unreachable device, e-stop), **not adversarial input**; nothing published tests what happens when the experiment protocol an agent reads contains injected instructions. AIRT should model MHS as a new actuation-capable tool class where the payoff of a successful prompt injection is physical rather than informational, and should build probes for: injected instructions in protocol documents, sample metadata and instrument output; agents chaining across **multiple instruments in parallel**, which Anthropic advertises as a feature; and whether the driver's declared safety limits can be read, reasoned about and approached asymptotically without tripping. AISPM should treat **MHS drivers, discovered devices, and device safety-limit metadata as new inventory entity types**, and flag agents holding MHS device grants as a distinct privilege class. It is model-agnostic and slated to be open-sourced, so this will not stay an Anthropic-only surface. Source: https://www.anthropic.com/news/model-hardware-standard-research-preview

- **[ENDPOINT] [HIGH] Microsoft publishes a 25-agent local-AI-agent taxonomy and discovers their MCP server configs on Windows and macOS — including four Claw-based agents Zenity has never named**: Defender for Endpoint's **local AI agent discovery** (Preview) automatically finds supported local AI agents **and their local *and remote* MCP server configurations** on onboarded Windows and macOS devices, then renders them as a **local AI agent inventory**, an **exposure map** linking agents to devices, identities and the resources those identities can reach, and **KQL advanced hunting**. Two things here are directly actionable. **First, the taxonomy is a published coverage checklist**: *CLI* — Claude Code, Codex CLI, Gemini CLI, GitHub Copilot CLI, **Junie CLI**, Kiro CLI, **OpenCode**, **Warp**, **Antigravity CLI**; *Desktop* — ChatGPT, Claude, Codex, **Goose**, **Hermes Agent**, **Ollama**, Perplexity, **Poe**; *Agentic IDEs* — Cursor, Devin Desktop, Kiro IDE, **Antigravity IDE**; *VS Code extensions* — Claude Code, **Cline**, Codex, **Gemini Code Assist**, GitHub Copilot, **Roo Code**; *Claw-based* — **OpenClaw, Clawpilot, QClaw, Claw/Nanobot**. The bolded names have no prior mention in this monitor's reports, and the Claw-based category in particular is an entire local-agent family Zenity has not been tracking. **Second, Microsoft's aggregation rule is a deliberate design choice Zenity should decide on consciously**: Defender "defines an agent as a combination of a user, a device, and an agent type," so Claude Code in 15 project folders is *one* entry. That is defensible for licensing and posture, but it collapses exactly the dimension that matters for blast radius — **which repositories, which working directories, and therefore which MCP configs and secrets each instance actually had in scope**. If Zenity adopts the same tuple it inherits the same blind spot; if it keeps per-workspace granularity, its counts will not reconcile with the customer's Defender console, and that discrepancy needs an answer ready. Source: https://learn.microsoft.com/en-us/defender-endpoint/local-agent-discovery-overview

- **[AIRT] [HIGH] Defender now inspects agent-to-LLM network traffic for prompt injection, and documents its own bypass in one sentence**: **AI agent runtime protection** (Preview) blocks prompt injection at the device level by inspecting three points in the agent loop — the **user prompt**, the **pre-tool call before execution**, and the **post-tool response**. It ships two independent mechanisms, both with `Disabled`/`Audit`/`Block` modes: **`AiAgentProtection`**, which rides the agent's own vendor hook interface (**Claude Code hooks, Codex CLI hooks, GitHub Copilot CLI hooks, GitHub Copilot app hooks**), and **`AiAgentNetworkInspection`**, which inspects the **agent-to-LLM network flow in transit** for agents that expose no hook interface. The second mechanism is the finding. Microsoft is putting a TLS-terminating inspection point on the wire between local agents and model endpoints, and states the evasion condition outright: it **"doesn't support agents that use certificate pinning or HTTP/3."** That is a directly testable bypass — an agent that pins its certificate or negotiates HTTP/3 to its model endpoint is invisible to network inspection, and if it also exposes no hook interface it has **no runtime protection at all** while the tenant's console reports the feature as enabled. AIRT should build exactly that probe: enumerate which agents on a protected host pin certificates or use HTTP/3, cross it with which agents expose vendor hooks, and report the intersection as unprotected-but-believed-protected. Three secondary gaps compound it. The hook-based path covers **four agents** out of the 25+ Microsoft itself discovers, so agent-native inspection is the exception rather than the rule. There is **no native Intune policy support** — enablement is a PowerShell platform script that "Intune normally runs once," so drift after re-imaging or a failed run is silent and there is no policy object to audit. And the whole feature is off unless someone explicitly turned it on, per device, per method. AIRT should also treat the **"Suspicious AI prompt injection"** alert as a corroborating signal to ingest where present, and AISPM should treat `AiAgentProtection`/`AiAgentNetworkInspection` mode per device as a posture attribute — `Audit` is not `Block`, and Microsoft recommends organizations sit in `Audit` for weeks. Sources: https://learn.microsoft.com/en-us/defender-endpoint/ai-agent-runtime-protection-overview and https://learn.microsoft.com/en-us/defender-endpoint/configure-ai-agent-runtime-protection

- **[AIDR] [HIGH] Copilot Studio ships a documented allow/block webhook for every tool invocation — and it fails open in one second, per environment, with no tenant-wide enforcement**: Copilot Studio's **external threat detection** integration (Preview) is a "bring your own protection" contract: whenever the orchestrator considers invoking a tool, it POSTs to a partner-implemented REST endpoint and honours `{"blockAction": true|false}`. The API is fully specified at `api-version=2025-05-01` with two endpoints — **`POST /validate`** for health and **`POST /analyze-tool-execution`** for the decision — and the request body is the richest agent-runtime payload Microsoft has published: **`plannerContext`** (the user message, the planner's own **`thought`** explaining why it chose this tool, **`chatHistory[]`**, and **`previousToolOutputs[]` including output values**), **`toolDefinition`** (id, type, name, description, input and output parameters), **`inputValues`** (the actual arguments about to be passed — Microsoft's own example is a `bcc` of `hacker@evil.com`), and **`conversationMetadata`** (agent id/tenant/environment/version/`isPublished`, the user's **Entra object ID**, trigger id and schema, `conversationId`, `planId`, `planStepId`, `parentAgentComponentId`). This is simultaneously an integration path Zenity can implement and a set of defects Zenity should be detecting in customer tenants. **Four of them.** *It fails open*: "The agent expects a response … within less than 1,000 ms … If your system doesn't respond in time, the agent behaves as if your response is 'allow', invoking the tool" — the default error behaviour is **Allow the agent to respond**, and flipping it to **Block the query** is an explicit opt-in, so a slow or degraded provider silently degrades to no enforcement. *It cannot be enforced centrally*: "There's no global or tenant-wide setting… no PowerShell, API, or admin center setting to enforce or propagate this configuration globally for other existing or future environments" — so protection must be re-enabled by hand on **every environment created from now on**, and a new environment is an unprotected environment by default. *It does not cover classic agents*: "External threat detection is only called on generative agents that use generative orchestration. External threat detection is skipped for classic agents." *And only one provider slot exists per environment* — configuring Defender as the provider means no other vendor is in the path. AIDR should model the `analyze-tool-execution` payload as a first-class runtime event source and, independently, AISPM should audit per environment: is a provider configured at all, is the error behaviour set to Block or left on Allow, which environments were created after the last review, and what fraction of agents in each environment are classic and therefore never evaluated. Sources: https://learn.microsoft.com/en-us/microsoft-copilot-studio/external-security-provider and https://learn.microsoft.com/en-us/microsoft-copilot-studio/external-security-webhooks-interface-developers

- **[AISPM] [HIGH] Defender's real-time protection covers Agent 365 agents only through Work IQ MCP — the uncovered set is defined by which tools an agent happens to use**: Defender XDR **Security for AI** turns on **automatically, with the Enable toggle on by default**, the moment a tenant onboards to Agent 365, and it brings discovery, posture assessment via prebuilt Advanced Hunting queries, near-real-time detections and **real-time protection rules**. The rules model is a built-in **Default rule that audits all agents** plus **custom rules that block**, scoped to all or specific agents, matching on four detection types — **Secret exfiltration, Malicious content propagation, Evasion techniques, Unsafe email domain** — and writing every audited or blocked action as a behaviour to the **`BehaviorInfo`** table. Three sentences in that documentation define coverage gaps precisely enough to detect. **First**: Agent 365 real-time protection works via **Work IQ MCP**, "including invocations of customer MCP tools onboarded to Agent 365," and then — "**Agents that rely on unsupported tools or don't integrate with Work IQ MCP aren't covered.**" So an agent's protection status is a function of its *tool mix*, changes whenever a maker adds a tool, and is invisible from the agent's own configuration page. AISPM should compute, per agent, the fraction of its tools that route through Work IQ MCP and flag agents with unonboarded MCP tools as unprotected-in-practice. **Second**: the exclude-agent picker states that "**Only agents with a Microsoft Entra agent ID appear in the list**" — meaning an agent without an Entra Agent ID cannot be reasoned about by these rules at all, which makes *absence of an Entra Agent ID* a posture finding with teeth rather than a hygiene note. **Third**, and counter-intuitive: "**When a blocking rule covers an agent, near-real-time alerts aren't generated for that agent**" — turning on enforcement *removes* the alert stream for that agent, leaving only `BehaviorInfo` behaviours. Any Zenity ingestion that keys on Defender alerts will see agent coverage silently drop the day a customer moves from audit to block; the behaviours table is the durable source. Coverage also differs by platform in a way worth encoding: **Foundry agents are evaluated on user requests, agent responses, tool invocations *and* tool responses**, while **Copilot Studio agents are evaluated at tool invocation only** — so the same policy intent yields different enforcement depth depending on where the agent was built. Source: https://learn.microsoft.com/en-us/defender-xdr/security-for-ai/ai-agent-real-time-protection

- **[AISPM] [HIGH] Agent 365 auto-ingests AWS Bedrock and GCP Vertex AI agents with no code change, and every Entra agent identity is minted by a blueprint whose permissions are inherited by all of them**: Two structural facts from the Agent 365 developer documentation reshape how Zenity should model Microsoft agent inventory. **First, Agent 365 is now a cross-cloud registry.** For Vertex AI and Bedrock agents, "Registration … requires **no development work** — agents are **pulled automatically via the Google and Amazon APIs**. No SDK integration, no blueprint, and no code changes are required." A tenant that enables Agent 365 therefore acquires an inventory of AWS and GCP agents without those agents' owners doing anything, and Defender's discovery correspondingly spans **Copilot Studio, Foundry, AWS Bedrock and GCP Vertex AI**. AISPM must expect a customer's Microsoft-side agent inventory to contain non-Microsoft-cloud agents, must not treat an agent appearing in both Agent 365 and Zenity's AWS/GCP inventory as two agents, and should use the Agent 365 registry as a cross-check on its own cloud discovery — a Bedrock agent that Google/Amazon's APIs surfaced to Microsoft but that Zenity's AWS collector missed is a discoverable gap. **Second, the Entra agent identity blueprint is the real privilege primitive, not the agent identity.** A blueprint is "an object in Microsoft Entra ID that serves as a template for creating agent identities" and is itself a special identity type that can perform exactly one operation — provision or deprovision agent identities — using its own OAuth client ID, credentials and the **`AgentIdentity.CreateAsManager`** Graph permission. **Credentials are configured on the blueprint**, and "**OAuth permissions granted to an agent identity blueprint are granted to ALL agent identities created from that blueprint**." **Inheritable permissions** go further: "When an administrator grants permissions on the blueprint principal from an inheritable resource app, **all agent identities in that organization receive those permissions automatically**" — a single consent action that silently re-privileges every existing and future agent of that type. Conditional Access targets blueprints; disabling a blueprint kills authentication for all its identities. And blueprints can be **multitenant and published through Microsoft catalogs**, so a customer can add a *third-party* blueprint to their tenant and it can then mint agent identities there — the agent-identity equivalent of a multitenant app registration. AISPM should inventory `agentIdentityBlueprint` objects and blueprint principals as first-class entities via Microsoft Graph, map blueprint → agent identities, evaluate permissions **at the blueprint level** rather than only per agent, flag inheritable-permission grants as fan-out privilege events, flag multitenant and third-party-published blueprints present in a tenant, and treat a blueprint's `AgentIdentity.CreateAsManager` grant as an agent-minting capability. Sources: https://learn.microsoft.com/en-us/microsoft-agent-365/developer/ and https://learn.microsoft.com/en-us/entra/agent-id/agent-blueprint

- **[AISPM] [HIGH] Salesforce Agentforce Operations — a GA back-office agent product reaching ERP, email and collaboration systems that this monitor has never reported**: **Agentforce Operations** has been generally available since **April 29, 2026** — the productized form of the **Regrello acquisition that closed October 1, 2025** — and returns **zero hits across every report this monitor has written**. It is not an incremental Agentforce feature; it is the extension of Agentforce agents out of CRM-adjacent front-office work and into **"the processes and systems that run the business"** — explicitly **email, ERP and collaboration tools** — for "end-to-end agentic execution across the back office," on the stated premise that "agents are designed to **complete** work rather than route it." That framing is the risk: these are write-capable agents in financial and operational systems of record, and Salesforce describes them as **"specialized back-office agents [that] autonomously perform work across disconnected systems from email to ERP."** The documented agent behaviours are specific — extracting data from complex documents, running computations, **updating credit models**, identifying compliance gaps, and performing **data verification, approvals and compliance checks** — which means an agent is executing the control that a human control-owner would otherwise perform, and the approval step itself becomes an agent action. Three inventory surfaces come with it. **Blueprints**: 30+ out-of-the-box templates (invoice auditing, onboarding, PO rescheduling) *plus* the ability to **generate blueprints from unstructured process documents** — the authoritative definition of what an agent may do can be produced by a model reading a Word document, which is both a new entity type and a new injection path into agent scope; and business users edit those processes **in plain language, without code**. **Cross-platform surfaces**: work is brought to **Slack and Microsoft Teams**, so an Agentforce agent's actions and prompts leave the Salesforce trust boundary into two other collaboration platforms Zenity monitors separately. **Flow integration**: auto-sync and the ability to **trigger actions with Salesforce Flows** was slated for beta in May 2026, connecting agent decisions to the existing Flow automation estate. AISPM should discover Agentforce Operations deployments, inventory **process blueprints** (including which were model-generated from documents, and from which documents), map each specialized agent's reach into ERP, mail and Slack/Teams connectors, and build toxic-combination rules for the pattern this product creates by design: an agent that both **performs** a business action and **approves** it, or that holds a compliance-check role over data it can itself modify. Note the discovery lesson too — this was found only because a WebSearch for late-August Salesforce news surfaced the announcement; four months of scans against the configured Salesforce URLs, all of which return 403, produced nothing. Source: https://www.salesforce.com/agentforce/operations/

- **[AISPM] [MEDIUM] Gemini Enterprise added five data stores and gave AirOps, Airtable and Zoho Desk write actions, including Airtable record creation**: The August 28 release-note entry brings **Campfire, Clay, CourtListener, Daloopa and MSCI** into public preview as data stores an agent can "search and read … using natural language," and — the part that matters more — grants **new actions** to three connectors that previously read: **AirOps** gains *"Update knowledge base document metadata"*, **Airtable** gains *"Create records for a table"*, and **Zoho Desk** gains *"Update event."* This is the same read-to-write drift reported on 2026-08-21 for Supabase, and it is now a pattern rather than an incident: Google keeps widening the action surface of already-connected data stores without the connector itself appearing as a new entity, so an inventory captured before the change understates what the agent can do afterward while the connector list looks unchanged. **AirOps updating knowledge-base document metadata is the sharpest of the three** — it lets an agent modify the metadata of the corpus that grounds agents, which is a self-referential integrity problem: poisoned or retitled knowledge-base entries change what future retrievals surface. Airtable record creation is straightforward agent-driven data writing into a system many organizations use as an operational database. AISPM should enumerate Gemini Enterprise data stores **with their per-connector action lists**, treat any read-to-write action addition on an existing connector as a privilege-change event requiring re-evaluation rather than a catalogue update, and specifically flag write access to knowledge-base or grounding corpora as distinct from write access to business records. The five new data stores are additional inventory entities, two of which — **Daloopa and MSCI** — are financial-data sources, matching the pattern already seen in Claude for M365's S&P Global / LSEG / Daloopa connector set. Sources: https://docs.cloud.google.com/gemini/enterprise/docs/connectors/manage-actions and https://docs.cloud.google.com/gemini/enterprise/docs/connectors/msci

- **[ENDPOINT] [MEDIUM] Cursor Cloud Agents can now create code with no source-control connection and publish it to a live public URL**: The August 27 Cursor release removes the last two things that anchored agent-produced code to a reviewable location. **"Start from scratch"** lets a Cloud Agent begin with **no GitHub or third-party SCM connection at all** — Cursor "automatically creates an Origin repo in the background," and the user only later decides whether to name it and set visibility. So work now exists in Cursor-hosted storage *before* any repository the organization knows about is created, and if the user never clicks *Create repo*, there may be no named artifact for an inventory to find. **Port-forwarded live preview** exposes the agent's cloud environment directly to the developer's browser, and **Publish with Vercel** turns the result into a **live URL** on a connected Vercel account. Chained, that is a complete path from prompt to internet-reachable application with **no git host, no pull request, no review, and no artifact in any system the security team currently enumerates** — the agentic version of shadow IT, and a data-egress path if the agent's environment held organizational context. This extends, rather than repeats, the **Cursor Origin** git-forge finding of 2026-08-21: Origin established that Cursor hosts code; this establishes that code can now originate and terminate entirely inside Cursor and Vercel. ENDPOINT and AISPM should enumerate Origin repositories including unnamed background-created ones, treat a connected **Vercel** account on a Cursor org as a publication capability requiring inventory, and correlate published URLs back to the originating agent session and prompt. Note also, as standing context rather than a new item, that Cursor's **Google Workspace plugins** (August 3) already give agents Gmail send/read, Drive read-and-create and Calendar write — so the same agent that can publish to the internet can also read the user's mailbox. Sources: https://cursor.com/changelog/start-from-scratch and https://cursor.com/docs/origin/create-repository
