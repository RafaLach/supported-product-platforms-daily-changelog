## Executive Summary

**Twelve findings. Microsoft shipped an agent type that holds a real employee account in the tenant; Anthropic turned agent fleets into infrastructure-as-code and moved tool authorization from the client to the server; and ServiceNow's Zurich release reached GA with a "publish managed agents to external registries" capability that has no coverage at all.**

**The single most consequential item is Microsoft Foundry's autopilot.** Foundry now documents a **third agent type** whose defining property is not a capability but an identity: an autopilot holds an **Entra agent user account** in addition to the agent identity every Foundry agent already has. That account gives it **its own email, calendar, OneDrive, Teams presence, a place in the organization chart, and a manager** — and lets it "perform Microsoft 365 actions as itself" rather than on behalf of a signed-in user. Microsoft is explicit that "the distinction between an agent and an autopilot is binary." You don't build an autopilot; you build a **blueprint** that teams "hire" into per-team instances, each with its own identity, its own agent user account and its own team-scoped access. That is a one-to-many fan-out from a single governed object into an unbounded set of mailbox-holding principals. The autopilot articles were published in the August Foundry roll-up that this monitor mined on 2026-09-02, but the autopilot pages themselves were **not** read then — they were in the held-back list. That was a miss, and it is corrected here.

**Anthropic shipped two structural changes to how agents are defined and how their tools are authorized.** `ant apply` (CLI 1.30.0, September 3) makes **agents, environments, skills, memory stores and scheduled deployments declarative files in a Git repository**, reconciled against the API and pinned by a committed `claude-lock.json`. A skill reference can be a **raw GitHub URL** that `ant apply` downloads and uploads. CI runs it under **Workload Identity Federation**. An agent fleet's definition now lives in source control and changes through pull requests — which is good hygiene and a completely new place Zenity has to look. Separately, the new **`auto` permission policy** (September 10) moves per-call tool authorization **to Anthropic's server**: the server evaluates each agent-toolset and MCP-toolset call against the tool, its input, and the session content so far, and **runs it, denies it, or pauses it**. A server-side denial **cannot be overridden by the client**. The evaluation is exposed on every `agent.tool_use` and `agent.mcp_tool_use` event as `evaluated_permission` plus an `evaluation` object with a `reason_code`. Anthropic also documents the injection surface in plain terms: the server reads `user.message` content **as your intent**, and "if you relay untrusted end-user input in `user.message` events, the server reads that input as your intent too, and it can get a call allowed."

**AgentCore added a hosted consent surface.** The **Consent Portal** is an AWS-managed, AWS-hosted web portal that authenticates end users to an OIDC IdP and collects their consent before an agent acts on their behalf. It is a new resource with its own create/get/list/update/delete operations, attaches to a single Gateway, and "keeps the OAuth flow server-side: the browser never holds a token." A new consent-granting UI in the delegation path is exactly the kind of object that needs inventory.

**ServiceNow's Zurich release is GA and it is agent-heavy.** The family index remains useless, but the Zurich highlights page renders: **Build Agent** (natural-language app creation inside ServiceNow Studio, now with expanded **MCP support** and the ability to create apps and metadata **in the global scope**), **Machine Identity Access Controls** enforcing REST/SOAP endpoint access for non-human identities, a redesigned **AI Control Tower** with deduplication, kill switches and AI Service Graph Connectors across AWS/Microsoft/GCP, and — with **zero hits across every prior report** — **"publishing managed agents to external registries."**

### Claude Enterprise (Anthropic) — September 3 to September 18

- **`ant apply` — infrastructure-as-code for agent fleets (CLI ≥ 1.30.0, September 3).** Creates and updates **agents, environments, skills, memory stores and deployments** from files in a repository. Agents are Markdown (frontmatter = config, body = system prompt); environments and memory stores are YAML; deployments are Markdown whose prose "becomes the message that starts each session"; a skill is a directory with `SKILL.md` uploaded as one bundle. Kind is inferred from a `type` field, the containing directory (`agents/`, `environments/`, `memory_stores/`, `deployments/`), or a filename prefix. Resources reference each other **by relative path** and `ant apply` resolves them in dependency order. **A skill reference can be a GitHub URL** (`https://github.com/<owner>/<repo>/tree/<branch>/<dir>`) that `ant apply` downloads and uploads, pinned to the resolved commit until `--upgrade`. State lives in a committed **`claude-lock.json`** recording each resource's kind, ID, version and two hashes (what was sent, what the API returned) plus the bound `organization_id` and `workspace_id`. CI guidance is `ant apply --yes .` on the default branch, authenticated with **Workload Identity Federation**, and the command "refuses credentials that resolve to any other organization or workspace." `--force` overwrites out-of-band edits; `--prune` archives resources whose files were deleted. Source: https://platform.claude.com/docs/en/cli-sdks-libraries/cli/apply
- **`auto` permission policy — server-side per-call tool authorization (September 10).** A third policy alongside `always_allow` and `always_ask`. "The server evaluates each call before it runs… Because the evaluation considers the tool, the call's input, and the session's content up to that point, the server can treat two calls to the same tool differently." Three outcomes: the call runs; the call is **denied** (the agent gets `Permission to use {tool_name} has been denied.` with `is_error: true`, and "your client cannot override the denial"); or the call **pauses** for approval. Defaults are unchanged — agent toolset `always_allow`, MCP toolsets `always_ask`, and "no toolset uses `auto` by default." Anthropic's own warning: "`auto` is not a human checkpoint. If the server determines that a call is safe, the call runs before anyone sees it, and its effects might not be reversible." Source: https://platform.claude.com/docs/en/managed-agents/permission-policies
- **New event fields on every tool call.** Under **any** policy, `agent.tool_use` and `agent.mcp_tool_use` events now carry **`evaluated_permission`** (`"allow"` / `"ask"` / `"deny"`) and, in most cases, an **`evaluation`** object whose `type` names the resolving policy; under `auto` it nests the server's determination plus a **`reason_code`** (`high_risk`, `indeterminate`). `evaluation` is **absent** when the agent names a tool that isn't enabled (denied without policy evaluation) and on events recorded before the field existed. `agent.custom_tool_use` carries neither field. Source: same
- **`ant beta:sessions connect` (September 10)** — attaches a terminal to a running Managed Agents session, shows waiting tool calls and sends the `user.tool_confirmation` event interactively; `--web` serves a session viewer locally. Source: https://platform.claude.com/docs/en/cli-sdks-libraries/cli/sessions-connect
- **Compact-on-demand (beta, September 14)** — a top-level **`compaction`** parameter on the Messages API under the `compact-2026-09-04` beta header. The API returns a **signed `compaction` block** summarizing prior messages, and can "keep recent turns word-for-word while preserving thinking validity." Source: https://platform.claude.com/docs/en/build-with-claude/compaction
- **Compliance API: Claude in Chrome sessions (beta, September 18).** The local session endpoints now return transcripts with **`product_surface: claude_in_chrome`**. The covered surface list is now **Cowork, Claude Code, Claude Science, Claude for Microsoft 365, and Claude in Chrome**; Cowork and Claude Code are stable, the other three are beta. No new key, scope, setting or client update is required — the existing Compliance Access Key with `read:compliance_user_data` works. Source: https://platform.claude.com/docs/en/manage-claude/compliance-sessions

## New Coverage Required

- **[AISPM] [HIGH] Microsoft Foundry autopilots are agents that hold a real Entra *user* account — mailbox, calendar, OneDrive, Teams presence and a manager — and one blueprint fans out into an unbounded set of them**: Foundry now documents a **third agent type** whose definition is identity, not capability. "An autopilot is a type of agent that works under its own identity as a persistent, named member of your organization. It holds a standing role rather than answering one request at a time." Every Foundry agent already carries an Entra **agent identity** (a service principal). What makes an autopilot different is that it **also** carries an Entra **agent user account** — a *user object* — and Microsoft enumerates exactly what that buys: "its own email, calendar, OneDrive, Teams presence, and a place in the organization chart," plus the ability to "perform Microsoft 365 actions **as itself**." Microsoft states the test plainly: "An agent either has its own agent user account or it doesn't, which is what makes identity a reliable definition. The distinction between an agent and an autopilot is **binary**." **This collapses the boundary Zenity's M365 and Entra collectors rely on.** An autopilot appears in the tenant's user object space, in the org chart, and in mail and Teams traffic as a named member of staff; it can act in **group chats** where no single user's permissions apply; and it "can act without being prompted" in response to events with **no user in the loop at all** — which is precisely the scenario Microsoft says motivated the feature. Any inventory, DLP rule, sharing-risk calculation or anomaly baseline that partitions principals into "humans" and "service principals" will now classify autopilots on the wrong side of the line. **The fan-out is the second half of the finding.** "You don't build an autopilot. You build a blueprint that teams use to create their own autopilot instances, each with its own identity and its own team-scoped access." A regular Foundry agent is one-to-one — one agent, one blueprint, one agent identity, no user account. An autopilot blueprint is **one-to-many**: one blueprint, many *hired* instances, and **each instance gets its own agent identity *and* its own agent user account**. So a single reviewed, approved object silently becomes N mailbox-holding principals with N different access grants, each scoped by whichever manager hired it. Microsoft's own argument for the design is that it prevents ten teams from building ten near-identical agents whose "controls drift apart," and that argument is sound — but the inventory consequence is that **the governed object and the acting principal are different objects at different cardinalities**, and only the blueprint is centrally reviewed. Three specifics are directly actionable. **First, the blueprint is the kill switch**: "Update the blueprint and every instance updates. Block the blueprint and every instance stops." AISPM should model the blueprint→instance relationship as a first-class inventory edge, because it is simultaneously the blast radius of a bad change and the only single point of containment. **Second, only Foundry *hosted* agents can be published as autopilot blueprints**, which ties this directly to the hosted-agent surface already tracked — including the **bring-your-own-registry** path reported on 2026-09-02, meaning an autopilot's container image can originate outside Azure entirely. **Third, Microsoft draws a tool/data distinction Zenity should adopt verbatim as a rule**: "Holding a tool isn't the same as holding access to the data behind it. Giving an autopilot a SharePoint tool doesn't give it any SharePoint site, and giving it a mailbox doesn't give it the ability to send mail." Effective reach is therefore the **intersection** of the blueprint's tool grants and the instance's resource grants, and an inventory that reports only one of the two will systematically over- or under-state what an autopilot can do. AISPM should discover autopilot blueprints as an entity distinct from agents, enumerate hired instances per blueprint, resolve each instance's **agent user account** back to its Entra user object and its **manager**, join that user object against mailbox, OneDrive, Teams and SharePoint permission grants the same way it would for a human, and flag: an autopilot user account with no manager assigned; an instance whose resource grants exceed its sibling instances from the same blueprint; a **company-wide** autopilot (Microsoft's own pattern for "one production instance per business process") holding tenant-wide scope; and a **personal** autopilot created by a single user outside any review. AIDR should treat activity from an agent user account as agent activity, not human activity, wherever the two are currently conflated. Note the correction: these pages were published in the August Foundry roll-up and were in the material this monitor held back on 2026-09-02 without reading. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/autopilot-overview

- **[AIDR] [HIGH] Anthropic moved per-call tool authorization onto its own server, added a decision record to every tool event, and documented the prompt-injection path into it**: The new **`auto` permission policy** (September 10, `managed-agents-2026-04-01` beta) is a third option alongside `always_allow` and `always_ask`, and it changes where the authorization decision happens: "the server evaluates each call before it runs. Because the evaluation considers the tool, the call's input, and the session's content up to that point, **the server can treat two calls to the same tool differently**." Three outcomes — run, **deny**, or pause for approval — and the denial is final: the agent receives `Permission to use {tool_name} has been denied.` with `is_error: true`, and "**your client cannot override the denial**." Sending a `user.tool_confirmation` for a server-denied call is rejected with a 400. **Three things follow for Zenity.** **First, there is now a decision record on every tool call, under every policy.** `agent.tool_use` and `agent.mcp_tool_use` events carry **`evaluated_permission`** (`"allow"` / `"ask"` / `"deny"`) and, in most cases, an **`evaluation`** object naming the resolving policy; under `auto` it nests the server's determination and a **`reason_code`** of `high_risk` or `indeterminate`. This is a genuinely new, free, first-party detection signal — **a `deny` with `reason_code: high_risk` is Anthropic telling you an agent tried something its own classifier judged dangerous**, and AIDR should ingest it as a first-class alert rather than as event metadata. Two absence cases must be handled correctly or they will read as gaps: `evaluation` is missing when the agent names a tool that isn't enabled (the server denies without evaluating, so `evaluated_permission: "deny"` with no `evaluation` means *unknown tool*, not *blocked by policy*), and it is missing on events predating the field, which Anthropic says to read as `always_allow` when the outcome is `allow` and `always_ask` when it is `ask`. `agent.custom_tool_use` carries neither field, so **custom tools remain entirely client-authorized and produce no decision record at all** — that is the blind spot in this telemetry and it is where an adversary would put the tool that matters. **Second, `auto` is an injection target and Anthropic says so.** "What you post in `user.message` events counts as your intent, and it can lead the server to allow a call it would otherwise deny." The server "assesses but does not take instructions from" tool results, fetched webpages, MCP responses, or messages between session threads — but `user.message` is trusted, and: "**If you relay untrusted end-user input in `user.message` events, the server reads that input as your intent too, and it can get a call allowed.**" That is an explicit, vendor-documented privilege-escalation path in any application that forwards end-user chat into a Managed Agents session, which is the overwhelmingly common architecture. **AIRT should build this as a probe**: place attacker-controlled text in `user.message`, attempt a tool call the server denies without it, and measure whether the denial flips. **Third, `auto` will be mistaken for a control it is not.** Anthropic's own warning: "`auto` is not a human checkpoint. If the server determines that a call is safe, the call runs before anyone sees it, and its effects might not be reversible." AISPM should inventory the resolved permission policy **per toolset and per tool** (defaults are agent toolset `always_allow`, MCP toolsets `always_ask`, and no toolset uses `auto` by default), flag any agent that **downgraded an MCP toolset from `always_ask` to `always_allow` or `auto`**, flag `auto` on destructive tools such as `bash`, and record that **running sessions keep the toolset configuration they were created with** — so a policy tightening does not take effect on sessions already in flight, and a point-in-time posture read will disagree with live session behavior. Source: https://platform.claude.com/docs/en/managed-agents/permission-policies

- **[AISPM] [HIGH] `ant apply` turns Claude agent fleets into Git-managed infrastructure — including skills pulled straight from GitHub URLs — and the authoritative inventory is now a lockfile in a repository**: `ant apply` (CLI ≥ 1.30.0, September 3) "creates and updates Claude API resources from files: **agents, environments, skills, memory stores, and deployments**. They live in your repository and change through the same review as your code." This is the Claude platform's answer to Terraform, and it relocates the source of truth for an agent fleet **out of the Anthropic Console and into version control**. Five properties matter. **First, the resource set is the whole attack surface.** An agent file's frontmatter is its configuration and its body is its **system prompt**; an **environment** YAML declares the sandbox including `networking: {type: unrestricted}`; a **memory store** YAML declares persistent cross-session state; a **deployment** Markdown carries a **cron schedule** and prose that "becomes the message that starts each session" — i.e. **an unattended, recurring agent trigger defined in a text file**. Every one of these is an entity Zenity already models, and all of them now change by pull request. **Second, skills can be pulled from arbitrary GitHub URLs.** A skill reference may be `https://github.com/<owner>/<repo>/tree/<branch>/<dir>`, which `ant apply` "downloads and uploads," pinned to the resolved commit **until you run with `--upgrade`** (with `GITHUB_TOKEN` for private repositories). That is a third-party supply-chain edge into an agent's capability set, expressed as one line of YAML, and the pinning is only as good as the discipline around `--upgrade`. This is the [[agent-plugins-cross-vendor-standard]] pattern again: capability arriving from a repository rather than from a platform control plane. **Third, `claude-lock.json` is the inventory artifact and it is committed to the repo.** It records, per file, the resource `kind`, its API `id`, its `version`, and **two hashes** — `hash` (what was last sent) and `remote_hash` (what the API returned) — plus the bound `organization_id` and `workspace_id`. Zenity should read this file directly: it is a complete, machine-readable manifest of an organization's declared agents, and the hash pair is a **drift detector** — a mismatch means a resource was changed outside the files, which `ant apply` refuses to overwrite without `--force`. AISPM should treat the presence of `--force` in a CI pipeline as a finding, because it means declared state is being pushed over out-of-band changes without review. **Fourth, CI runs under Workload Identity Federation.** Anthropic recommends `ant apply --yes .` on the default branch after merge, authenticated by WIF rather than a stored key, and the command "refuses credentials that resolve to any other organization or workspace." Good design — and it means **a CI identity now holds create-and-update rights over an organization's entire agent fleet**, which AISPM should enumerate as a privileged non-human principal alongside the personal and service-account keys reported on 2026-09-02. **Fifth, the adoption gap is real and detectable**: `ant apply` "can't adopt a resource you created in the Console or with `ant beta:agents create`," and applying a file describing an existing agent **creates a second one**. So organizations mid-migration will have duplicate agents, and only the lockfile-tracked half is governed by code review.
