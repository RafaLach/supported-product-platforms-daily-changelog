## New Coverage Required

- **[AISPM] [HIGH] AgentCore "Export harness to code" — a one-command escape hatch out of managed-harness governance**: `agentcore export harness` takes a managed AgentCore harness and emits the equivalent agent as editable Strands Python, which can be deployed to AgentCore Runtime *or to Lambda, ECS/Fargate, EC2, Kubernetes, an on-premise server, or any container host*. Everything that made the harness governable travels with it as plain code — the model provider config **including API key references**, remote MCP tool and Gateway bindings, the built-in `shell` and `file_operations` tools, AgentCore Browser and Code Interpreter, filesystem mounts (session storage, EFS, S3), execution limits and **authorizer configuration** — but the declarative harness resource that Zenity inventories no longer governs the running agent. The exported agent is a new, separate runtime entity; if it is self-hosted, it leaves the AWS control plane entirely while still holding the original credential references. AISPM needs to treat export as a high-signal lifecycle event (a harness whose capabilities now exist in an untracked copy), inventory the generated runtime agent as a distinct entity, and flag the self-hosted case as an agent operating outside any discoverable control plane. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-export.html

- **[AISPM] [MEDIUM] AgentCore harness managed memory is provisioned by omission and deleted by cascade**: When a harness is created through the service API **with the memory configuration left out, the service silently provisions a managed AgentCore Memory resource** — the AgentCore CLI defaults the opposite way (disabled unless explicitly chosen), so the same logical harness has opposite memory posture depending on which path created it. Managed memory runs four long-term extraction strategies (`SEMANTIC`, `SUMMARIZATION`, `USER_PREFERENCE`, `EPISODIC`) that distill durable knowledge out of conversations into `actorId`-scoped namespaces (e.g. `/summary/{actorId}/{sessionId}/`), and retrieval is **automatic with no configuration** — every invocation queries long-term memory at `topK=10`, `relevanceScore=0.2` and injects the results into context before the model reasons. Two inventory consequences: managed memory **cannot be deleted through the Memory APIs** and is cascade-deleted by `DeleteHarness` unless `deleteManagedMemory=false` is passed, so it is a memory store whose lifecycle is not independently manageable; and because `actorId` is supplied by the caller at `invoke_harness` time rather than derived from an authenticated principal, memory isolation between users rests on a caller-controlled string. AISPM should inventory harness-managed memory as a first-class store (distinct from BYO `agentCoreMemoryConfiguration`), record its active strategies, and treat an API-created harness with no explicit memory block as memory-enabled by default. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-memory.html

- **[AIRT] [HIGH] Anthropic Cyber Verification Program consolidates into three safeguard-reduction tiers and absorbs Project Glasswing**: On 2026-10-06 Anthropic merged the original Cyber Verification Program and Project Glasswing into a single program with three named tiers — **Defense Access** (SOC/IR work, malware reverse engineering, vulnerability analysis), **Red Team Access** (adds authorized pen testing; real-time blocks remain only for physical harm and mass disruption — ransomware deployment, damaging physical systems, pen testing high-risk safety systems), and **Specialized Access** (**the fewest cyber blocks of any tier**, reserved for organizations authorized to test flight operating systems, power grids, telecom networks, interbank transfer infrastructure and government administrative networks). Every tier grants Claude Opus 5.5, Claude Sonnet 5.5 and **Claude Mythos 5.1** — a model line Zenity does not see on standard entitlements. This is the fourth confirmed instance of Anthropic's **guardrail-by-entitlement** pattern: the safeguards are removed per-entitlement, not per-model, so an organization's effective model behavior is determined by an out-of-band approval Zenity cannot read from the API. AIRT's consequence is direct — a red-team probe run against a CVP-entitled key will *not* reproduce the refusal behavior seen on a standard key, so refusal-based guardrail tests silently pass while the deployed configuration has materially fewer blocks. AIRT should model tier as an input to every Anthropic guardrail assertion and treat Mythos 5.1 availability as the detectable signal that an elevated tier is in force. Source: https://www.anthropic.com/news/cyber-verification-program

- **[AISPM] [MEDIUM] OpenAI Decisions API is now a callable endpoint with a published schema**: The Decisions API, reported 2026-10-01 as a DevDay announcement with no public schema, shipped in beta on 2026-10-06. It is `POST /v1/decisions` on model `gpt-6-luna`, taking an `input` (text, or user messages mixing `input_text` and base64-inline `input_image` parts) plus a `questions` array, and returning an `answers` array of three types: **predicate** (probability 0–1), **choice** (a selected value from caller-supplied options, with a full probability distribution and confidence), and **score** (a probability-weighted average over ordered levels). Several independent questions can be evaluated against one shared input in a single call. Two properties make it a blind spot rather than just another endpoint: it emits **no generated text at all** — only probabilities over a caller-defined answer set — so there is no model output for content inspection to read, and at `$0.10/1M` input tokens with **no charge for output or cache** it is priced to be called on every hop of an agent loop. It is explicitly positioned for routing requests and choosing an agent's next action, which makes it agent control flow. AISPM should add `/v1/decisions` to the OpenAI API inventory as a distinct surface from Responses and Chat Completions; AIDR needs a decision-call activity type, since the only inspectable artifacts are the question set and the chosen answer. Note the cross-vendor pattern now confirmed across three vendors in three scans — Perplexity's equivalent was reported 2026-10-06 and a Foundry-side surface was announced at DevDay. Source: https://developers.openai.com/api/docs/guides/decisions

- **[ENDPOINT] [MEDIUM] Antigravity Boost and Teamwork reach Gemini Enterprise with admin controls — a hierarchical autonomous subagent fleet on the developer endpoint**: Gemini Enterprise shipped GA admin controls on 2026-10-06 for two Antigravity capabilities, which is also the first documentation of those capabilities under enterprise governance. **Boost** (`/boost`) runs a tiered multi-agent hierarchy for deep debugging and algorithmic work. **Teamwork** is the larger surface: a **Sentinel** coordinator spawns a **Project Orchestrator**, which breaks an approved brief into milestones and delegates to two distinct agent classes — **Explorers** (read-only repository research, call-chain tracing) and **Workers** (terminal and file tools, building components, refactoring, writing tests) — running parallel work tracks with per-agent scratch spaces under `~/teamwork_projects/{PROJECT_NAME}`. Human approval is a **single Phase-1 gate on the generated brief**, after which execution is autonomous; file-ownership arbitration prevents two workers touching one file, but nothing in the flow re-gates a worker's terminal access. The admin side is the coverage requirement: Gemini Enterprise administrators can now enable or disable Boost per user, and for Teamwork can **enforce workspace sandboxing and restrict browser or MCP server permissions** — meaning sandbox scope and MCP reach are now tenant-level policy settings with an auditable state that Zenity should read. ENDPOINT needs Sentinel, Project Orchestrator, Explorer and Worker as local agent entity types, the `~/teamwork_projects/` workspace as a monitored path, and the per-tenant Boost/Teamwork/MCP-permission settings as configuration to inventory. Source: https://antigravity.google/docs/teamwork/

- **[ENDPOINT] [MEDIUM] Cursor Remote Control for Local Agents — an inbound mobile channel into an agent running on a developer workstation**: Released 2026-10-06, Cursor's iOS app can now see and reply to agents running on the user's own computer, with the agent continuing to execute locally. This inverts the usual endpoint model: the agent's instruction source is no longer the local IDE session but a remote device outside the corporate network and outside any endpoint or DLP control that watches the workstation. Steering input arrives over Cursor's cloud relay, so the prompts that redirect a locally-running agent — one that holds the developer's repository access, shell and credentials — are never observable on the host. ENDPOINT should detect whether remote control is enabled for a Cursor installation and treat remotely-injected instructions as an unattributed input channel; AIDR needs mobile-originated steering as an activity type distinct from local IDE interaction. Source: https://cursor.com/changelog
