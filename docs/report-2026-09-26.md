## New Coverage Required

- **[AISPM] [HIGH] AgentCore `allowedTools` does not restrict `InvokeAgentRuntimeCommand` — the tool allowlist and the shell API are unrelated controls**: The `allowedTools` parameter on an AgentCore harness accepts glob patterns (`"@builtin/shell"`, `"@git/read_*"`, `"@*-mcp/status"`) and reads exactly like a sandbox. AWS states verbatim that it **"scopes LLM tool selection during `InvokeHarness` only. It does not affect `InvokeAgentRuntimeCommand`, which is a separate API with its own IAM action (`bedrock-agentcore:InvokeAgentRuntimeCommand`) that executes commands directly without passing through the LLM."** The documented remediation is **"do not grant `bedrock-agentcore:InvokeAgentRuntimeCommand` in your IAM policies."** Per the harness-environment audit on 2026-09-25, that API runs as **root (uid 0)** in the microVM, above the container's `USER` directive. So a harness configured with `allowedTools: ["@builtin/file_operations"]` — no shell, by every reading of its configuration — is fully shell-capable to any principal holding that one IAM action. Compounding it: **omitting `allowedTools` allows all tools**, a fail-open default. AISPM must treat `allowedTools` and the `InvokeAgentRuntimeCommand`/`InvokeAgentRuntimeCommandShell` IAM grants as **two independent controls on one harness**, and raise a toxic combination when a harness carries a restrictive `allowedTools` list *and* any principal holds either shell IAM action on it — that pairing is the signature of an operator who believes they have sandboxed an agent and has not. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-tools.html

- **[AISPM] [HIGH] AgentCore harness tool attachment — five tool types, arbitrary remote MCP by URL, and plaintext credentials in harness config**: `harness-tools` documents the full attachment surface for an AgentCore harness, each a distinct inventory entity: **`remote_mcp`** (any remote MCP endpoint by URL — AWS notes "No Gateway required for simple cases," so this path carries **no Gateway policy enforcement, no inbound/outbound auth and no access control**), **`agentcore_gateway`** (governed, policy-backed, by ARN — with outbound auth selectable as AWS IAM, **None**, or OAuth), **`agentcore_browser`**, **`agentcore_code_interpreter`**, and **`inline_function`**. Two builtins — **`shell`** (bash) and **`file_operations`** (view/create/edit) — are present in **every session** unless restricted. Critically, a `remote_mcp` tool's `headers` map holds **raw plaintext secrets**: AWS's own example is `{"Authorization": "Bearer <your-token>"}`, with the Token Vault reference syntax (`${arn:...:apikeycredentialprovider/...}`) offered only as the better alternative. Tools are settable at **CreateHarness, UpdateHarness and per-`InvokeHarness`** — so a create-time inventory snapshot does not describe what the agent actually had at runtime. AISPM must inventory harness tools as first-class entities, flag `remote_mcp` targets pointing outside the org's approved MCP set, flag literal credential material in `headers`, and flag `agentcore_gateway` tools whose outbound auth is `None`. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-tools.html

- **[AIDR] [HIGH] AgentCore interactive shells: full terminal access with a documented command-content logging blind spot, plus a shell-takeover primitive**: The `InvokeAgentRuntimeCommandShell` WebSocket API opens a persistent bash terminal inside the harness session's microVM. AWS states a principal holding it **"has interactive command access to the harness session"** and that the shell **"can access customer-provided data, files, and secrets in the selected environment or on mounted filesystems"** and reach any network destination the session can. The audit surface is the problem: **"The service doesn't log terminal input or output"** to CloudWatch, and **"CloudTrail doesn't log terminal input or output"** either — CloudTrail records only caller identity, timestamp, source IP and response status for the *connection*. Every command run against mounted EFS or bidirectionally-synced S3 filesystems is therefore invisible. Two further surfaces: authentication has a **second path that evaluates no IAM action at all** (bearer-token requests "must satisfy the harness inbound authorizer instead," with the token carried inside a `Sec-WebSocket-Protocol` value for browser clients); and **opening a second connection with the same `shellId` replaces the first**, evicting the original client with close code `4000` while the shell's environment, working directory and running processes persist — a session-takeover primitive against a live agent terminal. Detached shells keep running and do not count toward the 10-active-shell limit. AIDR must add shell-connection events as an activity type keyed on `shellId` + `runtimeSessionId`, alert on `reconnected: true` and on `4000` evictions, and record that command content is structurally uncollectable from AWS-native logs — it can only be recovered from the harness runtime itself. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-command-shell.html

- **[AIDR] [MEDIUM] Claude Compliance Activity Feed retroactively strips file names, document names and artifact titles**: As of **September 24**, the Compliance API's Activity Feed no longer returns `filename` or `title` on file, project-document and artifact activities. The fields are **"now always empty or omitted, including on activities recorded before this change"** — this is not a going-forward change, it silently degrades **already-collected history**. Resolving a name from the ID on the activity now requires a **separate Compliance Access Key scoped `read:compliance_user_data`**, which is a different (and more sensitive) credential than the feed itself needs. Any Zenity detection, DLP correlation or investigation workflow that matched on document names in the Activity Feed is now matching on empty strings and will **fail silently rather than error**. AIDR must (a) treat empty `filename`/`title` as "redacted," not "no file," (b) add the ID→name lookup as a second collection step with its own credential, and (c) re-check whether any existing rule keys on these fields. This is a coverage regression rather than a new feature, reported because it directly reduces an active detection surface. Source: https://platform.claude.com/docs/en/manage-claude/compliance-activity-feed#understand-the-activity-object

- **[AISPM] [MEDIUM] AgentCore `inline_function` tools execute client-side, and the obvious audit hook is documented as unreliable for them**: An `inline_function` tool is defined with a schema on the harness but **"executes on the client side, not on the harness VM."** The harness pauses with `stopReason: "tool_use"`, hands the call back to the caller's code, and resumes only when a matching `toolResult` arrives on the same `runtimeSessionId`. AWS names **human-in-the-loop approvals** as the primary pattern — meaning the approval gate for an agent's most sensitive actions frequently lives entirely outside AWS, in customer code, with no AWS-side record of what was approved or by whom. The harness holds the authoritative `toolUse` in session state and ignores a resent copy; a missing, duplicate, stale or replayed result cannot resume the handoff. AWS further warns to read the lifecycle-hooks caveat **"before using an `after_tool_call` event for an inline function as an authorization or audit signal"** — the natural instrumentation point is explicitly not trustworthy for this tool type. AISPM should inventory `inline_function` tools separately from server-side tools, record that their execution and any approval decision are off-platform, and flag harnesses whose privileged actions are gated only by an inline function. Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-tools.html
